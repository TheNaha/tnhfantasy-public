# Code audit — 2026-10-04 (second pass)

Sixth pass over the whole tree, run after the consolidation work that produced
`docs/audit-2026-10-04.md` was still uncommitted. Method: four read-only audit
passes over disjoint trees in parallel (backend, frontend, provider tier,
wiring/CI), every candidate finding re-derived and reproduced by hand before it
was accepted, then fixed in batches with a regression test per fix and an explicit
**revert check** — each test was run against the reverted fix to confirm it fails.
A test that does not fail on revert is not evidence, and that rule is what
separates this pass from the previous five.

## 0. The finding that mattered most: CI had been red for days

`backend-tests.yml` failed on **all five** runs of the last four days
(`37124915160`, `37120594213`, `37110029576`, `37100367848`, `37090090800`), with
the same message:

```
E       ModuleNotFoundError: No module named 'torchvision'
       .../transformers/models/aria/image_processing_aria.py:11
       └─ transformers/__init__.py:2301 _LazyModule
tests/conftest.py:110: in _redirect_session_sync
E       AttributeError: module 'transformers' has no attribute 'get_session_sync'
```

`tests/conftest.py` walked `sys.modules` and did
`getattr(module, "get_session_sync", None)` on **every** module to rebind the
sync session helper. `getattr` is not a passive read: `transformers` defines a
PEP 562 module-level `__getattr__` that resolves an unknown name by *importing
the submodule it names*. Probing `transformers` for `get_session_sync` therefore
imported `transformers/models/aria/image_processing_aria.py`, which imports
`torchvision` — which is not in `requirements.txt`. The autouse fixture raised, and
because it is autouse every test that ran afterwards errored too: **1355 of 2832
tests**.

The local venv cannot import `transformers` at all (no embedding stack), so the
suite was green here and red in CI. The consequence is larger than one red badge:
every "verified green" claim in the previous passes was a local observation. The
audit history is not wrong about the code, but it was not measuring what CI
measures.

Fixed by narrowing the rebinding loop to modules that belong to this backend
(`backend_v2/...`). A module has to hold one of the two original function objects
to be rebound, so nothing outside the backend was ever a legitimate target.

**`torchvision` is still not in `requirements.txt`.** The fixture no longer trips
over it, so the embedding stack's own coverage remains unverified on CI. That is
open (§4, A1).

## 1. Security

### S1 (P1, fixed) — the frontend re-published the API it was supposed to front

`docker-compose.yml` published the frontend on `0.0.0.0:5174`, with a comment
explaining why that was fine:

> Left as-is deliberately: unlike the backend this one is a dev server you open in
> a browser, and binding it to loopback bought nothing because Traefik's frontend
> router already existed and **the backend API was the actual exposure**.

The reasoning inverts cause and effect. This service is a reverse proxy to that
API — `frontend_v2/nginx.conf` has `server_name _` and forwards `location /api/`
to `backend_v2:8002` with no host check — so publishing it publishes the API.
Measured on the running stack before the fix:

```
curl http://192.168.1.28:5174/api/ready     -> 200
curl http://192.168.1.28:8002/api/ready     -> 000   (no host port, as designed)
```

So `0.0.0.0:5174` served the entire unauthenticated API — every prompt, every
story, and `DELETE /api/jobs`, which is how 154 rows of job history were deleted
on 2026-10-01 — to every interface, including the plain home LAN that NetBird does
not cover. Removing the backend's host port was undone at the proxy in front of it.

The backend has no host port *because* Traefik reaches it on the external `proxy`
docker network. The frontend needs no host port for the same reason, so binding
it bought nothing **except** the boundary.

Fixed by deriving the bind from `COMFY_FRONTEND_BIND`, defaulting to loopback, with
one deliberate subtlety: a single host address cannot be both `localhost` and a
VPN address, and losing `http://localhost:5174` is not a trade worth making. So
the compose file publishes **two** bindings — `127.0.0.1:5174` unconditionally and
`${COMFY_FRONTEND_BIND:-127.0.0.2}:5174` — and `127.0.0.2` is inside
`127.0.0.0/8`, so the unset case publishes loopback twice and exposes nothing.
Docker rejects two identical bindings (`address already in use`), which is why the
second default is a *distinct* loopback address rather than a repeat.

`scripts/preflight.sh` gained a **Network exposure** section that fails on a
wildcard bind, reports a loopback bind as `ok`, and `note`s a named address.

Verified access, before and after:

| Path | Before | After |
|---|---|---|
| `http://localhost:5174/` | 200 | **200** |
| `http://100.150.0.4:5174/` (Tailscale) | 200 | **200** |
| `http://192.168.1.28:5174/api/ready` (home LAN) | **200** | **000** |

## 2. P0 — a failed request rendered as a reason to generate

### F1 (P0, fixed) — the dashboard reported "No images yet" when the fetch failed

`src/pages/Dashboard.jsx` destructured `useGallery(filters)` without `isError`, so
`DashboardGalleryGrid.jsx` fell through to its empty state. Reproduced live by an
auditor against the running stack, intercepting the request and returning 503:

```
FAILED-FETCH: no-images-yet= true | CTA= true
"Can't load images — No images yet. Start creating amazing AI-generated images"
```

…while the same page printed **"Matching total unavailable"** in the facet panel
beside it. The UI contradicted itself on one screen: an outage reported as an
absence of data, with a "Generate Your First Image" button pointed at it. The
sessions query 390 lines away in the same file was already error-gated.

Fixed at both ends, and `src/test/queryErrorInvariants.test.js` was widened from
`src/pages/*.jsx` to all of `src/**`, because the empty state that lied lives in a
*component*. The rule is "emptiness that derives from query data", which keeps
`StorySandbox.jsx`'s `!activeStoryId` (a route param, not a query) correctly
exempt — a naive version of that test false-positives on it.

Widening the guard immediately found **two more of the same class**, neither in any
prior audit: `MemoriesPanel.jsx` ("No memories yet" on a failed fetch) and
`CollectionsPanel.jsx` ("Collection is empty" on a failed fetch). Both fixed.

### F2 (P0/P1, fixed) — five unguarded `navigator.clipboard` dereferences

`navigator.clipboard` is `undefined` in a non-secure context, and `.writeText`
then throws a **synchronous** `TypeError` before returning a promise — so
`.then()/.catch()` never attach. Measured on the documented LAN host:

```
http://100.150.0.4:5174  -> {"secure": false, "clip": false}
http://localhost:5174    -> {"secure": true,  "clip": true}
```

`src/utils/clipboard.js` already guards this and was used by 4 components; five
call sites bypassed it. The worst was `components/story/ExportModal.jsx`, where
`onSuccess` copied and *then* called `onClose()`: the throw skipped `onClose()`, so
the modal stayed open reading **"Story published — link copied!"** with no link and
Publish still enabled — a **second publish** on the next click. `Prompts.jsx`
incremented the prompt's usage counter *first*, so a failed copy left the counter
moved and no feedback at all.

All five now route through `copyToClipboard`. Fixing this surfaced a bug in the
guard itself: the `execCommand` fallback called `removeChild` only on the success
path, so a throwing `execCommand` leaked an invisible focusable `<textarea>` into
the live DOM on every failed copy. Moved to `finally`.

**Correction to the prior audit:** it claimed `Prompts.jsx:52` "reports success on
a rejected copy". That is **refuted** — it had a `.catch` at `:54-56`. The defect
is the absent-property case only. Saved so it is not re-raised.

## 3. Backend correctness

### B1 (P1, fixed) — `update_job`'s FSM guard authorised over a concurrent terminal state

`job_service.py` guarded its status transition against
`repo.get(job_id)` → `session.get(Job, id)`, which is **identity-map first, no
SELECT**. A cancellation committed from another Session was invisible, so a later
terminal write was authorised and destroyed it.

One correction to the reproduction as first written: it does not reproduce as
stated. `Session.identity_map` holds only **weak** references, so a `repo.get(...)`
used as a bare temporary is collected before the next statement and the next `get`
re-SELECTs and sees the truth. The defect bites while something holds a strong
reference — which is exactly what production does, because `cancel_job` does
`job = await self.get_job(job_id)` and then calls `update_job`. The regression test
holds the job in a list and asserts it is still `SENT_TO_PROVIDER` before the
write, so the staleness is **proven, not assumed**.

Fixed with a conditional write, `UPDATE … WHERE id = :id AND status = :expected`,
treating 0 rows as the `invalid_fsm_transition` the guard already emits.
Deliberately *not* fixed in `get_job`: `get_job` calls `session.refresh(job)`, so
the four mid-flight terminal guards in `job_runner.py` are already sound.

### B2 (P1, fixed) — a failed enqueue stamp stranded a job forever

`_mark_enqueued` swallowed every exception, so the compensating delete was
unreachable for the only failure that strands a row. A stranded row is
`PENDING / claimed_at IS NULL / enqueued_at IS NULL`; `job_queue.py` requires
`enqueued_at IS NOT NULL` to claim it and `recover()` does not touch it — so it
counted in `summary["pending"]` forever.

Fixed by re-raising only when DB claims are in use, preserving the documented
SQLite behaviour (SQLite has no `now()`, so the stamp always fails there — which is
what made both halves of the gate testable without mocking). Added an
age-bounded stale-PENDING failure pass to `recover()` as a second line of defence.

Deviation worth recording: the window is **900 s**, not `STALE_JOB_TIMEOUT_SECONDS`
(300 s). Several callers create a PENDING row and then run the work themselves
(the orchestrator, the agentic narrator, ~12 more), so 300 s would kill a live
inline LLM job. A stranded row can never be rescued by waiting; a long inline job
must not be.

### B3 (P1, fixed) — three Docker probes lied, and a fourth 500'd on the same outage

`_probe_container` and `_container_status_sync` both caught `Exception`, logged at
**debug**, and returned `"stopped"` — indistinguishable from "container absent".
The route cached the lie for 10 s while asserting `container_runtime_available:
true`. `provider_runtime.py` had a third copy of the same swallow.

Worse, and not in the prior audit: `list_containers()` had **no** exception
handling, so `GET /api/v2/providers/containers/list` returned **500** when the
Docker runtime was down, while `GET /api/v2/providers/containers/status`
simultaneously reported every container `"stopped"` with
`container_runtime_available: true`. Same host, same second, opposite answers.

Probes now raise on a non-`NotFound` error and cache nothing; `list_containers`
degrades to `([], False)`; the route computes the flag and only caches when true.
A new `"unreachable"` status distinguishes "the runtime cannot be reached" from
"the container is not running" — and the frontend renders it correctly with no
change, because `providerStatus.js` humanises unknown statuses and falls back to
an offline tone.

One existing test was changed rather than satisfied:
`test_snapshot_failure_reports_stopped` asserted, in full, that a raising snapshot
resolves to `{"status": "stopped"}`. That assertion *is* the defect; there is no
weaker version of it that is not the lie. Renamed, inverted, and reasoned in the
docstring. Two further route tests were found to be **vacuous** — they patched
`api.deps.get_container_manager`, which the route never reads because
`get_container_manager` resolves from `request.app.state`. They now use
`app.dependency_overrides`, which is what turned them from passing-on-revert into
failing-on-revert.

### B4 (P1, fixed) — `progress` percent was normalised twice at the provider seam

`provider_core` normalises progress to percent 0..100. The backend then re-applied
a legacy heuristic for containers predating that:

```python
percent = int(val * 100) if val <= 1 else int(val)
```

Its `val <= 1` branch reads a worker reporting exactly `value == 1` — **one
percent done** — as a fraction and records **100**. A job that appeared finished
had not run at all, silently, on the most-watched number in the UI. No worker
emits fractions any more, so the branch could only ever misfire.

The provider tier now names the unit on the wire (`TaskEvent.value_unit`), so the
unit decides and an absent unit keeps the legacy reading for un-redeployed
containers. The heuristic is kept deliberately; only the ambiguity is removed.

### B5 (P2, fixed) — five declared indexes were never created on a fresh install

`test_migration_indexes_exist.py` reads `pg_indexes`, but the CI Postgres is an
empty `pgvector/pgvector:pg16` container, so it reported every declared index
missing. Fixed by migrating the database it reads — which turns it into a stronger
assertion: not "some prepared database has these indexes" but "running the app's
own `create_all` + `run_migrations` produces them".

That immediately exposed a real defect the previous pass's index work had missed,
the same class as commit `a23344cd`:

- `character_memories.embedding` is a pgvector `Vector`, and its index is
  `USING hnsw (embedding vector_cosine_ops)`. A SQLModel column with
  `index=True` can only ask SQLAlchemy for a plain btree, so `create_all` creates
  the table without it; and migration 041 creates the table *and* its indexes but
  early-returns when the table exists — which on a fresh database it always does,
  because `create_all` runs immediately before the steps runner. **Semantic
  character-memory search had no vector index on any fresh install.** Added
  migration `081_operator_class_indexes`, idempotent, Postgres-only.

Three of the other four "missing" indexes were a **guard defect, not a product
defect**, and the distinction matters: a column declared `index=True` is emitted
by `create_all` under SQLAlchemy's default name (`ix_voice_models_character_id`)
while the migration calls the same index `idx_voice_models_character`. The guard
compared *names*, so it could not tell "absent" from "present under another name",
and it also could not see the one index that genuinely was absent. It now matches
by **coverage** — table plus key expression — parsed with a balanced-paren scan so
an expression index like `coalesce(generated_at, created_at)` compares whole. That
parser also had to learn two things the first version got wrong, both found by
revert checks: statements split across adjacent Python string literals have a
quote character between the name and `ON`, and seven indexes were silently dropped
from the coverage check because of it.

`idx_campaigns_name` is recorded in a new `RETIRED` map with its reason: the
`campaigns` table is dropped by migration 077 (renamed to `worlds`), so the two
`CREATE INDEX` statements that remain in `steps.py` can never run again.

### B6 (P2, fixed) — four smaller ones, each with a test

- **World Timeline** surfaced soft-deleted images (13 other asset reads filter
  `deleted_at IS NULL`; this one did not) and ordered its window on `created_at`
  while the merge sorts on `generated_at or created_at`, so deep pages silently
  dropped events. Now reuses `ASSET_GALLERY_TIMESTAMP` rather than inventing a
  third definition.
- **`search_prompts`** built `LIKE :like` with **no `ESCAPE` clause**, so `100%`
  matched `100 percent`. The shared `like_contains` helper is now used *and* the
  `ESCAPE` clause added — both halves are required, as the helper's own docstring
  says.
- **`batch_get_metadata`** resolved up to 1000 names with no session, so each name
  checked out its own pooled connection. Measured on revert: **80 pooled
  connections for one batch of 40 names**, versus 1.
- **`get_runtime_state`** mutated module-level `_runtime_states` with no lock,
  though the lock exists two functions above. Two more functions do the same, and
  `remove_provider_state` iterates the dict — so a concurrent insert can raise
  `RuntimeError: dictionary changed size during iteration`. Latent (no cross-thread
  caller found) but one line from real. Fixed under the lock, released immediately
  in the two that also take an async store lock.

## 5. Provider tier

**There is no P0 in this tier.** Every destructive path correctly refuses to delete
when validation is `indeterminate` (four call sites), and no path was found where a
transient error deletes a valid model or file. `get_safe_path` is total at all 11
call sites. This was verified, not assumed, and it is the most reassuring result of
the pass.

Fixed:

- **`_scan_directory` swallowed `scandir`/`stat` failures** and returned `[]`, so
  one transient EIO on `models/checkpoints` made every model in that directory
  look missing and re-downloaded the whole directory of multi-GB checkpoints. Now
  raises, matching what all three `_fetch_dir` closures already expected.
- **An unguarded `getsize`** on a transient artifact raised out of the LLM
  validator's 16-directory loop with no `try`, so one `ENOSPC` lost the entire
  sweep and reconciliation logged "⚠ Validation step failed" and ran with no data.
  Reproduced: `RAISED: OSError: [Errno 28]`. Now returns a per-directory `error`
  key, which is what the agent's engine already did.
- **A failed validation HTTP call returned `{}`**, which reconciliation reads as
  `total_invalid == 0` and logs **"✓ All existing models are valid"**. A 401 from a
  token mismatch therefore read as a clean sweep on two of three engines. Now
  raises, as the Modal twin already did.
- **A chunked download was never size-verified.** A 206 with no `Content-Range`
  total set `total_size = 0` and skipped every size comparison. Reproduced: a
  **60 202-byte body published as a 7 000 000-byte model**, while the same body
  with a declared total was correctly rejected. Publishing now refuses an undeclared
  total outright.
- **The consolidated SSE parser dropped a frame split across two `data:` lines.**
  Reproduced: payloads `['{"choices":[{"delta":', '{"content":"Hi"}}]}']` parsed to
  `[None, None]` — a silently truncated answer, the exact class the consolidation
  was meant to end. Now buffers per the EventSource algorithm. Two smaller
  divergences fixed with it: a bare `data:` line yielded `""` (logged as a JSON
  error by one engine, skipped by two), and a blanket `.strip()` mangled payloads
  whose JSON legitimately begins with whitespace.
- **`remote_agent` blocked the event loop with a 512 MiB synchronous write** — the
  one heavy op in the file that missed `_bounded_to_thread`, which itself had **no
  timeout**, so even the threaded calls could hang the pool forever. Both fixed;
  `delete_model`'s `rmtree` moved off-loop too. Its Dockerfile healthcheck
  hardcoded `8001` while the app reads `$PORT`.
- **`ENOSPC` parked an uncompletable partial**, and the next attempt's
  `_claim_resume_slot` renamed the multi-GB slot back and appended into the same
  full volume. Parking is right for `indeterminate` and wrong for "the filesystem
  said no". A pre-flight free-space check now runs before any body byte.
- **`pending_download_paths` matched temp files by basename prefix**, so
  `foo.safetensors` also swept `foo.safetensors.fp16.safetensors.999….downloading`
  — and that is a legal name for a *different* model. This helper is the
  **authorisation gate** on the delete routes (four call sites), so a false
  positive there authorises a delete. Now matched structurally against the two
  generators, with the regexes defined beside them and a test derived by calling
  them so a rename cannot silently break matching.
- **Three engines disagreed on `list_models` failure.** Two returned a hardcoded
  5-model list; the backend only falls back to `[{"id": "default"}]` when the list
  comes back *empty*, so the fabricated list suppressed the honest fallback and a
  revoked key yielded five selectable ids that all fail per turn. The two engines
  that return `[]` were behaving better than the two that fabricate. Now `[]`
  everywhere.

### Test doubles that were themselves wrong

Fixing F4 was only possible after correcting a double: `test_lock_resume.py` used
a plain `dict` for response headers, so `headers.get("content-length")` missed its
own `"Content-Length"`, `total_size` was always 0, and **no size check ever ran in
that file**. The 206-without-a-total case could not have been caught.

Two more doubles fed `data:` lines with no blank-line separators, which real SSE
servers always send, so the framing tests were asserting against a shape that does
not occur.

### A flake that was not a flake

`test_416_with_a_matching_size_is_treated_as_complete` failed roughly 1 run in 8
**on the pristine tree**. The fake origin appended `{"status": None}` to a shared
list and filled in the status *after* `end_headers()` — so the client could read
the response and the test read `None`. Reordering the assignment before the headers
go out makes the write happen-before the socket write. 25 consecutive full-file
runs: 0 failures.

### A claimed duplication that does not exist

`llm_worker/engines/anthropic/client.py` vs `google/client.py` was reported as
**213 byte-identical non-blank lines** (difflib ratio 0.589). Measured per method
by AST: 17 shared method names, **11 byte-identical methods totalling 29 lines**,
all 1–3 line stubs. `inference` is 58.7% similar with 12 of 119 lines identical at
the same position; `get_health` 44%. The `difflib` ratio is a *matched-line*
ratio, not an identity count. The only genuinely extractable overlap is 18 lines,
in exchange for a base class on a `provider_id`-dependent contract four engines'
tests exercise. **Left alone deliberately** — behaviour preservation is worth more
than line count.

## 6. Guards that could not fail

Five of these are the same defect: a hand-maintained list, or a regex that matches
nothing. Each was repaired to be generated from the thing it constrains, and each
was proven able to fail.

| Guard | Why it was blind | Repair |
|---|---|---|
| `conftest.py` rebinding | `getattr` on a PEP 562 module imports a submodule | Scope the loop to backend modules |
| `test_migration_indexes_exist` | Compared index **names**; CI read an unmigrated DB | Match by coverage; migrate the DB it reads |
| `test_e2e_endpoint_contract` | Checked **paths only**, so a correct path with an incomplete body passed | Resolve request bodies against `requestBody.required` |
| `eventContractInvariants` | The producer search matched the enum **against itself**; both parse regexes required an exact format, so a re-added `DOWNLOAD_*` member vanished and `len > 15` passed; 141 co-located `*.test.js` counted as production subscribers | Cut the enum body out of `core/events.py` only; relax the regexes; filter `*.test.js`; assert both sides parse to the same member set |
| `hoverRevealInvariants` | `/group-hover\\\/([a-z0-9-]*):opacity-100/` cannot match, because Tailwind escapes the colon — as-written matches `[]`, the fixed regex matches `["message","chat-row","menu-item",…]` | Fixed the escape, then removed the two stale names it revealed |
| `settingsKeysHaveReaders` | An `EXEMPT` line silenced any key with no "still needed" counterpart | Ported the staleness check from `querySignalInvariants` |
| `paginationTerminationInvariants` / `promptCategoriesInvariants` / `iconButtonAccessibility` | New. Each has a staleness case, and each caught a real exemption during this work | Adopted the fixes and deleted the entries |

The last three earned their keep immediately: I adopted the three fixes they had
exempted (blocked at the time on files another agent owned), and the staleness
cases failed telling me to delete the exemptions.

Two guards were **vacuous for a different reason** — they patched
`api.deps.get_container_manager`, which no route reads, because it resolves from
`request.app.state`. They now use `app.dependency_overrides`.

### The "known flake" that was deterministic

`docs/STATUS.md` carried
`test_lifespan_runs_every_declared_startup_phase` as a load-related flake. It was
not load. Its `EVENT_BUS_TOPICS` listed `"download"`, which has had no
`EventType` behind it since the family was removed on 2026-10-03, so
`assert 0 > 0` for `download` could never be satisfied by a correct lifespan. It
failed identically in 24 s alongside 67 other tests. The list is now derived from
`EventType`, and the comment records that the label was wrong.

### The dead websocket room

`websocket.py` allowlisted `"download"` as a subscribable topic and acked
subscriptions to it, while the room name is derived from `EventType` — so the room
could never receive an event. A client asking for it got `subscribed` and then
silence. Both copies of the list (the broadcast subscription and the subscribe
allowlist) are now derived from one `BROADCAST_TOPICS` constant, guarded by
`tests/test_websocket_topic_contract.py` in both directions.

Note `tests/test_websocket.py::test_subscribe_multiple` asserted that a client
*could* join the dead room. That test was pinning the defect, and it is replaced
with one that asserts the topic is refused.

### Two phantom `TaskEvent` kinds

- **`artifact`** — in the `Literal`, the docstring and `_TASK_EVENT_KINDS`, with no
  producer anywhere and no branch in the reducer. The reducer's `if/elif` chain has
  no `else`, so it would be dropped silently by both ends. **Removed.**
- **`started`** — the backend's *only* writer of `JobStatus.PRE_GENERATION`, which
  is what `JobCard`'s "Preparing" state renders from, and no worker emitted it. So
  that status and that UI state were unreachable: a job went straight from queued to
  generating. **Emitted**, in `router.py` — the one request path every image
  worker's `/inference` passes through. Deriving it from ComfyUI's own
  `execution_start` message does not work: a fully-cached graph emits
  `execution_cached` and never starts executing, and the websocket reader does not
  handle `execution_start` at all.

`tests/test_task_event_contract.py` asserts both directions — every declared kind
has a producer *and* a handler — plus that `_TASK_EVENT_KINDS` is derived rather
than retyped.

## 7. Consolidation

- **Nine ad-hoc byte formatters, one model, three renderings.** A 2 GB model read
  `2048.0 MB`, `2048 MB` and `2.00 GB` in three places. Now one
  `src/utils/bytes.js`, with the convention stated in the docstring — including
  that `size_kb` is **kibibytes**, which the consolidation surfaced as a live bug:
  `ModelImportCard.jsx` read it as MB while `ModelGridCard` read the same field as
  GB. Guarded against a tenth copy.
- **Four pagination implementations.** The two that hit `/api/files` disagreed:
  one compared `length === 50` and ignored `total`; the other was total-aware.
  Consolidated onto one total-aware helper (`total` when sent, terminate on an
  empty page, cursor always advances).
- **The prompt-category list, four times.** The three component-level fallbacks
  were not dead as claimed — `useQuery().data` is `undefined` before the first
  resolve, so the hook needs `placeholderData`. One constant now.
- **Seven `useCallback`s depending on a `useMutation` result object.** React Query
  v5 returns a fresh literal per render, so every action callback was new every
  render. `useFavorites.js` documents the hazard and destructures `mutate`; that is
  now the pattern, with a structural guard.
- **`useModelDirectories`' memo could never hit.** `useQueries` with no `combine`
  returns a fresh array identity every render, so all six consumers got a new
  `modelsByKey` object per render. Fixed with a `combine`.
- **24 icon-only close buttons with no accessible name** — 38 in fact, once
  `<img alt="">` children and non-close icon buttons were included. Guarded by a
  test that parses the JSX recursively.
- **Lint warnings 11 → 6.** The five `BatchGenerate` ones were not the identity
  churn; they read `modelsByKey.checkpoints || []`, a fresh `[]` per render,
  independent of identity, and a module-level `NO_MODELS` constant removes them
  properly.

## 9. Verification

Every fix above has a regression test, and every test was run against the reverted
fix to confirm it fails. The report for each was required to state the revert
result explicitly; a test that does not fail on revert was treated as no test.

Two findings in this pass came from **revert checks failing to fail**, which is
the argument for doing them:

- The e2e body guard passed on the reverted defect because a `...overrides` spread
  made it skip the one call site it was written for.
- Its schema unwrap returned the *media-type map* as if it were the schema, which is
  truthy and has no `required` key — so it read "nothing is required" and passed
  everything.

  "string" that swallowed every brace to the next apostrophe in the file.
- Its literal search reached past the call's closing paren into an unrelated object
  literal, reporting three valid helpers as omitting required fields.

Four independent ways for one guard to pass while checking nothing. The canary
tests added alongside each are the actual deliverable.
