# Codebase audit — 2026-10-05 (pass b)

**Scope.** Whole repository, whole stack: `backend_v2/`, `frontend_v2/`,
`provider_containers/`, `remote_agent/`, `scripts/`, `docker-compose*.yml`,
`.github/workflows/`, `docs/`.
**Supersedes** `audit-2026-10-05.md` for everything it marks fixed, and inherits
its findings as still-open unless listed below. This pass closes that gap.

**Why this pass exists.** The 2026-10-05 audit was written ~1 h before this one
and is thorough. Two things were still true when this pass started:

1. The tree was **mid-consolidation**, with long-standing open items unclosed.
   Ten of the seventeen backend dead symbols had already been listed as OPEN in
   `audit-2026-09-27.md`, `2026-10-01.md`, `2026-10-03b.md` and `2026-10-04.md`.
   The pattern was "known, triaged, never closed" — the audits were accumulating
   findings rather than retiring them.
2. Nothing had been **measured**. Prior audits reasoned about the hot paths from
   code shape. This pass ran the stack.

**Baseline at the start of this pass** (both suites green, which is worth stating
because it is what made the defects below invisible):

- `backend_v2`: **3096 passed, 9 skipped**
- `frontend_v2`: **1615 passed in 178 files**
- `ruff check .`: clean · `npm run lint`: **0 errors, 6 warnings**
- Live stack up: `tnhfantasy-backend` 8002, `tnhfantasy-frontend` 5174, `tnhfantasy-db` 5432

A green suite is not evidence of correctness. Every P0 and P1 below passed
before it was found.

## Method

Eight parallel read-only audits over disjoint scopes, each required to
**refute its own findings** before reporting and to mark VERIFIED or UNVERIFIED:

| Scope | Outcome |
|---|---|
| `backend_v2` api/services/core/infrastructure | 12 verified + dead-code inventory |
| `frontend_v2` hooks/api/store/utils | 12 verified |
| `frontend_v2` pages/components | 14 verified + duplication inventory |
| `provider_containers/`, `remote_agent/` | (see open list) |
| Cross-seam contract drift | (see open list) |
| Performance & database (**measured**) | 14 verified, 40+ measured tables |
| Dead code / non-functional sweep | 14 verified + 4 inventories |
| Infra / CI / docs coherence | (see open list) |

Then one own pass: a Playwright crawl of **all 32 routes** recording console
errors, page errors, failed requests and every HTTP ≥ 400, plus direct
`curl`/`EXPLAIN (ANALYZE, BUFFERS)` measurement of every hot endpoint against the
running stack.

**The crawl found nothing.** 32 routes, **0 console errors, 0 page errors, 0
unexpected non-200s**, every route rendering 440–1900 characters of real content.
Every `ERR_ABORTED` in the trace is React 18 `StrictMode` double-mounting in the
Vite dev server, not a defect.

That negative result is the most important methodological finding in this
document: **the app is not visibly broken.** The defects below are defects in
*cost*, in *truthfulness*, and in *wiring* — things a smoke test and a green
suite both pass.

## Error states: an outage that renders as "you have nothing"

The single largest defect class in the frontend, and the one the project had
already named as "first thing to do next" in `STATUS.md`.

A failed `GET` and an empty collection produced **identical pixels**. The user is
told they have no prompts, no entries, no scenes, no tags — and invited to
create some they already have. `Prompts.jsx` rendered *"0 saved prompts / Start by
adding your first prompt!"* on a 500. `Lorebooks.jsx`'s entries panel said *"No
entries yet. Add the first one."* right beside a working Add form.

The structural reason this survived: **`queryErrorInvariants.test.jsx` only
detected `<EmptyState` call sites.** Hand-rolled `<div>`/`<p>` empty states were
invisible to the guard that was supposed to prevent them — a guard that cannot see
the code is not a guard.

Fixed and, more importantly, made detectable: the invariant now also scans for
hand-rolled "you have nothing" copy, combined with the existing
`guardBefore`/`isQueryDerived` machinery so only query-derived sites count. A
guard that cannot fail is not a guard, so every exemption is explicit and
commented, and a canary proves the new rule can fail.

## Decisions this pass refused to make

Three items are the same question — *wire it, or delete it?* — and have now
survived four audits precisely because nobody has answered it. They need the
owner's call, and guessing would be worse than leaving them visible.

1. **`enable_memory_snapshot`** — the backend reads it and sends `use_snapshot`
   in the payload; **no worker in `provider_containers/` or `remote_agent/` reads
   it**, and the `ENABLE_MEMORY_SNAPSHOT` env var `modal_config.py` emits is read
   by nobody either. The Settings toggle is a control wired to nothing. Wiring it
   for Modal is not mechanical — `enable_memory_snapshot` applies to
   `@modal.fastapi_endpoint`/ASGI apps, and every Modal method here is a plain
   `@app.function` RPC, so a naive implementation would be wrong in a new way.
   *Wire it (with a supported path), or remove the control and the field?*
2. **`ProviderVersionStatus.verified_at`** — a real column commented "Last
   integrity check", and there is **no integrity check anywhere in the codebase**.
   Same question: implement the check, or drop the column?
3. **`ModelV2.stats_updated_at`** — a column that is `NULL` on every row forever.

## Deployment: the biggest win is already built

`frontend_v2/Dockerfile` has a complete, correct `prod` stage — nginx, non-root
uid 1000, `location /api/` and `/socket.io/` proxied to the backend, healthcheck
support. `docker-compose.yml` already defaults to `target: prod`.

**It is never used**, because the documented full-stack command
(`AGENTS.md` → `bash setup_jules.sh`, and the compose line in "Quick commands")
applies `docker-compose.dev.yml`, which overrides to `target: dev`. So the
deployment that serves the LAN/VPN site is a dev server: every query twice,
unbundled source, `StrictMode` double-effects.

Verified during this pass: `docker compose -f docker-compose.yml build frontend_v2`
builds, and the image is nginx-as-`app` with the built assets and four
`proxy_pass` directives.

This is not a code defect but it is the largest single quality-of-use problem
measured, and it is a *choice* rather than an oversight — the dev override is
legitimate when you want HMR. What is missing is any way to tell which one you
are on.

## Method notes and corrections to prior work

- **The "many functions are literally non-functional" premise did not hold for
  `pages/` and `components/`.** Every suspicious handler traced to a live backend
  route. Four source-scanning guard tests defend that layer, and the residue was
  error-state and accessibility defects, not dead handlers. The genuinely
  non-functional controls were in *settings* and *config* (items 9, 10, 18 above)
  and in the **dev/prod deployment target**.
- **`refetchPage`** — a prior audit called the gallery's refetch-page fix dead
  code because `refetchPage` is not a react-query v5 option. Correct, and the fix
  never worked; superseded here by the `queryErrorInvariants` work.
- **Session-detector `_load_rows`** and **`/api/files?sort=name_asc`** were both
  reported in earlier audits and both were still present when this pass started.
  Item 4 above is the first fixed, with a before/after measurement.
- **10 of 17 backend dead symbols** appear in ≥ 1 prior audit. Audit documents
  that accumulate findings without closing them are themselves a defect: this
  document records every fix with the test that fails without it, so the next pass
  can verify rather than re-derive.
