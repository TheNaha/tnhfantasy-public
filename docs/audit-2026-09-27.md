# Codebase audit — 2026-09-27

Consolidation-pass audit of TNHComfy: backend, frontend, provider containers,
infrastructure. Four independent read-only sweeps, every finding verified against
the source at the time of reading, then triaged and fixed.

Supersedes `docs/audit-2026-09-26.md` and `docs/audit-2026-09-26-followup.md`
for everything marked **FIXED** below. Those two documents' still-open lists are
not repeated here; see "Relationship to the previous audits".

## 1. P0 — committed live credentials

**`provider_containers/rclone_tf.py` — FIXED (file deleted)**

The file contained a Google OAuth client secret, an OAuth access token, three
OAuth refresh tokens and four rclone crypt passwords, in plaintext, in a tracked

1. rotate the Google OAuth client secret;
2. revoke all three refresh tokens;

4. `git filter-repo --invert-paths --path provider_containers/rclone_tf.py`,
   force-push, re-clone.

A secret scanner in pre-commit and CI is the actual fix for the class.

## 2. P0 — every unhandled exception took ~22 seconds to become a 500

This was the single most expensive defect in the codebase, and it was invisible
because the tests it broke were *also* slow and nobody had run them recently.

### The chain, each link verified at runtime

1. `backend_v2/infrastructure/logging.py` ended its file with a bare
   `# Initialize` comment and **never called `configure_logging()` at import**.
   It was only called from the FastAPI lifespan.
2. A structlog proxy binds its processor chain **on first use and never
   rebinds**. So every module-level `logger = get_logger(...)` — `api/main.py:50`,
   `api/error_handlers.py:19`, and most of `services/` — captured structlog's
   DEFAULT chain. Verified: `error_handlers.logger._processors[-1]` was
   `ConsoleRenderer`, while `structlog.get_config()['processors']` said
   `compact_renderer`. The two disagreed, which is the whole bug.
3. `ConsoleRenderer.__call__` (`structlog/dev.py:956`) hands `exc_info` to
   `RichTracebackFormatter.__call__` (`structlog/dev.py:466`), which builds a
   `rich.traceback.Traceback` and **pretty-prints the locals of every frame**.
4. `rich` is importable because **`modal` depends on it**. Whether the
   expensive path was taken depended on an unrelated package's dependency tree.
5. A frame holding a SQLAlchemy `Session`/`Connection` is an unbounded object
   graph. `rich.pretty.pretty_repr` walked it for ~22 s. Confirmed by 6 of 6
   `faulthandler` thread samples landing in `rich/containers.py` via
   `rich/pretty.py:check_length`, reached from `api/error_handlers.py:125`.

The handler runs on the event loop, so this was a self-inflicted denial of
service: one bad request froze the entire application for 22 seconds.

### Fix

- `configure_logging(...)` is now called at **import** in
  `infrastructure/logging.py`, with a comment saying it is load-bearing and must
  not move back to the lifespan.
- `compact_renderer` now renders `exc_info` itself, via a new bounded
  `_format_exc_info`: 40 frames, 16 000 characters, tail kept because that is
  where the failure is. Rendering is deliberately hand-rolled so it cannot
  become rich's locals renderer again if `rich` is installed tomorrow.

The traceback is now **better** than it was, not worse: it is printed, and it is
not 22 seconds late.

### Measured effect

| | before | after |
|---|---|---|
| unhandled exception → 500 | 22–45 s | 0.22 s |
| `tests/test_image_tags.py` (57 tests) | 868 s | 3.3 s |
| full backend suite | 1097 s | 220 s |

Regression tests: `tests/test_logging.py::TestExceptionRenderingIsBounded`
(5 tests, including one that fails loudly if frame locals are rendered again).

### Side effect worth knowing

One existing test was passing only because of this bug: it asserted on
structlog's `ConsoleRenderer` bracket format (`"[error" in logged`). It now
asserts the app's own level token. See item 8.3.

## 3. P0/P1 — backend correctness

### 3.1 `GET /api/v2/assets/facet` was 100% dead — FIXED

Two independent defects in `api/routes/world_vault/tags.py`:

- `tags.py:717` called `_parse_id_list(lora_model, "lora_model")` against a
  one-argument signature → `TypeError` on **every** request.
- The facet SQL was built with `select(subquery_column)`, which makes SQLModel
  treat the column as a FROM element. The result was a cartesian product
  between `assets` and the subquery (SQLAlchemy's own `SAWarning` says so), and
  unpacking the row raised `TypeError: 'int' object is not subscriptable`.
  Rewritten against `_matched_ids()`, which returns a `Subquery`, and the count
  queries now use the **subquery's** columns rather than `Asset.*` — using
  `Asset.*` there is what put `assets` back in the FROM.

`total_matched` had the same unpack bug: `session.exec(...).one()[0]`, where
SQLModel already unwraps a single-column select to a scalar.

### 3.2 `tag_service.reindex_asset_tags` ignored its own `limit` — FIXED

`limit` was checked *after* the batch had been processed, so it bounded the
number of batches inspected, not assets processed. `reindex_asset_tags(limit=2,
batch_size=10)` over five assets tagged all five and reported `processed=5`.
The fetch size is now `min(batch_size, limit - processed)`, and `truncated` is
computed by asking whether more rows exist rather than being hardcoded `True`.

### 3.3 An asset could never converge to zero auto-tags — FIXED

`reindex_asset_tags` did `if not asset.metadata_: skipped_no_metadata += 1;
continue`, which bypasses `auto_tag_asset` — the one function whose docstring
says "a later pass that finds no vocabulary must converge to zero tags, not
leave the old set in place". An image whose LoRA metadata was cleared upstream
therefore kept its stale auto tags forever. The counter is kept; the `continue`
is gone.

### 3.4 `POST /api/v2/jobs/recover` could fail open on a DB error — FIXED

`api/routes/jobs.py:_active_job_ids` had `except Exception: return set()` with
the comment "a DB failure must not block recovery". The empty set is not the
conservative answer: `recover_jobs` branches on `if active_ids`, so "unknown"
and "nothing" are the same branch, and that branch is the one that sets every
active job back to PENDING and re-dispatches it. The one query guarding a
destructive operation was the one query that could fail open. Now it raises.

### 3.5 A permanently stranded job — FIXED

`services/job_queue.py`: the `if not self._processor: ... continue` sat
*before* the `try/finally` that calls `_clear_claim`. In Postgres-claims mode
the row kept `status='PENDING', claimed_at=<set>`, and `_claim_next_job_sync`
requires `claimed_at IS NULL` — so the job was permanently unclaimable and
silently never ran. The claim is now released on that path too.

### 3.6 Two dispatches could claim one worker's job slot — FIXED

`infrastructure/worker_registry.py:dispatch_job_to_worker` checked
`if worker.current_job` *after* `_get_live_worker` had released `_workers_lock`,
and assigned it *after* an `await send_json`. Two concurrent dispatches to the
same provider both passed the check and both dispatched; `unregister_worker`
could then only fail one future, and the other waited out its full timeout while
the worker ran a job the backend had no handle on. The check and the claim are
now one critical section (`_claim_worker_slot`), released on send failure.

### 3.7 `build_image_workflow(filename_prefix=...)` was accepted and discarded — FIXED

Proven at runtime: `build_image_workflow(prompt='x',
filename_prefix='MY_CUSTOM_PREFIX')` emitted `SaveImage` with
`filename_prefix: 'T2I_2026-09-27_14-37-10'`. There was no such field on
`GeneratorOptions`, so the real prefix always came from
`_generate_filename_prefix(mode)`.

Six call sites passed meaningful values that all vanished —
`"StoryAgenticGen"`, `"AgenticGen"`, `"ChatIllustrate"` — so image origin could
not be read off the filename. The **video** path has always honoured the same
parameter; the asymmetry is what let the image side rot.

`GeneratorOptions.filenamePrefix` added (default `None`, so `""` is still
distinguishable), both builders forward it, and the three call sites that
merely passed the default `"ComfyUI"` no longer pass it — so the default
behaviour (`T2I_<timestamp>`) is unchanged and only the deliberate values take
effect. Regression tests in `tests/test_workflow_filename_prefix.py`.

### 3.8 `JobService.get_job`'s recovery branch was a no-op — FIXED

```python
try:    self.session.get(Job, job_id)
except: raise NotFoundError("Job", job_id)
```

`Session.get` returns `None` for a missing row; it does not raise. The result
was discarded, the `NotFoundError` was unreachable, and a caller got back a
possibly-stale detached object believing it was fresh.

### 3.9 `_parse_civitai_datetime` — test fixed, not code

`tests/test_model_repo_v2.py::test_datetime_passthrough` asserted that a naive
`datetime` passes through unchanged. Commit `ddb0a875` deliberately made naive
values timezone-aware UTC, because `civitai_published_at` is a `UTCDateTime`
column and SQLModel's bind processor rejects naive values — which is what turned
"Add model" into a 500 for any CivitAI model with a version timestamp. The code
is right; the test was lying about the contract. Replaced with two tests that
assert the intended behaviour and name the 500 they prevent.

### 3.10 An endpoint that was 100% broken, with no test and no caller — FIXED

`api/routes/models/maintenance.py:499` did
`providers = await provider_service.get_enabled_providers()`. That method is a
plain `def` — it returns `self.repo.get_enabled()`. So every call raised
`TypeError: object list can't be used in 'await' expression`, and
`POST /api/v2/models/maintenance/backfill-statuses` did nothing but 500.

It survived because the route has **no frontend caller and no test**. Found by a
cross-module AST sweep for `await` of a known-synchronous function — a check
worth keeping, because the shape is invisible to both the linter and any
single-file reading. The sweep found one real instance across `api/`, `services/`,
`core/` and `infrastructure/`.

This is §7's lesson arriving early: an endpoint with no consumer and no test is
not free, it is invisible.

### 3.11 Three LLM engines report success for a download that never happens

`llm_worker/engines/{openai_compat,anthropic,google}/client.py` `download_model`
returns `ok(...)` — HTTP 200, `status: "success"` — for an operation that cannot
happen. The sibling engine that also cannot do it answers honestly with
`failed(..., code=501)`. A caller that trusts the success marks a model present
on a provider with no bytes. **Delegated to the provider fix wave.**

## 4. P1 — blocking work on the event loop

The pattern throughout: `get_session_context()` is an `@asynccontextmanager` that
yields a **synchronous** `Session`. It reads as async and gives no concurrency
benefit. FastAPI runs the sync `get_session` dependency in a threadpool, so the
~160 handlers that are already plain `def` are fine — but a handler declared
`async def` calls `session.exec(...)` straight on the loop.

`GET /api/ready` was the worst live case: it runs
`session.exec(text("SELECT 1"))` on the loop, so every orchestrator health probe
contended with real traffic.

### 4.1 A blocking full-table read on every outbound provider request — FIXED

`infrastructure/http_client.py:_refresh_known_provider_hosts` opened a fresh
`get_session_sync()` and ran `ProviderRepository.get_all()` — and
`_ProviderTokenClient.build_request` calls it, and `build_request` is
synchronous, so **there is no await point to offload at**. A blocking DB round
trip plus a full table scan, inline on the loop, for every provider call whose
30 s TTL was cold.

The 30 s cache made it 1-in-N rather than every request, which is why it survived
this long. The fix is architectural: the host set is now *published* by
`load_known_provider_hosts()` (called at startup, and after every provider
create/update/delete) and *read* by `published_known_provider_hosts()`, which
never touches the database. `None` (never resolved / last read failed) and
`frozenset()` (resolved, no providers) are now distinct types, because collapsing
them is what turned a transient DB error into unauthenticated requests to every
provider. Four regression tests in `tests/test_http_client.py`, including one
that fails if the token path opens a session at all.

### 4.2 ~31 `async def` handlers doing sync DB work — FIXED

Enumerated in `api/routes/world_vault/chats.py` (10), `prompts.py` (**12**, not
the 7 the sweep counted), `stories.py` (5), `world_vault/llm_config.py` (2),
`characters.py` (1), `locations.py` (1), `models/maintenance.py` (1),
`health.py` (1), plus `providers/crud.py` and two outside the listed files.
38 handlers in total.

Fixed by converting to plain `def` where there is no `await` — 18 of them,
including `GET /api/ready`, which was the worst live case — and by extracting a
module-level `def` behind `asyncio.to_thread` for the 20 that genuinely need to
stay `async`. Every session call was moved; a `Session` is created and used in
the same thread throughout.

**Three things this uncovered, which no route edit can close:**

1. **`JobService.create_job` was `async` but did its INSERTs inline** — FIXED. A
   route can only `await` a coroutine on the loop, so this was the largest
   remaining share and it was invisible from `api/`. It is now
   `await asyncio.to_thread(self._create_job_sync, ...)` *and* costs half the
   round trips it used to: the typed routing columns were set AFTER
   `repo.create` had already committed and refreshed, so every job carrying
   metadata — most of them — paid a second commit and a second refresh. Six round
   trips per submission, half redundant, on the loop. Now one INSERT, one commit,
   one refresh, in a worker thread. This is the hottest path in the application.
2. **`JobSubmissionService.create_and_enqueue_job`'s prologue** — FIXED.
   `resolve_default_provider` and `validate_workflow` are three or four
   synchronous queries run inline on the loop once per generate/illustrate/
   narrate request, while the requesting coroutine waited. Now one
   `to_thread`; the resolved provider id comes back out of the worker thread
   because it is reassigned and used after the `await`.
3. **Hidden lazy loads after commit.** `session.commit()` expires all instances,
   so reading `message.id` or `story.lorebook_ids` *after* an awaited
   `create_job` triggers a fresh SELECT on the loop. The handlers in scope were
   fixed to return ids from the thread and to commit through `to_thread`;
   instances of the same pattern remain in untouched `services/` paths.

**A caveat on the thread rule.** The obvious rule is "a Session belongs to one
thread". That is not this app's invariant. FastAPI builds the `get_session`
dependency in a *threadpool* thread even for `async def` routes, and the ~160
existing synchronous handlers already use that session from another thread, so
the real invariant is **no concurrent cross-thread use**. The request-scoped
session is therefore passed into `to_thread` rather than re-opened, matching
`files.py:_sync_file_to_providers` — re-opening would have bypassed the tests'
`api.deps.get_session` override and held two connections per request.

### 4.3 `ContainerManager.start_container` — FIXED

Every blocking Docker SDK call was inline in an `async def`: `images.get`, a
possibly multi-minute `images.build` with its log stream, `containers.get`,
`stop`, `remove`, `containers.run`. `_wait_for_health` one function below
already used `to_thread`, so the awareness existed and just stopped at the
boundary. Extracted `_start_container_sync` and awaited it. Reached from
`provider_lifecycle_service.start_container` and from
`load_balancer._warm_provider_in_background`, i.e. while other requests are being
served.

Reached from the event loop while `_wait_for_health` used `to_thread` is exactly
the kind of near-miss that survives review.

The extracted version also checks `HOST_BACKEND_PATH` **before** stopping the
existing container, so a misconfigured host no longer stops a running provider
and then fails to start it again.

`env_file` was a parameter that no caller passed and the code never read.
Removed.

### 4.4 Embedding inference on the loop — FIXED

`_finalize_llm_job` called `create_memories_from_extraction` synchronously from
an `async def`; its body ran `generate_embedding()` once per memory, serially,
each a full sentence-transformers forward pass. Now `asyncio.to_thread`d, and
the loop is one batched `generate_embeddings()` call with a per-item fallback —
the same shape `rag_pipeline` already uses — so one un-embeddable memory does not
cost the other four their vectors.

### 4.5 Blocking filesystem work in the paid-reply consumer — FIXED

`world_integration_service._handle_avatar_animate` did `os.path.isabs`,
`os.path.exists`, `os.makedirs` and `shutil.copy2` (a multi-megabyte video, on a
possibly cold mount) inline in an `async def`. It is reached from the single
`JOB_COMPLETED` consumer whose own docstring says it must never head-of-line
block, because an evicted completed job is a paid generation nothing can
reconstruct. Extracted `_install_avatar` and offloaded it.

`result_paths` — read there and written nowhere in the repository — was removed;
that branch could only ever yield `None`, and would have raised `IndexError` into
the blanket handler if ever present-but-empty.

### 4.6 `VACUUM` on the loop — FIXED

`infrastructure/database.vacuum_database` ran `VACUUM (ANALYZE)` inline from a
daily APScheduler job on an `AsyncIOScheduler`, so the whole application stalled
behind it. Split into `_vacuum_sync` and awaited via `to_thread`.

### 4.7 Four more, all FIXED

- **`services/agent_simulation.py:78-82`** — an unbounded full-`Job` scan inside
  a per-chat loop, materialising `workflow` + `metadata_` + `outputs` jsonb to
  read one enum field and test it in Python. Now
  `select(exists(select(Job.id).where(...)))`, answered by the database in one
  round trip per chat instead of one that grows with the job table. The status
  set moved to a named `IN_FLIGHT_JOB_STATUSES` constant, because its old home
  was inside an `any()` and therefore easy to forget to extend.
- **`services/world_integration_service.py:777-786`** — every `Message` row for
  the affected chats, no `LIMIT`, no column narrowing, `content` TEXT included,
  loaded to test one key of `message_metadata` against a set of at most `limit`
  job ids. A 5 000-message chat put 5 000 full rows in memory on every
  reconciliation tick. The flat `source_job_id` is now compared in SQL; only the
  nested `alternates` list, which no column comparison can reach, still selects
  the single jsonb column — with the chat and job filters applied, so it does not
  walk the chat either.
- **`services/context_builder.py:442-446`** — an unbounded lorebook read in the
  *fallback* path, i.e. the one with less bounding than the two happy paths
  around it, which use `scan_cap` and `limit * 2`. A SillyTavern world book of a
  few thousand entries went into the system prompt whole. Now bounded by both a
  per-lorebook scan cap and a total entry cap.
- **`services/provider_status_service.py:601`** — `build_provider_status_cards`
  was still the serial `for` loop that `build_provider_records` carries a
  sixteen-line docstring about having replaced: the sum of every provider's
  latency where the slowest would do. It is live at
  `api/routes/providers/lifecycle.py:188`, so the page was still paying the
  serial sum. Now gathered, with the same per-provider exception isolation.

### 4.8 The WebSocket path, which is the worst place for this — FIXED

`api/routes/worker_ws.py:_worker_owns_job` is called before **every** inbound
frame, including every progress tick of a live generation, and it did
`session.get(Job, job_id)` on the event loop — loading the whole `Job`, `workflow`
and `metadata_` jsonb included, to compare one string field. A worker streaming
progress for a 60-second image was doing a full-row SELECT per tick on the loop
that every other request needed.

Now a one-column `select(Job.provider_id)`, issued through `to_thread`.
`_fetch_pending_models` (a multi-table read on every worker handshake) likewise.

`websocket.py:stop_broadcasting`'s cancel path was dead code — `self._broadcast_task`
was assigned only in `__init__` as `None` and never set, so the `if` guard was
permanently false — and the broadcast loop checks `_running` only *after* an
event, so on a quiet bus a bare flag flip could never stop it. The task is now
recorded, and `EventBus.subscribe_multiple` has a `finally` that cancels its
pending queue reads and unsubscribes, so cancellation is the clean exit.

## 6. P1 — endpoints that answered 200 on failure

`api/routes/files.py` had two handlers that caught `Exception` and returned
**HTTP 200 with `{"files": [], "total": 0}`** — `_scan_local_model_directory` on
any failure, and the `output`/`output/…` branch of the file lister. That body is
indistinguishable from "you have no models": a driver failure, a corrupt index
and a bug all render as an empty gallery with no error anywhere, and `total: 0`
is a lie (the count is unknown, not zero).

Replaced with a new `core/exceptions.ServiceUnavailableError` (503) and its own
handler. It is a separate class from `ConfigurationError` because a retry is the
right response to one and the wrong response to the other, and separate from an
opaque 500 because the client has to be able to tell "try again" from "you are
holding it wrong".

## 7. P1 — detached systems: backend features with no UI


This is the "missing integration between components" category, and it is the
largest one by surface area. The app exposes **247 OpenAPI paths**. 107 of them
have no `api.get`/`post`/… call site in `frontend_v2`, and after
cross-referencing the providers, services and infrastructure, **42 have no
caller anywhere in the stack**.

The direction matters and is good news: **the frontend calls nothing the
backend does not have.** All 234 frontend call sites resolve to a live route. So
this is unfinished work, not drift — the backend got ahead of the UI.

I re-verified the headline claims myself rather than repeating them, and two of
the sweep's groupings were over-broad:

- The **character expression** system is **wired** — `hooks/useExpressions.js`
  calls `GET /api/v2/characters/{id}/expressions` and `useUpdateExpressions`
  patches the character. Not a finding.
- The **model** tag endpoints are **wired** — `api/models.js:38,50` reach
  `/api/v2/models/maintenance/{id}/tags`. The sweep conflated them with the
  per-asset tag endpoints, which are genuinely unwired.

## 8. P1 — a paid LLM job on every single chat reply

`services/memory_extraction.should_extract_memories` returned
`len(user_msgs) >= 2` over the **newest 20 messages**. Once a chat passed 20
messages, any normal user/character alternation puts ≥2 user messages in that
window, so the test was true **forever**. `job_processing` calls it
unconditionally after every `chat_reply`, with no throttle and no
`ai.memoryExtractionEnabled` gate.

The gate was supposed to be a throttle and was a constant.

Now a turn counts as *newly complete* only when the character has already
answered it. A conversation alternating user/character therefore yields two
answered user messages before the third, which is the trigger itself: the gate
is closed until the user sends a fourth. The two duplicate queries
(`should_extract_memories` and `build_extraction_messages` each ran the same
`select(...).limit(20)`) are now one shared fetch.

## 9. P2 — correctness and determinism

**8.1 Non-deterministic LLM provider selection — FIXED.**
`services/llm_config.resolve_default_provider` did
`select(Provider).where(llm, enabled).all()` with **no `ORDER BY`**, then
`or providers[0]`. Postgres makes no ordering promise, so the fallback was
whatever the plan happened to return: the same config could resolve to different
providers on two consecutive chat messages, with no way for a caller to tell it
was not a stable choice. Now `.order_by(Provider.priority, Provider.id)` — the
tie-break is on a unique column, so the fallback is deterministic.

**8.2 `reset_config` had the defect `update_config` was just fixed for — FIXED.**
One function below the locked, `mkstemp`+`fsync`+`os.replace` writer,
`reset_config` did an unlocked write to the module global and a
truncate-then-write `open(..., 'w')`. `settings.py` reaches both through
`asyncio.to_thread` from two routes, so they really do race. Both now share one
locked atomic writer. (`DEFAULT_CONFIG.copy()` was also a shallow copy of a
nested dict; it is a deep copy now.)

**8.3 A test that was passing only because of the P0 — FIXED.**
`tests/test_event_bus_loss_prevention.py` asserted `"[error" in logged`, which
is structlog's `ConsoleRenderer` bracket format. With the logging bug fixed the
app renders `ERROR` in a fixed-width column, so the assertion failed. It now
checks the level token, and additionally asserts the event is not logged at
`WARNING` — which is the property the test was actually written to protect
(a content-bearing drop is an ERROR, not a counter tick).

**8.4 `request_dedup` shield undone by its own `finally` — OPEN.**
`infrastructure/request_dedup.py:97-106`: the comment says "shield shared work
from caller cancellation so one waiter cannot cancel the underlying request",
but the `finally` runs on the creator's own cancellation and pops
`_in_flight[key]`, de-registering a task that is still running. The next
identical request then starts a second concurrent task.

**8.5 Four env-var parsers with different failure behaviour — OPEN.**
`infrastructure/database.py:15` and `services/load_balancer.py:24,32` take an env
*name* and log a warning when it fails to parse.
`infrastructure/config_helpers.py:27,55` take a raw *value* and fall back
**silently**. A typo in `COMFY_LB_CONTAINER_PROBE_TIMEOUT_SECONDS` or
`COMFY_DB_POOL_SIZE` is invisible; the same class of typo in `COMFY_PREVIEW_*`
is logged.

**8.6 `llm_config._read_cache` two-key update with no lock — OPEN.**
`_read_cache["mtime"] = mtime` then `_read_cache["data"] = data` are two writes
into a module global read from the event loop. A reader landing between them
sees the new mtime with the old data, caches it as fresh, and serves stale data
until the file changes again.

**8.7 `_runtime_states` mutated without `_load_state_lock` — OPEN.**
`services/load_balancer.py:145-151`. The lock exists at `:146` and is used only
for `load_state_from_db`. Keyed by `state_id` and only two values occur in
practice, so growth is bounded — but the lock is right there.

## 13. API layer: not in the fix waves, catalogued

**Two envelopes for one class of failure — FIXED for the two worst cases, the

middleware only wraps HTTP so it is not logged here — but any reverse proxy's
access log captures it.

**`POST /api/v2/models/maintenance/backfill-statuses` fans out to every provider
× every model directory in one held request** (`maintenance.py:443-505`): it
loads every model with every version into memory, then dispatches per
`(provider, directory)` pair — 12 directories × N providers, each an HTTP call to
a remote container. Its sibling `resync-all` correctly uses `BackgroundTasks`.
Two instances of `resync-all` can also run concurrently with no dedup, even
though `api/lifecycle.py:290-295` already schedules the same function every 24 h.

**`DELETE /api/jobs` truncates the job table** (`jobs.py:728-731`). It is guarded
(400 while jobs are active), which is good, but the guard is a TOCTOU check and
a stray `DELETE` from a link prefetcher wipes job history. Wants a `?confirm`.

**Seven "list" endpoints use five mutually incompatible response contracts** —
`{jobs, next_cursor}` (no `total`), `{jobs, total, limit, offset, summary}`,
`{jobs}` (no total, no limit echo, **no truncation signal at all**), `{items,
has_more, next_cursor}`, `{sessions, total, limit, offset}`, a bare array with
`X-Total-Count` headers, and a bare array with **no headers** despite
`_set_pagination_headers` existing 500 lines away in the same feature. The
header-based one exists only because the body shape was frozen by
`ChatTimeline.jsx` — a migration constraint to note in a doc, not a pattern to
extend.

**Eleven collection endpoints have no pagination parameter at all** and load the
full table — `characters`, `lorebooks`, `voices`, `locations` (×2, one of which
is a *search*), `scenarios`, `campaigns`, `personas`, `world_hub/entities`,
`world_hub/search`, `providers/`. The two search routes are the worst: an empty
or single-character query returns the entire table.

**Over-fetching:** `GET /api/v2/chats/{id}/messages` serialises
`Message.message_metadata`, which holds the `alternates` list of every swipe, so
a legal `?limit=1000` returns 1000 messages each carrying all of its variants.
And every item in `GET /api/v2/assets` embeds the complete `metadata_` jsonb
blob — the promoted columns that exist for exactly this purpose
(`core/entities.py:282-300`) are not used.

**`core/entities.py:301` — `Asset.metadata_` had no `alias="metadata"`** —
FIXED. Unlike `Job.metadata_` at line 71 in the same file. Latent because no
route returns a bare `Asset` (`files.py` hand-builds the dict), so it was
verified by execution rather than by a failing request: under FastAPI's
`model_dump(by_alias=True)`, `Asset` emitted `metadata_` and `Job` emitted
`metadata`. Any future `response_model=Asset` would have leaked the python-side
name to the client, and two entities in one file disagreed on the documented wire
contract. Both now emit `metadata`.

**Checked and healthy** (so a reviewer does not re-flag them): all 327
`(method, path)` pairs are unique with zero shadowing; every router is included
exactly once; `api/deps.py` is a clean boundary with no route importing
`Session(engine)` or a service singleton; 59 uses of the `ComfyError` hierarchy;
`files.py` and `statistics.py` are the reference implementations for the
off-thread pattern; `batch_delete_endpoint` validates against an allowlist and

they should be; `job_repo.get_queue_items` is now bounded (see §5).

## 14. Providers and infrastructure

**Everything in the P0/P1 lists below is fixed**; the rest is catalogued. The
wave closed all 21 items, added 128 tests, gave `provider_containers` its first
`ruff.toml`, and — the part that matters most for the future — closed the CI gaps
so a broken `Dockerfile`, a compose cycle, or a change to `remote_agent/server.py`
cannot ship green again.

**P0:** see section 1.

**P1, unreachable code that the UI reports as data:**
`image_worker/engines/modal/modal_app.py` returns early on
`if not is_model_file(name)` *before* its `.downloading` branch, and
`is_model_file('x.safetensors.resume.abc.downloading')` is `False` — so the
partial-download detection and deletion can never run, and `total_partial` is
permanently 0 for the Modal engine while the remote agent reports it correctly.
The only test covering it is a **source-grep** for the string `"is_model_file"`,
which is why it survived.

`llm_worker/engines/modal/client.py:200-212` — `setup_models` awaits

### 14.1 Providers and infrastructure checked and healthy

Verified negatives, recorded so a later pass does not re-litigate them or, worse,
"fix" working security code.

- **Compose validity.** `docker compose -f docker-compose.yml
  -f docker-compose.dev.yml --profile providers config --quiet` exits 0.
  `depends_on` is acyclic (`db` → `backend_v2` → providers; `frontend_v2` →
  `backend_v2`), every `depends_on` uses `condition: service_healthy` against a
  service that *has* a healthcheck, and no provider is a `depends_on` target — so
  the `/live`-vs-`/health` cascade the tests describe cannot recur.
- **Container naming.** All five live providers are `tnhcomfy-{PROVIDER_ID}`
  verbatim, including the deliberate `tnhcomfy-direct_url` underscore, which
  matches `provider_container_name()`'s non-normalising behaviour.
- **Auth posture.** `_require_worker_token` fails **closed**, uses
  `hmac.compare_digest`, and every state-touching route carries
  `dependencies=protected` — all 24 route registrations checked. Only `/health`
  and `/live` are open, both documented as required for the healthcheck. The
  `/provider-stats` amplification (16 authenticated round trips) is gated.
- **No `shell=True`, no `os.system`, no equivalent** anywhere in production code.
  `provider_core/deploy.py:105` uses `asyncio.create_subprocess_exec(*cmd)` with
  an argv list built from literals, so the `/deploy` route cannot inject a
  command.
- **No world-writable paths and no `chmod 777`** anywhere in
  `provider_containers/` or `remote_agent/`. `exclusive_path_lock` creates its
  lock file `0o644`.
- **Path traversal.** Every file-serving path goes through `get_safe_path`
  (`os.path.realpath` + `os.path.commonpath`) — verified at all nine call sites
  including both `modal_app.py` `FileStorage` classes, and the `ValueError` is
  handled as "Path traversal blocked" at the two places it can fire. The one gap
  is the unencoded URL interpolation at `remote_comfy/client.py:320`, which is a
  *transport* bug, not a traversal bug — the agent still applies `_data_path`.
- **`create_task` retention.** All six fire-and-forget `create_task` calls in the
  inference generators hold the task in a local and cancel it in a `finally`. The
  four long-lived ones are the lifespan loops, whose teardown does own the list.
  `spawn_background_task` is a correct, bounded, documented helper.
- **Quadratic string concatenation is gone.** `provider_core/deploy.py:28-55`
  uses a `deque` with a byte budget and joins once per read; the old
  `out_str += chunk` is documented as removed.
- **Streaming, not buffering, for large files.** `relay_bytes` enforces
  `get_file_size_cap()` per chunk; Beam's `get_file` has a declared
  `Content-Length` pre-check *and* a second check on the base64 path; the agent
  and Beam use `FileResponse`; Modal uses ranged reads; `downloads.py` streams in
  8 MB chunks and never holds the file.
- **Timeouts.** Every `requests.*` call in production code has an explicit
  `timeout=`, except the two flagged in §14. Every `httpx` call goes through
  `get_http_client`, whose `httpx.Timeout` defaults to 30 s, and the 23 engine
  call sites needing longer pass it explicitly. `asyncio.timeout` wraps all five
  `inference()` implementations.
- **Retry/backoff is real.** `downloads.py` has 3 attempts with exponential
  backoff capped at 30 s, a `TRANSIENT_STATUSES` list for retryable HTTP, a
  `PERMANENT_ERRNOS` list so `ENOSPC` is not retried, and the
  identity/ETag/Content-Range triple-check that makes resume safe rather than
  blindly appending. `SharedHttpClient` retries GET on timeout/connect/read/5xx.
  `push_reconciliation_event` retries 3× with backoff.
  `batch_update_file_status_v2` is correctly bounded at 4 concurrent.
- **Engine registration is complete.** Every `ENGINE` the backend can emit is
  wired, and there is no registered-but-unwired engine.
- **Env-file wiring for the documented `up` command.** All five providers'
  `env_file:` targets exist, and both shared secrets are injected into every
  provider from the root `.env` via `environment:` rather than left to
  `env_file:` — which is the failure the compose comment describes.
  `preflight.sh` strips YAML comments before extracting the required list, so the
  commented-out `provider-remote-comfy` block does not produce a false failure,
  and it exits non-zero on a real one.
- **`.dockerignore` for the provider build context** correctly excludes
  `__pycache__`, `*.pyc`, `tests/`, `.env*`, `venv/` while keeping
  `!.env.example`, so the 15 GB local venv and the secrets stay out of the image.
- **`get_safe_path` and `is_model_file` are genuinely single sources of truth**
  where the comments claim: `is_transient_artifact` is used by both
  `modal_app.py`s, `beam_app.py`, the agent and `utils.py`, with no per-engine
  suffix list left behind.
- **`translate_task_events` cannot double-report.** `_TASK_EVENT_KINDS` is in
  sync with the `TaskEvent.event` Literal including `cached_nodes`,
  `{"status":"queued"}` is filtered to `None`, and a canonical `TaskEvent` dict is
  re-emitted rather than misread as a legacy update.

## 15. Open items, ranked

Ordered by cost of leaving them.

**Should be done next** — items 1-4 are the ones that lose work or money.

1. **`api/main.py:160,163` — request bodies in the log and in the response.**
   A `RequestValidationError` logs `f"... - Body: {exc.body}"` at **error**
   severity, so every malformed `POST /api/jobs` writes the whole ComfyUI
   workflow — including prompt text — to the log; and the same body is echoed
   back to the client in the response. It also uses a second error envelope
   (`{detail, body}`) where every other handler returns `{error, code}`.
   *The one item here with a privacy dimension, and the smallest.*
2. `infrastructure/request_dedup.py:95-108` — the shield is undone by its own
   `finally`. The comment promises one waiter's cancellation cannot cancel the
   shared work; but the `finally` runs on the *creator's* cancellation and pops
   `_in_flight[key]`, de-registering a task that is still running, so the next
   identical request starts a second one. Silent, and it only shows under
   concurrency.
3. `worker_ws.py:244` — a raw exception string is written into the user-visible
   `jobs.error` column, which `GET /api/jobs/{id}` returns. A SQLAlchemy or
   httpx traceback with a connection URL reaches the browser. The full string is
   already logged two lines above.
4. The eleven unpaginated collection endpoints and the two search endpoints that
   return a whole table on a one-character query (§13).
5. `services/asset_metadata_index.normalise_model_reference(kind=...)` — both
   callers pass `kind` and both take the identical path, so the branch its
   docstring describes does not exist. Implement it or drop the parameter.
6. `_runtime_states` / `llm_config._read_cache` — both mutate a module global
   without the lock that already exists a few lines away.
7. `infrastructure/config_helpers` — unify the four env parsers so a typo is
   visible in the same class of typo.
8. `api/routes/models/maintenance.py:443` — the backfill fan-out belongs behind
   `BackgroundTasks` like its sibling already is.
9. **A backend boot smoke test.** Nothing exercises the real startup path — the
   lifespan, the scheduler registrations, the event bus, the background tasks.
   This is the exact gap that let every provider container crash-loop on a
   bad argument while 596 tests passed: they covered the parts and never the
   wiring. See "Done since" for the two times that has already cost us.
