# Codebase Audit — 2026-09-26

Audit of `master` @ `ae3a010` (clean worktree). Three pillars: `backend_v2` (267 py files),
`frontend_v2` (360 js/jsx files), `provider_containers` + docker + scripts.

Method: three parallel deep reads (backend / frontend / providers+infra+cross-cutting), then
manual verification of every P0 claim against source before this document was written.
Runtime check: the stack was already up and healthy (`db`, `backend_v2`, `frontend_v2`, and five
provider containers), so "the website is reachable" is a known-good baseline to preserve.

## Summary

| Severity | Count | Theme |
|---|---|---|
| P0 | 15 | Crash paths, auth that fails open, availability of the site itself |
| P1 | ~50 | Broken features, detached code, query patterns that scan whole tables |
| P2 | ~55 | Duplication, dead code, unwired config, contract drift between provider engines |
| P3 | ~30 | Quality-of-life, hygiene, docs |

The dominant theme is **not** missing features. It is **false signals**: code paths that report
success while doing nothing, a modal that can never open, a chat illustration endpoint that can
never succeed, a provider that authenticates only when a token happens to be set. Several of these
are actively misleading during debugging, which is worse than an obvious break.

### Corrections made during verification

Six findings did not survive verification. They are listed here rather than
quietly dropped, because "the audit said X" is more useful than a silently
shorter list:

- **P0-1 (character delete cascade) is latent, not active.** The route test passes on the
  unfixed code because `scrub_entity_references` nulls `chat.character_id` first and the
  autoflush de-associates the children before the parent delete. Empirically, with the
  relationship loaded and the scrub skipped, the old cascade leaves `chats=0 messages=0`;
  with `save-update, merge` it leaves `chats=1 messages=1`. Still worth fixing — the
  safety depended entirely on flush ordering — but it is not destroying anyone's chats.
- **P0-2 (voice model FK) is not a live crash.** With `PRAGMA foreign_keys=ON` the delete
  succeeds, because SQLAlchemy nulls the FK during flush. The explicit cleanup is still
  correct; the crash claim was wrong.
- **P0-12 (`HOST_BACKEND_PATH` unset) is wrong.** It is set in `.env` and passed to the
  backend. The real defect was narrower: it is documented nowhere, so a clean checkout has
  no way to know it is required.
- **P0-15 (`scripts/migrate_sqlite_to_pg.py` broken import) is wrong.** The module lives at
  `backend_v2/scripts/migrate_sqlite_to_postgres.py` and resolves via implicit namespace
  packages. `python3 scripts/migrate_sqlite_to_pg.py --help` works.
- **`Job.queue_id` does not exist.** No column, index, or migration reference anywhere.
- **`backend_v2/memory_snapshot_helper/` is not dead code.** `tests/test_memory_snapshot.py`
  imports and exercises it; it is a ComfyUI prestartup patch mounted into provider
  containers.
- **`useDeleteMemory`'s invalidation is correct.** The call site passes `characterId`, and
  `onSuccess(_, variables)` receives the full variables object even though `mutationFn`
  destructures only `{ id }`.
- **`.kilo/plans/1787583794283-tnhfantasy-hardening-plan.md` does exist** (15 KB, committed in
  `769b180`). An earlier draft asserted it was missing. `PLAN.md`, `ROADMAP.md` and
  `DEMO_GAPS_PLAN.md` genuinely supersede one another; the complaint is document sprawl, not a
  dangling reference.

This exposed a third, larger problem, now recorded as its own finding below: **the test suite
ran with `PRAGMA foreign_keys=OFF`**, so every FK violation that Postgres rejects at
runtime was invisible to CI. Enabling it immediately surfaced 15 tests that were seeding
rows like `chat_id='chat-x'` and `character_id='char-1'` against parent rows that did not
exist — states the production database cannot hold.

## P0 — Must fix

### Data loss

**P0-1. `Character.chats` carries a cascade that can destroy every chat and message.**
`core/entities.py:825-828` declared `cascade="all, delete-orphan"`, and `Chat.messages`
(`entities.py:885-888`) cascades again. Verified empirically: with the relationship loaded and a
chat + message present, `session.delete(character)` leaves `chats=0 messages=0`; with
`save-update, merge` it leaves `chats=1 messages=1`.

In the *current* `delete_character` ordering this does not fire, because
`scrub_entity_references` nulls `chat.character_id` first and the autoflush de-associates the
children before the parent delete is processed. So this is a **latent** hazard, not observed data
loss: the scrub happens to disarm the cascade, and the safety depends entirely on flush ordering —
the same ordering that `delete_chat` (`chats.py:490-499`) was already hardened against, with a
comment saying so. Any future path that reaches `session.delete(character)` with the relationship
loaded and the scrub absent or reordered silently wipes chat history. Fixed by removing
`delete-orphan` from that one relationship, so the outcome no longer depends on flush order.
`Character.memories` and `Character.collections` keep `delete-orphan` deliberately — there is an
existing regression test for memories.

**P0-2. `VoiceModel.character_id` had no explicit cleanup on character delete.** `entities.py:759`
is a hard FK with no `ondelete`, and `Character.voice_models` (`entities.py:829-832`) declares no
delete rule, so the safety came entirely from SQLAlchemy nulling the FK during flush. Verified: with
`PRAGMA foreign_keys=ON` the delete succeeds. **Not a live crash** — but `scrub_entity_references`
(`services/reference_cleanup.py:47-81`) is the function whose documented job is exactly this, and it
had no branch for it. Now handled explicitly so a raw/bulk delete path cannot inherit the ORM's
flush-ordering luck.

**P0-13. Migration `049` writes a column that migration `055` adds.**
`_migration_049_seed_starter_pack` (`infrastructure/migrations/steps.py:1549`, INSERT at `:1648`)
includes `sort_order`, which is only created by `_migration_055_add_character_sort_order`
(`:2171-2179`, registered at `:1579`). On any Postgres database that has not yet run 055, step 049
fails with `column "sort_order" does not exist` and **startup aborts**. Fresh databases survive only
because `create_all()` happens to run first.

### Wrong results / crashes

**P0-3. `POST /api/v2/chats/{id}/illustrate` without a prompt can never succeed.**
`api/routes/world_vault/chats.py:1521` filters `Message.role.in_(["char", "user"])`. On Postgres,
`messages.role` is a native enum stored under the *member names* (`CHAR`/`USER`) — the migration
file documents this at `steps.py:1014-1015`. The lowercase predicate matches zero rows, `last_char`
is always `None`, and the endpoint always raises `"No prompt and no character reply to illustrate"`.

**P0-4. Agentic `narrate_scene` silently drops the narrator message.**
`services/orchestrator_service.py:452` imports `Message`, `MessageRole`, `datetime`, `timezone`
**inside** the `elif chat_id:` branch. Python binds them as function-locals at compile time, so the
later use at `:594-602` raises `UnboundLocalError` whenever `source_context` is truthy — which is
precisely the chained/agentic case, since `process_tool_calls_and_chain` writes
`original_messages` into every follow-up job. The `except Exception` at `:606` swallows it into a
`logger.warning`. Narration is never persisted and nothing surfaces the failure.

**P0-5. `GET /api/files/proxy/{provider_id}/{path}` is an unvalidated path traversal.**
`api/routes/files.py:1660-1696` takes `path` raw from the URL into `HttpFileProxy.get_file`, which
only `quote(path, safe="/")`s it (`infrastructure/providers/provider_registry.py:33-34`). `.` is a
unreserved URI character, so `../` survives verbatim. Every other file endpoint in the module goes
through `get_safe_path()`. The endpoint has no frontend consumer, so it is both dead and unsafe.

**P0-6. Worker-supplied `progress` can violate the `jobs.progress` CHECK constraint and kill the socket.**
`api/routes/worker_ws.py:159-176` normalises `0..1 → 0..100` on the canonical `TaskEvent` branch but
writes the worker's raw value on the legacy branch. Migration `047`
(`steps.py:1170-1172`) added `CHECK (progress BETWEEN 0 AND 100)`, so a worker emitting a `0..1`
fraction — exactly the case that branch exists to support — raises `IntegrityError` inside the
session context, propagates to the outer handler at `:278`, and **closes the whole WebSocket**,
leaving the job non-terminal.

**P0-7. Cancelled jobs get re-dispatched to a second provider after failover.**
`services/job_runner.py:297` resets `retry_count = 0` on provider failover, so the
`if retry_count > 0: job = await job_service.get_job(job_id)` refresh at `:308` is skipped and
`latest_status` is a stale in-memory value. A user who cancels mid-flight on provider A, followed by
an A-side failure, still gets the job dispatched to provider B — real GPU spend, and the FSM then
silently drops the `GENERATING` transition because `CANCELLED` has an empty transition set
(`services/job_service.py:75`).

### Auth that fails open

**P0-8. Every provider endpoint is unauthenticated whenever `PROVIDER_WORKER_TOKEN` is empty — and
empty is the shipped default.** `provider_containers/provider_core/router.py:40-43`:
`if expected and request.headers.get(...) != expected`. `.env.example:10` ships it empty and
`docker-compose.yml` passes `${PROVIDER_WORKER_TOKEN:-}`. So `/inference`, `/download-model`,
`/delete-model`, `/delete-file`, `/get-file/{path}`, `/upload-file`, `POST /config` and **`/deploy`**
are open by default. `/deploy` is the worst case: `image_worker/engines/modal/client.py:201` shells
out to `["modal", "deploy", ...]`.

**P0-9. `provider-direct-url` has no `environment:` block at all** — the only provider service
without one (`docker-compose.yml:274-302`). It receives neither `PROVIDER_WORKER_TOKEN` nor
`COMFY_DISCOVERY_TOKEN`, and `.env.direct-url` supplies neither.

**P0-10. Backend-autostarted provider containers get no token and publish a random host port.**
`services/container_manager.py:202-209, 246` builds the environment without
`PROVIDER_WORKER_TOKEN`, and `services/provider_env_builder.py:26-68` does not add it either. The
port is published on `0.0.0.0`.

**P0-11. Discovery self-registration is unauthenticated by default.**
`api/routes/discovery.py:39-41` has the same `if discovery_token and ...` shape. With the default,
any container on the `tnhfantasy` bridge can register an arbitrary `provider_id` pointing at any
RFC1918 address — an unauthenticated job-hijack and internal-network-fetch primitive.
`COMFY_DISCOVERY_ALLOW_NEW_PROVIDERS=0` does not help: `provider_service.py:356` only disables the
record, it still creates it and stores its `discovery_url`.

**P0-17. `_worker_owns_job` treats `provider_id IS NULL` as claimable by anyone.**
`api/routes/worker_ws.py:54-55` returns `job.provider_id in {None, provider_id}`, and that check
gates `job_started`/`job_progress`/`job_completed`/`job_failed`. Any connected worker can report
success for a job it was never assigned.

### Non-functional features

**P0-12. `HOST_BACKEND_PATH` is set nowhere, so `start_container` always raises.**
`services/container_manager.py:226-233` raises `ValueError` when it is empty; the only other
references are `services/provider_deploy_orchestrator.py:158` and a docstring. It appears in no
compose file and no `.env.example*`. Same for `HOST_PROVIDER_CONTAINERS_PATH`
(`provider_deploy_orchestrator.py:170`). Provider autostart and the deploy path are dead.

**P0-15. `scripts/migrate_sqlite_to_pg.py` imports a module that does not exist.**
Line 6 is `from scripts.migrate_sqlite_to_postgres import main`; `scripts/` contains only
`verify.py`, `fix_filenames.py`, `migrate_sqlite_to_pg.py`, `requirements.txt` — and no
`__init__.py`. `ModuleNotFoundError` on the first line of real work.

**P0-16. `remote_agent/docker-compose.yml:16` ships an unedited path placeholder as a bind-mount
source** — `/path/to/your/ComfyUI/models`. Compose will create that directory on the host. The same
file also declares `env_file: .env.agent` while only `.env.agent.example` exists, so compose aborts
first.

### Availability of the site

**P0-14. `frontend_v2/nginx.conf` caches the backend IP forever.**
`resolver 127.0.0.11` is declared but `proxy_pass http://backend_v2:8002` uses a literal hostname
with no variable, so nginx resolves once at startup and never re-resolves. `docker-compose.yml:57`
sets `restart: unless-stopped`, so a backend crash gets a new IP and the frontend returns 502 for
`/api/` and `/socket.io/` until the frontend itself restarts. The `resolver` line and `valid=10s` are
dead config. This is the single most likely cause of "the site went down and I did nothing wrong".

## P1 — Broken features, detached code, table scans

### Backend

- **Blocking sync DB I/O in `async def` handlers.** `api/routes/files.py:613-709, 712-724, 727, 749`
  — `list_assets`, `serve_asset_file`, `serve_asset_thumb`, `move_asset` open a sync `Session`
  inline with no `asyncio.to_thread`, contradicting the module's own contract note at `:545-547`.
  `files.py:1815` already does it correctly.
- **`/api/statistics/detailed` `steps_cfg` correlation never aggregates and is O(n²).**
  `api/routes/statistics.py:510-522` appends with raw `meta["steps"]` (int) but compares against
  `item["steps"]` (str, normalised at `:421`). The comparison is never true, so every image gets its
  own entry with count 1, and the linear scan runs per asset. At the 13k assets this repo documents
  that is ~170M iterations per request.
- **`search_lorebook_entries` loads every entry row with no LIMIT.**
  `services/rag_pipeline.py:156-162` materialises all `LorebookEntry` rows then applies
  `scan_cap` in Python. Runs on every chat message, suggest, impersonate and story continue.
- **`metadata_->>'chat_id'` filters cannot use the GIN index.**
  `api/routes/world_vault/chats.py:765, 1120` and `services/agent_simulation.py:81`. The index from
  migration 024 supports `?` containment (which `job_repo.get_metadata_key_counts` uses correctly),
  not `->>` equality, and no btree expression index exists. `.as_string()` is also deprecated.
- **`GET /api/jobs` has no `limit` cap and returns each job's full `metadata_`.**
  `api/routes/jobs.py:156-161` + `services/job_service.py:707`. For agentic LLM jobs
  `metadata_["original_messages"]` is the whole conversation. Sibling endpoints cap at 100/1000.
- **Agentic context is stored twice per job and grows with hop depth.**
  `services/orchestrator_service.py:1043-1048` and `services/llm_workflow.py:43-47` put the same
  list in `workflow["messages"]` and `extra_metadata["original_messages"]`, each hop's context being
  the previous hop's plus the new turns. Cumulative row size is O(depth × conversation).
- **`/api/settings/schema` advertises sections that cannot be written.**
  `api/routes/settings.py:62-292` documents nine; `SettingsUpdate` (`:300-306`) accepts five;
  `PERSISTENT_KEYS` (`config.py:90-98`) persists six. The `websocket` section does not exist in
  `DEFAULT_CONFIG` at all. Every write to the others returns `Unknown configuration section`.
- **`reorder_chapters` accepts a partial id list and can violate a unique constraint.**
  `api/routes/world_vault/stories.py:704-717` renumbers only the supplied ids, so omitted chapters
  keep their numbers and `UniqueConstraint("story_id", "chapter_number")` (`entities.py:1071-1087`)
  can fail → 500. `reorder_characters` validates membership; this one does not.
- **Story continuation sends the entire chapter as one unbounded message.**
  `api/routes/world_vault/stories.py:858-868`. `prune_context` cannot help — its loop
  (`context_builder.py:208`) stops at 2 messages. `illustrate_chapter` at `:1438` correctly slices
  `[-3000:]`.
- **Webtoon export builds an unbounded-height bitmap.** `stories.py:466-480` sums every line and
  image height with no cap before `Image.new`. Reachable unauthenticated through
  `GET /api/v2/stories/published/{token}/export?format=webtoon`.
- **Unauthenticated published endpoints do unbounded CPU work.** `stories.py:617, 667-678`. The app
  has no auth at all (verified: no auth `Depends` anywhere), so any leaked share link is a
  resource-exhaustion vector.
- **`worker_ws` `try/finally` with no `except` falsely resolves the job as successful.**
  `api/routes/worker_ws.py:215-237` — if `finalize_successful_job` raises, the `finally` still
  signals success, then the exception closes the socket. Job left non-terminal.
- **Migration `063` hard-adds an FK the ORM does not declare, conflicting with provider pruning.**
  `steps.py:2422` adds `fk_jobs_provider` on `jobs.provider_id`; `entities.py:85` has no
  `ForeignKey`. `prune_stale_providers` (`api/lifecycle.py:172`) deletes provider rows with nothing
  nulling `jobs.provider_id` → `IntegrityError` inside periodic maintenance.
- **`rollback_chat` deletes same-timestamp siblings.**
  `chats.py:1057-1062` uses `>= anchor.created_at` while the sibling `regenerate_reply`
  (`:1106-1111`) uses `>`. `_parse_message_timestamp` (`chats.py:260-274`) returns "now" for
  unparseable input, so imported SillyTavern chats with date-only `send_date` values collide.
- **`LoadBalancer.save_state_to_db` blocks the event loop while holding an asyncio lock.**
  `services/load_balancer.py:572` — `record_success` is `async`, holds `self._lock`, and calls a
  synchronous SELECT + COMMIT. Every provider success serialises the event loop behind a sync write.
- **`llm_config` does un-cached, un-locked, truncate-then-write file I/O on the hot request path.**
  `services/llm_config.py:16-25, 92-96`. `get_default_llm_model()` is called inside `async def`
  handlers on every chat message / story continue / suggest / impersonate. A concurrent reader can
  observe a truncated file.
- **`resolve_default_provider` can return a provider/model mismatch.**
  `services/llm_config.py:82-89` — after detecting the stored provider is disabled and
  auto-selecting provider B, it still returns `get_default_llm_model()`, which reads `model_id`
  from the same file (i.e. provider A's model).
- **`agent_simulation` loads every LLM job from the last 2 hours with no LIMIT**, then re-filters in
  Python. `services/agent_simulation.py:78-96`.
- **Full-table asset load per statistics request.** `services/asset_reconciler.py:530-542` loads the
  entire non-deleted `assets` table with two `os.stat` calls per row, twice per detailed request.
- **16 `config.py` getter functions are referenced only by tests** — `config.py:457,462,467,473,
  478,483,561,566,571,591,596,602,607,612,643,650,655`. *(Corrected: an earlier draft of this
  document generalised from "the getter is unused" to "the config key is write-only", which is

  `api/routes/collections.py:217-231` — 2N round trips.

  `Index Scan using ix_jobs_metadata_chat_id ... Index Cond: ((metadata_ ->> 'chat_id'::text) = 'x')`,
  with the `status IN (...)` predicate demoted to a cheap filter.
- **`steps_cfg` now aggregates.** On 16,048 live assets: 29 distinct pairs whose counts sum to
  16,048. Previously this produced 16,048 entries of `count: 1` with a ~129M-comparison
  linear scan.
- The index expression deliberately includes the `::varchar` cast, because SQLAlchemy compiles
  the existing filter to `CAST((metadata_ ->> 'chat_id') AS VARCHAR) = ?` and a btree
  expression index is only used on an exact expression match. Indexing the bare `(->>)` would
  have left every query still scanning.

### Highest-value remaining items (not fixed — recorded, not attempted)

1. **`/api/statistics/*` should aggregate in SQL.** Each of `/` and `/detailed` does its own
   full load of all 16k non-deleted `assets` rows, so a cold request takes ~5s (subsequent
   requests are 0.04s — the 5-minute `cache_stats` cache works). `GROUP BY metadata_->>'checkpoint'`
   plus `date_trunc` removes both loads. This is the largest remaining latency in the app and
   wants a real refactor, not a patch applied at the end of a hardening pass.
2. **Streaming model fetch.** `image_worker/engines/modal/modal_app.py` →
   `provider_registry.py` materialises the model file in RAM three times; `beam/client.py`
   base64-decodes the whole thing. A 7 GB SDXL checkpoint cannot survive this. Needs a
   ranged/streaming transport redesign across four engines and the backend proxy.
3. **Provider model downloads have no per-path lock.** Two concurrent downloads of the same
   `storage_path` interleave chunks into one file and both `os.replace()` it. The size check
   still passes. This silently corrupts published models.
4. **~35 hand-rolled modal overlays** while a real `Modal` component exists (portal + Escape +
   backdrop) is used by 2 of ~39. Only 8 files handle the Escape key at all.
5. **`CharacterCard` is implemented twice** (`Characters.jsx`, `AvatarGallery.jsx`) with
   divergent props, tag limits, and drag-and-drop.
6. **No authentication on the app itself.** Every destructive endpoint, including the
   unauthenticated published-story export, is reachable by anyone who can reach the port. Fine
   for a single-user LAN deployment; must not be exposed publicly as-is.

### Found while verifying: the frontend suite is load-sensitive

One run of `npm test` failed 9 tests across 8 files while the ~3.5-minute
backend `pytest` was still competing for CPU, and passed 751/751 on every
other run (4 consecutive clean runs, including under an idle machine).
Nothing in this changeset touches those tests' subjects.

The pattern is the tell: failures arrive spread across unrelated files
rather than clustered, which is the signature of a timeout or a
worker-starvation problem rather than a logic error. Most of these
components use `waitFor` against async React Query state, so under
contention the default 1s assertion window is the first thing to give.

Worth addressing before this lands in CI, where a loaded runner is the
norm rather than the exception: either raise the `waitFor` timeout in
`src/test/setup.js`, or cap vitest concurrency so the suite does not
starve itself. Left as a finding rather than changed here, because
loosening timeouts can mask real regressions and that call deserves to be
deliberate.

### What was deliberately not done

`GroupedDashboardContent` re-architecture, the modal consolidation, and the `CharacterCard`
unification are real duplication with no correctness impact and non-trivial UI regression risk.
They belong in a dedicated pass, not a hardening pass. The design decisions that would need
product input — whether the app should require auth, whether the LLM engines should return the
canonical `StatusResponse` everywhere or keep the three existing dialects — were left as
findings rather than unilaterally changed.
