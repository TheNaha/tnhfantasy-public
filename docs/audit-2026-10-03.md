# Codebase audit — 2026-10-03

Supersedes `docs/audit-2026-10-01.md` for everything it marks fixed. Read this
with `docs/STATUS.md`.

Four parallel read-only audits (mobile/responsive, backend, frontend
architecture, end-to-end feature wiring) plus direct measurement of the running
stack at 390px and 1400px with Chromium's own layout and colour resolution. Every
claim below is either reproduced on the live stack or read at a cited
`file:line`; the register marks which. One vendor audit item is an operational

Baselines before any change: frontend **1334 tests / 143 files passing**,
`npm run lint` **0 errors / 12 warnings**, backend `ruff check .` clean.

## 1. Executive summary

The consolidation is **not** the problem, and the codebase is **not** full of
stubs. Grep for `TODO`, `FIXME`, `XXX`, `HACK`, `onClick={() => {}}`,
`console.log`, `alert` and `placeholder for` across all non-test frontend source
returns **0 hits**. Every route in the intended roleplay information architecture
exists and is wired: `/roleplay` is the front door with Chat and Story CTAs,
recent sessions and world access, the nine legacy tools sit under **Expert
tools**, the primary nav is Roleplay Home / Play / Stories / World, and
`/campaigns` is fully retired with no surviving caller.

What *is* real, and what "many functions are literally non-functional" actually
meant, is four things:

1. **A failed fetch rendered as a genuinely empty vault, on seven pages
   including the front door.** CONFIRMED by force-500 on the live stack.
2. **One labelled switch that could not do anything**, persisted and rendered
   as working. CONFIRMED by exhaustive grep: four references, all of them the UI
   and the store default, zero readers anywhere including the backend.
3. **Mobile geometry was not as sound as the previous audit recorded.** A
   dedicated 25-route measurement at 360/390/768 found six P0s: control groups
   that were invisible *and still swallowed taps*, a beat input collapsed to
   0px, a 54px graph canvas, 17px of the active tab permanently off-screen, and
   iOS auto-zoom on 21 fields under 16px — including the prompt box on every
   generator.

4. **The entire unauthenticated API was published on `0.0.0.0`.** Every other
   item on this list is an order of magnitude smaller than one line of compose.
   Now closed: the backend publishes no host port, Traefik reaches it over the
   `proxy` network it already used for the frontend, and reachability is governed
   by the NetBird ACL at the edge.

And the most consequential finding was not a code defect at all: **five of six
providers are registered disabled**, so the load balancer had one provider, the
free local GPU path was off, the local LLM was off, and five Modal apps were
billed as idle. The variable that did it was a security control in name only —
it was deleted rather than corrected, because a flag that demands a security
rationale it cannot survive will demand one from every future reader. §4.

| Route | Endpoint forced to 500 | Rendered before |

`frontend_v2/src/test/queryErrorInvariants.test.jsx` asserts the rule — a page

### 2.3 Seven routes took a SQLModel table class as their request body — P0

Two defects per route, both confirmed on the live stack before the fix.

| | before | after |
|---|---|---|
| `POST /api/v2/characters {}` | **500** | **422** |
| client-supplied primary key | `id` accepted and persisted | rejected |

the character's `Collection`.

renders in its edit form: the route returned 200, the UI toasted "Scenario
updated", and the values never changed.

`backend_v2/tests/test_no_table_class_request_bodies.py` asserts the rule by
parsing every route in `api/routes` and failing on any `POST`/`PUT`/`PATCH`
parameter annotated with a class that has a `__tablename__`. Keyed on
`__tablename__` rather than `SQLModel`, because `sqlmodel.Session` is itself a

### 2.4 iOS auto-zoom on 21 fields — P0 mobile

Measured at 390px, computing each control's own resolved font size:

| Route | controls under 16px |
|---|---|
| `/generate`, `/img2img`, `/inpaint` | 7 each |
| `/batch-generate` | 8 |
| `/story` | 3 |
| `/chat`, `/gallery` | 1 each |

Safari on iOS zooms the *viewport* when a text field is focused and its computed
font-size is under 16px, and does not zoom back out on blur. Tapping the prompt
box — the first thing anyone does on this app — left the page magnified with the
composer under the keyboard and the fixed action bar over the form, recoverable
only by manual pinch-zoom.

The existing `@media (max-width: 768px)` block already floored `min-height` to
44px and did nothing about this, because the two properties are unrelated. The
fix had to be **unlayered**: `font-size` on a `text-sm`/`text-xs` utility lives
in `@layer utilities`, so a rule inside `@layer base` loses to it — which is how
27 of these controls were still at 14px after the 44px pass had floored their
height.

One rule in `frontend_v2/src/index.css`, under `@media (hover: none)` so a phone
in landscape and an iPad are both covered. Re-measured: **21 → 0**, with no new
blocked controls and no new overflow.

### 2.7 `image_processing.embed_metadata_in_png` was a no-op toggle — P0

Rendered as an editable toggle in Settings → Image Processing, writable in the
schema, saved to config.json, success toast on save — and
`infrastructure/image_processor.py:74-101` added the PNG text chunks
unconditionally without ever consulting the config.

Now honoured. When it is off, `services/image_processing.py` writes the metadata
sidecar, because that is then the only copy: the gallery's "reuse parameters"
reads the PNG text chunk, so turning the toggle off with no sidecar would have

inside `save_image_with_metadata` because that helper's contract is "one PNG, one
path" and three other callers use it without wanting a sidecar.

### 2.8 `is_retryable=True` on a permanent failure — P0

`services/provider_client.py:259`: a malformed *success* payload from a provider
was declared retryable. A malformed success payload is deterministic — the graph
already ran and the answer cannot be used, and re-sending the identical request
produces the identical unusable answer. It routed into
`maybe_retry_current_provider` (`max_retries: 3`, base 1.0s, cap 60s) and then
into failover: up to four paid inferences per provider plus one per remaining
provider, to fail with the same error.

Now `is_retryable=False`. Test updated to the corrected contract.

**Correction to the backend audit.** It reported that the
`retryable=True` flags on `provider_containers/**` metadata reads
(`get_object_info`, `list_models`, `validate_models`) also burn inferences. They
do not: a provider's `retryable` flag is only honoured on the `/inference` POST
path (`provider_client.py:119-125`), and those methods return 200-OK JSON to
management routes that never enter the inference path. The two flags inside the
inference streams (`remote_comfy/client.py:218,222`,
`direct_url/client.py:267,271`) are timeouts and stream errors and are correct.

### 2.10 `asyncio.create_task` with no reference

`api/routes/models/autopopulate.py:224` fired a bare `create_task` and returned
200. CPython holds only a weak reference to a running task, so it could be
garbage-collected mid-flight, and it was absent from `_background_tasks` so
`cancel_background_tasks()` missed it at shutdown. The repo already has
`start_background_task` and uses it in nine other places, including the sibling
route doing the identical "kick off work, return 200" shape. Now used.

The same file also had `import asyncio` at module level *and* again inside a
function body — ruff's F811, masked until now because the outer import was
previously "used" by the `create_task`.

### 2.11 `/api/files?directory=models/*` degraded to a filesystem scan on DB error

A DB failure answered **200 with a different, smaller result set**: the model
list silently changed shape depending on whether Postgres was reachable. The
`output` branch of the same endpoint had already rejected exactly this with a
comment naming the reasoning; the models branch kept the lying fallback.

The scan is still attempted, but the response now declares itself
(`source: "filesystem_fallback"`, `degraded: true`), and a scan failure raises
`ServiceUnavailableError` rather than answering with an empty list.

### 2.12 Retries with no jitter

`services/job_runner.py:138`: `delay = min(base * 2**n, max)` is deterministic, so
every job failing against the same unhealthy provider retried at exactly 1s, 2s,
4s — synchronising into a thundering herd on the provider's recovery moment.
Now equal jitter (`ceiling * (0.5 + random.random()/2)`), which keeps the
schedule inside [0.5x, 1.0x] of the intended backoff so the first retry still
happens promptly, and the cap still holds.

### 2.13 `ipAdapters[].stopAt` was silently discarded

The generator UI renders a "Stop At" slider per IPAdapter and the store ships it,
but `core/workflow_builder.py:34` declared only `model`, `image`, `clipVision`
and `weight`, so pydantic dropped it and `IPAdapterApply` was never given an
`end_at`. A control that looked live and did nothing.

Now accepted (aliased, `ge=0.0`/`le=1.0`) and wired to the node's `end_at`,
omitted when the default 1.0 so an unconfigured adapter still produces the
workflow it always did.

### 2.14 Six more routes ran their queries on the event loop

`GET /api/v2/models/` returns 1.5 MB and was measured flat at **761 ms per
request at concurrency 1 and 778 ms at concurrency 16** — flat meaning fully
serialised, because the query really was running on the loop. The control route
one file over, which uses `asyncio.to_thread`, went 360 → 59 → 31 ms over the
same sweep.

Four converted: `list_models`, `get_generation_info`,
`acknowledge_all_failed_jobs`, `delete_all_jobs`. Each meant making its service
method synchronous (each has exactly one production caller) and the route a plain

`tests/test_event_loop_invariant.py` gained
`test_no_await_chain_ends_in_sync_work`, which closes the gap the file's own
docstring recorded as invisible: it resolves awaited callees **across modules**
and fails when the whole chain contains no suspension. That test found **32 more
routes of the same shape**, now registered in `SYNC_CHAINED` with their service
method named, so the list is visible and shrinkable rather than a list of names
the next person has to rediscover. The index is keyed on every definition of a
name rather than the first, so a name collision can produce a missed finding but
never a wrong one.

### 2.15 Six hover-gated control groups were invisible *and still swallowed taps* — P0

The single highest-leverage defect in the mobile pass, and a one-line fix.

Six call sites emit `opacity-100 sm:opacity-0 sm:group-hover:opacity-100`:
`dashboard/GroupedDashboardContent.jsx:455`, `characters/CharacterCard.jsx:244`,
`Worlds.jsx:263`, `Lorebooks.jsx:168` and `:589`, `Locations.jsx:274`.

`index.css` already had the right rescue — an `@media (hover: none)` block that
forces `opacity: 1` on hover-reveals — but it listed only the **unprefixed**
class names `.opacity-0.group-hover\:opacity-100`. `sm:opacity-0` and
`sm:group-hover:opacity-100` are different class names, so the rule never
matched. Measured on a 768px touch viewport, every one of those groups computed
to `opacity: 0; pointer-events: auto; visibility: visible` — the worst of all
three states. Proven with a capture-phase listener recording `event.target` for
a real CDP touch tap: the tap in the top-right 44×44 corner of a gallery
thumbnail was delivered to the **invisible** favourite button instead of opening
the image. No state change, no visual feedback, no error. On `/characters` the
entire per-card action row (Chat / Edit / Export) was laid out, hit-testable and
completely invisible.

Fixed by adding the `sm:`- and `md:`/`lg:`/`xl:`-escaped variants to the same
block, with a comment recording why a hover-reveal that only appears from `sm:`
up is exactly as wrong on a tablet as one that appears from zero. Re-measured
across all 25 routes at 360, 390 and 768: **0 invisible-but-tappable controls**.

## 4. Needs a decision from you — provider enablement

**This is the largest-impact finding in the document and it is not a code bug.**

All six registered providers report `discovered`, `connected` and `healthy` true,
heartbeating within the same second. Five of them are `enabled=false`, so
`/api/v2/providers/load-balancer/stats` reports `total_providers: 1`.

| provider | enabled |
|---|---|
| `modal-zetsuke` | **true** |
| `modal-hp196` | false |
| `modal-stepmania` | false |
| `tts-modal-hp196` | false |
| `llm-local` | false |
| `direct_url` | false |

Mechanism: `docker-compose.yml:77` sets
`COMFY_DISCOVERY_ALLOW_NEW_PROVIDERS=0`, and
`services/provider_service.py:517` — the only place a discovered provider row is
born — writes `enabled: os.getenv(...) == "1"`.

Consequences: no failover for image jobs (single point of failure on
`modal-zetsuke`); `direct_url`, the free local GPU path, is off; `llm-local` is
off, so **every chat turn bills a remote model** while five Modal apps sit idle
and are billed for it.

**The flag is sticky, which is what makes it expensive to diagnose.** The
discovery *update* branch re-asserts `worker_type`, `capabilities`,
`last_seen_at`, `discovery_url` and `container_config` — and deliberately never
`enabled`, because an operator who turned a provider off in the UI means it. So
setting the flag to `1` does **not** bring back an already-registered provider.
Each needs the Providers-page toggle or an explicit
`PATCH /api/v2/providers/{id} {"enabled": true}`.

What was changed, so this cannot cost another afternoon:

- `scripts/preflight.sh` gained a **Provider enablement** section that reports
  the flag and, by parsing the live response, how many registered providers it
  is currently keeping off the load balancer, plus both recovery routes.
- The heartbeat now logs `provider_disabled_at_registration` once per provider,
  with the exact PATCH, the first time it sees the flag turned on — so the next
  person to change it learns it from the log.

### Correction, same day: this is not a security control, and the default is now `1`

The framing above is wrong, and the user was right to push on it. Re-reading the
code settled it:

- **All six providers share one bearer token.** `discovery.py:63` is a plain
  `hmac.compare_digest` against `COMFY_PROVIDER_TOKEN`, and every provider
  container already holds it. The token cannot distinguish `modal-zetsuke` from
  an impostor, so it — not the flag — is the whole boundary.
- **The flag only sets `enabled` on *new* rows.** `provider_service.py:495`
  handles the update case and overwrites `config["discovery_url"]`
  unconditionally; the flag is never consulted.
- **Dispatch prefers `discovery_url`** over `container_config`
  (`job_processing.py:728`). So one authenticated heartbeat with
  `provider_id=modal-zetsuke` and a different `internal_url` redirects every
  subsequent job — prompt, checkpoint, LoRA list, reference images — to that
  address, with the flag at 0 or at 1.

So the flag protected against nothing that the token did not already protect
against. Its only real function is blast radius in unattended setups: a container
that restarts on its own does not silently start taking paid inference traffic
until someone looks. For a single-user local studio that is not a threat.

**`COMFY_DISCOVERY_ALLOW_NEW_PROVIDERS` is deleted, not defaulted.** It is gone
from `provider_service.py`, `docker-compose.yml`, `.env.example` and
`scripts/preflight.sh`. A new provider registers enabled.

Deleting rather than defaulting is the whole argument. The flag cost a silent
capacity-and-billing surprise, and a variable whose name demanded a security
rationale it could not survive will keep demanding one from every future reader.
The Komodo comparison is the right frame: a tool that hands out root-equivalent
access on a setup token and adds friction later, if ever, is easier to adopt than
one that asks you to reason about a flag whose only function is to surprise you.
Setup friction on a self-hosted project is a real cost paid by the next person,
and this flag bought nothing in exchange.

The five already-registered providers still need a one-time toggle, because
`enabled` is sticky by design — a heartbeat must not undo an operator's choice.
That part stands, and `preflight.sh` now reports the count unconditionally
rather than only when the flag was off.

### The hole that actually existed, and it is now closed

`docker-compose.yml` published `8002:8002` on `0.0.0.0` — verified reachable on
the host's LAN IP — and **`PATCH /api/v2/providers/{id}` has no authentication at
all** (`providers/crud.py:435`). Anyone on the network could skip the flag
entirely, enable the providers, repoint `discovery_url`, or call
`DELETE /api/jobs`, which is what destroyed 154 rows of job history on
2026-10-01. A flag on a code path does not protect an API with no authentication
in front of it.

**Fixed.** The backend now publishes no host port at all. Traefik already had a
working router for the frontend (`docker-compose.yml:113-118`, on the external
`proxy` network, `Host(comfy.lan.thenaha.my.id) || Host(100.150.0.4)`,
`websecure`, `tls=true`), so the backend needed the same six labels on the same
network — copy-paste, not research. Verified from inside the Traefik container:
`http://tnhcomfy-backend:8002/api/live` → `{"status":"ok"}`.

Measured before and after on the host's LAN IP: **200 → 000.**

Two findings worth recording, because both are the kind that survives review:

- **`docker-compose.dev.yml` was silently re-adding the port.** The hardening
  change went into the base compose, the dev override still said `ports:
  ["8002:8002"]`, and the container came up still exposed. A dev override
  re-publishing a port is how a fix in the base file gets undone without anyone
  editing the base file. Removed there too.
- **`docker compose ps` reported `0.0.0.0:8002->8002/tcp` for a container whose
  compose file had no `ports:` section.** The rendered config was correct; the
  running container was not. Recreating without removing the container first left
  a stale docker port-allocator entry that failed every `up` with "address
  already in use" against a port nothing was listening on. Cost an hour;
  `docker network prune` and a forced `docker rm -f` did not clear it, only a
  plain recreate did.

Reachability is now governed by the NetBird ACL on the reverse proxy, which
grants device-specific access and is a stronger control than anything a compose
label could express. `GET /api/v2/characters/{id}`, the other unauthenticated
read called out below, is still open — but only to a device you have explicitly
allowed, which is the intended trust model.

## 7. Where the root causes are

Ranked by defects retired per fix, not by severity.

1. **A primitive that supplies part of a contract makes adoption optional.**
   `ModalOverlay` supplies Escape but not focus → 16 sites opt out.
   `EmptyState` supplies empty but not error → 33 sites opt out → §2.1.
   `useWorldVaultResource` supplies `onError` → 85 mutations sit outside it.
   `start_background_task` exists → one site bypassed it (§2.10).
   `buildQueryKey` exists → 16 sites hand-write its strings.
   The rule that retires all of them: *a primitive either owns the whole
   contract or none of it.*
2. **Testing is enumerated, not invariant-based.** Four tests were added in this
   pass, each asserted to fail when its fix is reverted. Each one retires a class
   rather than an instance — which is the only reason §2.1, §2.2, §2.3 and §2.14
   will not be rediscovered by the next audit.
3. **A measurement scoped to the viewport that was checked.** The 4-vs-24
   accessible-name discrepancy is the same trap this document inherits from
   §11 of the previous audit. Two of this pass's own first-pass findings were
   false positives on exactly this: 6 "unreachable" controls on `/generate` that
   a five-offset re-measure showed were reachable, and a settings-reader guard
   that a comment made vacuous.
4. **Config defaults that silently disable a feature, unchecked by preflight.**
   `COMFY_PROVIDER_TOKEN` cost one outage on 2026-10-02.
   `COMFY_DISCOVERY_ALLOW_NEW_PROVIDERS` has been costing capacity and money
   since it was added, invisibly. One rule — *every `os.getenv` that gates a
   feature appears in `preflight.sh`* — retires the family.
