## The theme

Three findings dominate, and they share one root cause.

**The TTS feature shipped without a working path from either end.** It was
added in `9d2ecdcc`/`a3b4632c` and the tests that landed with it assert
*structure* — that the client is an `ImageWorkerProviderClient`, that
`select_client` does not route TTS — and never *behaviour*. Five independent
P0s sit behind that: the queue can never claim a TTS job, the provider discards
every output and reports failure as success, the backend has no TTS completion
path at all, the two chat/story narrate routes build a TTS graph and dispatch
it to an **image** provider, and the Modal app cannot be imported by the Modal
version its own Dockerfile installs, so it cannot be deployed.

**The Campaign→World rename was server-side only.** `a338abc0` renamed the
router and its own commit message says, verbatim: *"Still to do on this phase:
… the frontend (page, nav, and letting a chat or story pick its world)"*. That
work was not done. The Campaigns page, the nav entry, the ⌘K entry and the
roleplay front-door card all still call `/api/v2/campaigns`, which no longer
exists. The page has no `isError` branch, so it renders a plausible empty
state and the failure is invisible. Meanwhile the replacement entity is *also*
dead: `/api/v2/worlds` has zero frontend consumers, and the two FK columns the
migration was written to add — `Chat.world_id`, `Story.world_id` — have zero
writers and zero readers.

**Six CSS classes and one media-query block were deleted and never restored.**
`10024929` removed ~20 component classes and the whole `@media (max-width:
768px)` block. The `2026-09-29` audit restored 11 of the 20 classes. The ones
it missed include `btn-primary` and `btn-secondary` — which the Characters page
uses for *both* of its only two header actions, so Tailwind v4's preflight
renders "Import Card" and "Create Character" as bare text with no surface.

These are not three unrelated bugs. They are what "consolidation" looks like
when the server moves and the client does not, and when a test asserts that a
module *is* a thing rather than that the thing *works*.

## P0

### 1. `/api/v2/campaigns` does not exist; the Campaigns page, its nav entry and the roleplay count card are 404s
`frontend_v2/src/hooks/useCampaigns.js:23,28,40,53` · `pages/Campaigns.jsx:42`

`backend_v2/api/routes/world_vault/campaigns.py` was deleted in `a338abc0`
(only a stale `__pycache__` entry remains). The hook still calls
`/api/v2/campaigns` on all five verbs, and `Campaigns.jsx:42` destructures only
`{ data: campaigns = [], isLoading }` — **there is no `isError` branch in the
file**, so a 404 renders as "No campaigns yet" with a working-looking button.

Reachable from four surfaces: `constants/navigation.js:25` (sidebar **and** ⌘K
**and** the roleplay front door's expert-tools grid), `RoleplayWorkspace.jsx:140`,
and the `CountCard` at `:214` which therefore reads `0` forever. Creating one
surfaces only `toast.error('Failed to save campaign')`.

### 2. The `World` entity is dead in exactly the way `Campaign` was
`backend_v2/core/entities.py:1186,1397,1485-1491` · `infrastructure/migrations/steps.py:3233-3260`

The migration docstring states the design: *"ownership of a Chat or Story by a
World is a nullable FK column on the owned row — `Chat.world_id`,
`Story.world_id` — rather than a membership list on the World."* Reference
counts across the whole repo:

| | writers | readers |
|---|---|---|
| `Chat.world_id` | 0 | 0 |
| `Story.world_id` | 0 | 0 |
| `/api/v2/worlds` (frontend) | — | 0 consumers |

`StoryUpdate` and `ChatUpdate` both omit `world_id`. `World.lorebook_ids`,
`World.scenario_ids`, `World.voice_ids` are declared and never touched by
anything. `scrub_entity_references` has no `kind == "world"` branch. There is
no world page; the nav item labelled "World" points at `/world-vault`, which is
the search hub.

### 3. TTS jobs are enqueued to a queue whose claim query can never match them
`backend_v2/services/job_queue.py:107-111,352,380,702-704`

`get_queue` folds `tts` into the image queue, and the only queue object is
`self.image`, whose claim SQL binds `self._task_type == "image"`. A `tts` row
satisfies the status predicate but not `task_type = 'image'`, so it is never a
candidate. The wakeup on `self.image._queue` is only a hint; the worker
re-claims from the DB by the same predicate. On Postgres every TTS job the
backend creates stays `PENDING` forever, with a `queue_position` in
`/api/jobs/active` and no error written. On SQLite the in-process queue pops
directly, so the suite is green.

`test_provider_capabilities.py:287` asserts only that `get_queue("tts") is
image` — queue *identity*, never the claim predicate.

### 4. The TTS worker discards every output and reports the app's failure as success
`provider_containers/tts_worker/engines/modal/client.py:124-129,156`

Every Modal event is re-wrapped as `TaskEvent(event="running", message=json…)`,
so `outputs` is never set on any event, and the terminal `completed` at `:156`
is unconditional — outside every except branch, including the timeout path that
yields `{"status": "error", "retryable": True}`. The backend's `_ImageReducer`
ignores `event == "running"` and stores the bare completed event; `job_processing.py:786-804`
then finds neither `images` nor `outputs` and finalizes with `outputs=[]`.

So even with #3 fixed, a TTS job goes green with no audio and no error — worse
than hanging, because the user gets no signal at all.

### 5. A completed TTS job has no completion path in the backend
`services/provider_client.py:251-273` · `services/job_processing.py:786-804` · `services/image_processing.py:104-147`

Independent of #4. `complete_when_ready` reconciles only
`output.get("type") == "image"`. `build_job_outputs` opens every payload with
`Image.open` and emits `output_type: "image"` metadata. Even if the worker sent
base64 audio, the backend would write raw bytes under a `.wav` name with image
metadata and hand it to `reconcile_asset`, which expects an image. The only
audio-aware line (`job_processing.py:714`, `is_audio`) is downstream of an
`image_path` that can never be set.

### 6. Chat and story narration dispatch a TTS graph to an image provider
`api/routes/world_vault/chats.py:1032-1037,1066` · `stories.py:1694-1700` · `core/workflow_builder.py:705-767`

Both narrate routes call `job_service.create_job(task_type="image")` with a
graph built by `core.workflow_builder.build_tts_workflow`, whose node types are
`XTTS_v2` and `SaveAudio`. `rg -ni "xtts|saveaudio" provider_containers` returns
one line, a comment in the Qwen/TTS app. The correct path already exists and is
used by all three `/voices/*` routes: `services/tts_workflow_builder.build_voice_speak_workflow`
with `task_type="tts"` + `_require_tts_capable`. Both narrate buttons are wired
in the UI, so this fails at graph validation for every user.

### 7. `tts_worker/engines/modal/modal_app.py` cannot be imported — `modal deploy` of the TTS app fails
`provider_containers/tts_worker/engines/modal/modal_app.py:192`

```python
@cls_tts.cls(..., scaledown_window=SCALEDOWN, keep_warm=0, ...)
```

`keep_warm` was removed in Modal on 2025-02-24 and the decorator now raises
`DeprecationError` at import time. `tts_worker/Dockerfile:20` installs `modal`
unpinned. `modal deploy` imports the module, so the TTS app cannot be deployed
from this tree. The image worker's twin uses `scaledown_window` +
`min_containers` and imports cleanly.

`tests/test_tts_app_routing.py:120-130` reads the file with `open()` and parses
it with `ast` *instead of importing it* — the same escape hatch that let the
Beam auth gate ship unaudited.

### 8. Every persona save reports failure after the write has already landed
`frontend_v2/src/hooks/usePersonas.js:17` → `hooks/useWorldVaultResource.js:58`

```js
export const useUpdatePersona = () =>
    useUpdateResource({ basePath: '/api/v2/personas', listQueryKey: PERSONAS_KEY });
```

`useUpdateResource` has no default for `detailQueryKey` and calls it
unconditionally in `onSuccess`. `onSuccess` is awaited inside react-query's own
`try`, so the `TypeError` is caught and dispatched as an *error*. The PATCH
succeeds, the user gets two red toasts, the edit form never closes, and the
success callback never runs. Personas is the only one of six call sites that
omits it.

### 9. The CI compose-validation job is red on every clean checkout
`.github/workflows/provider-tests.yml:92-104` vs `docker-compose.yml:298-309`

The job seeds seven env files; the `providers` profile now needs eight.
Reproduced from `git archive HEAD`:

```
env file …/.env.tts-modal-hp196 not found
EXIT=1
```

The job fails at its second step, so the three `docker build`s below it never
run — the exact failure the job was created to prevent, recurring for the same
reason. `tts_worker/Dockerfile` is built by no workflow at all, and no workflow
triggers on a change to `docker-compose*.yml`, `scripts/**` or `.env.example*`.

### 10. `remote_agent` deletes healthy models when validation is *indeterminate*
`remote_agent/server.py:352-357`

`validate_downloaded_file` returns `valid: None, indeterminate: True` when
`open()` itself raised. The `2026-09-29` audit added that third state and
honoured it at three call sites, pinned by a test that lists exactly those three
files. This is the fourth, it is the one that talks to the operator's real
network volume, and reconciliation drives it with `delete_invalid=True` on a
2-hour tick. One transient read error destroys a multi-GB checkpoint
irrecoverably.

### 11. The LLM context for chat sends and swipes is not branch-filtered
`infrastructure/repositories/message_repo.py:34-45` · `world_vault/chats.py:844-846,1238-1240`

`audit-2026-09-29.md` P1 #30 records this as **fixed** — *"the same unfiltered
read fed the LLM — the model received the conversation duplicated and
interleaved."* The read route (`chats.py:663-671`) was fixed. The two reads on
the paid path were not. Branch copies share their originals' `chat_id` **and**
`created_at` (`branches.py:229-241`), so after one fork every subsequent send
and every swipe sends a transcript containing duplicate interleaved branches.

### 12. `Message.parent_id` is never written, so the branch graph has no edges
`core/entities.py:1280` · `world_vault/branches.py:229-241` · `chats.py:860-878`

The column is a real indexed FK. Reference count across all production code:
zero writers. So `create_branch`'s `parent_id=old_to_new.get(msg.parent_id)`
is always `None`, and `get_branches` returns a flat list, not a tree. Separately,
`Message.branch_id` is written *only* by `create_branch`; `SendMessageRequest`
has no `branch_id` and `_add_message_prep_sync` never sets one, so a forked
thread can be viewed but never continued.

## P2 (open, with the fix decided)

- **`search_models` is unbounded** and its `base_model` filter runs in Python
  after the full fetch, so it bounds nothing. *(carried from 2026-09-29)*
- **`/api/files?directory=…` is the hot model path (3.4 MB, 774 ms), not
  `/api/v2/models/`.** Needs a summary DTO plus an on-demand detail fetch — a
  feature change that wants its own commit. *(carried)*
- **`config.json` is still tracked**, so Settings-UI changes dirty the tree in
  dev. `COMFY_CONFIG_PATH` plus a first-boot seed now exists. *(carried)*
- **Port 8002 is published on 0.0.0.0 with no authentication.** One-character
  fix, but a product decision. *(carried)*
- **`get_session_context()` is an `@asynccontextmanager` yielding a
  synchronous Session**, so `async with` gives no concurrency benefit and every
  world-integration handler runs sync SQLModel work on the event loop. 41 sites
  in `world_integration_service.py` alone.
- **`chat_context_kwargs` reads `chat.location_ids`**, a field `Chat` does not
  have — the same `getattr`-hides-it mistake the previous audit fixed one line
  above.
- **The idle simulator ignores the global context-window setting**, pruning at
  `DEFAULT_MAX_TOKENS` (4096) while every `chats.py` path resolves it from
  config.
- **Cloning a character strips embeddings from its cloned lorebook** (the field
  is `exclude=True`, so `model_dump` drops it) and there is no reindex route for
  lorebook entries, so the loss is permanent.
- **`delete_character` orphans the embedded lorebook and its entries**;
  `delete_story` leaves `assets.story_id` dangling (`reference_cleanup` does not
  handle `Asset`).
- **The agentic `store_memory` tool has none of the dedup** `memory_extraction`
  was given, so the retrieval pathology the audit documented is still reachable
  through the second of the two writers.
- **`jobs.workflow` stores the system prompt twice** (`messages[0]` and
  `character_system_prompt`); no worker reads the second copy.
- **`.lock` sweep** — see #37.
- **`vllm_modal` hardcodes `retryable=True` on remote errors** where the other
  three LLM engines use `retryable_for_exception`, so a permanent failure is
  retried across the whole pool.
- **`runtime_config["storage_dir"]`** is written by all three workers and read
  by nothing.
- **The image worker relies on `background.py`'s `worker_type` default** while
  the LLM worker's comment asserts it passes one explicitly. The default
  changing would silently convert every image provider.
- **Two unused backend deps** (`img2pdf`, `fpdf2`) under a `# Export pipelines`
  comment, and `api/main.py:18` credits `tenacity` for a backoff that is
  hand-rolled in `job_runner.py:137`.
- **`sqlalchemy` is imported directly across the backend but only `sqlmodel` is
  declared.**
- **Compose `environment:` silently overrides `env_file:`**, so a per-provider
  `PROVIDER_WORKER_TOKEN` is dead if the project `.env` lacks it — and present-
  but-empty means "no token configured" → 503 on every protected route.
- **`test_app_boot_smoke.py::test_lifespan_runs_every_declared_startup_phase`**
  is a timing flake, roughly 1 in 3 full runs. *(carried)*
- **Dead code, both directions**: `build_voice_clone_workflow` (0 callers),
  `useVirtualListScrollMargin` (0 importers, and the bug it was written for is
  still in the file), `useAssetTags` (0 importers), `build_deploy_compatibility_response`
  (0 production callers), `ensure_tts_model_dir` (0 callers), six repository
  methods with no caller, `QueueManager.pending_count`/`active_count`,
  `/avatar-gallery` and `/world-timeline` (redirects nothing links to).
- **Six write-only or never-written columns** on World, Scenario and Character
  (`scenario_ids`, `voice_ids`, `default_checkpoint`, `default_voice_profile`,
  `parent_session_id`, `DetectionRun` rows with no reader).
- **Two request routes take SQLModel *table* classes as bodies** — the
  `ChapterUpdate` bug class, un-fixed in `create_chapter`, `create_character`,
  `create_lorebook`, `create_entry`. A client-supplied `id` is persisted.
- **Two keyboard-shortcut systems**: a topmost-wins registry that 11 raw
  `keydown` listeners bypass, including the Dashboard's, which fires under open
  dialogs.
- **`/providers` statically pulls a 290 kB recharts chunk** to draw one
  sparkline.
- **Three more undefined Tailwind plugin classes**: `animate-in`/`fade-in`/
  `slide-in-from-*` (9 sites, `tailwindcss-animate` not installed),
  `scrollbar-thin`/`no-scrollbar` (6 sites, `tailwind-scrollbar` not
  installed), `kbd` (4 sites), `animate-spin-slow` (1 site).

## How this was verified

Every P0 was re-checked directly before its fix rather than trusted from the
sub-report: the missing `campaigns` router was confirmed by grep (only a stale
`__pycache__` entry), the TTS claim predicate by reading the queue construction
and the bound SQL, the persona crash by reading the hook and the shared
`onSuccess`, and the dead CSS classes by grepping `index.css`.

The claims that are *measurements* rather than readings are marked as such in
the sub-reports: the lock-key instability was shown across three interpreters,
the modal `Volume` API absence by probing the installed package, the CI failure
by staging a clean checkout from `git archive HEAD`, the frontend root by
`docker exec ... id` on the running container, and the test counts by running
all three suites.

Two audit items from `2026-09-29` are reported here as **not fixed** despite
being marked fixed there — #30 and #31 above, plus #11 and #24 which were
fixed at two of three sites. That is the third time this pattern has appeared
in this repo's audit history; the common cause is a fix that lands at the site
named in the report while an equal site it did not name keeps the defect.

### Two things worth recording

**Three of my own regression tests were not load-bearing on the first pass.** The
`worker_type` test passed on a 404 without ever reaching the field; a source-level
sentinel guard could not fail at all; and the capabilities test proved the update
path while claiming to prove create. Each was found by reverting the fix and
re-running, which is the only reason they are correct now. A test that has never
been seen to fail is a comment.

**The `BatchGenerate.presets` suite failed once under full-suite load** — a 1 s
testing-library default on a file that takes 12 s in isolation. The assertion was
correct and the timing assumption was not, so the timeout is now explicit. Not
a product defect, but it is the third recorded timing flake in this repo's test
history and it is a shared-host hazard rather than a code one.
