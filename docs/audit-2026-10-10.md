# 2026-10-10 codebase audit — detritus from the 10-08 engine consolidation

Supersedes nothing: this pass is scoped to what the 10-08 provider-container
consolidation left behind, so it is a *delta* audit, not a whole-codebase one.
Read it after `audit-2026-10-05.md` (which remains the reference for everything
that predates 10-08).

Method: six read-only sub-agents over disjoint scopes (backend services,
backend routes/infra, engines, frontend data layer, frontend UI, cross-seam
integration), then **every candidate was reproduced by hand before it was
reported** — and three of the reported candidates turned out to be wrong, and are
recorded as such in §3. A candidate that survives verification is worth fixer
time; one that does not costs it.

Baselines before any change: backend 3181 passed / 9 skipped; frontend 1780
passed; ruff clean; eslint 0 errors; stack serving 200s on `localhost:5174`.

Severity follows the earlier audits: P0 data loss or crash, P1 wrong behaviour,
P2 quality or performance, P3 cosmetic.

## 1. Fixed in this pass

### 1.1 P1 — failover was defined and then made unreachable (fixed)

`services/load_balancer.py:546` answered `None` when a job's *pinned* provider was
unavailable — exhausted by an earlier attempt on the same job is the common case.
`job_runner.select_next_provider` reads `None` + a non-empty `exhausted_providers`
as "all providers failed" and finalises a `FAILED` job, so a pinned job could
never fail over at all. The non-health-aware branch below and the LLM branch above
both fell back to the strategy over the remaining pool; the health-aware branch
did not, which is the only branch the deployment actually runs.

Revert-verified by `tests/test_load_balancer.py::TestLoadBalancer::
test_pinned_provider_exhaustion_falls_over` — and it only fails without the fix
once `COMFY_LB_HEALTH_CHECKS_ENABLED=1`, because `conftest.py:17` turns health
checks off suite-wide and the test would otherwise have exercised the healthy
non-health-aware path.

### 1.2 P1 — the upload cap inversed and refused every upload (fixed)

`get_upload_size_cap()` documents 0/negative as *disabled*, and
`get_upload_max_bytes_encoded()` correctly returns 0 for that. Four engines then
compared `len(body) > encoded_cap` with no guard on the cap, so
`PROVIDER_UPLOAD_MAX_BYTES=0` — the documented way to turn the cap off — made
every non-empty upload fail. `api/routes/files.py:301` had the read right
(`cap and len(content) > cap`) and the four engine copies did not.

Fixed by extracting the verdict into one predicate, `encoded_upload_over_cap()`
in `services/engines/base.py`, and routing all four engines plus the pre-check
placement through it (`modal_engine`, `beam_engine`, `direct_comfy_engine`,
`llm_engine`). The pre-checks also moved out of beam/direct's `try` blocks so a
fault in the guard is no longer swallowed into a generic `return False`.
`remote_agent/server.py:642` had the twin defect (`max_bytes >= 0`) and is fixed
the same way.

### 1.3 P1 — a timeout was reported as a user cancellation (fixed)

`provider_client.call_in_process_llm_provider` wraps the engine stream in
`asyncio.timeout(timeout)`, which delivers the deadline by cancelling the task.
`AnthropicLLMEngine.inference` and `GoogleLLMEngine.inference` caught that
`CancelledError` and yielded a `cancelled` event instead of re-raising, so the
timeout never reached the timeout context manager's `__aexit__` and never became
a `TimeoutError`. The job finalised as "cancelled by user" and the retry the
timeout is allowed never happened.

Both engines already carry the cooperative `self._cancelled_jobs` check inside
their SSE loops — which is what a real user cancel uses, and what preserves the
partial content — so the `except asyncio.CancelledError` handler owned only the
propagate case and now re-raises. The partial content of a genuine cancel is
unchanged.

### 1.4 P2 — nested model files matched nothing, forever (fixed)

`in_process_reconciliation.py` keyed a listed file on `directory + basename`. The
remote agent walks recursively and reports `path` as a full relative path
(`models/checkpoints/sub/yolo.pt`), and `get_all_storage_paths()` builds
`models/{model.directory}/{filename}` — where `directory` can itself be two
segments (`ultralytes/seg`). Dropping the intermediate segment meant the path
never matched: the file was re-marked pending on every tick, reported as an
orphan on every tick, and with delete-orphans enabled that is a delete against a
path that does not exist.

Fixed by extracting `_storage_path_for_entry()`, which prefers the reported
`path`/`storage_path` and only falls back to `directory/name` — the same
preference order the maintenance scan (`api/routes/models/maintenance.py:531`)
has always used, which is the reference implementation this was drifted from.

### 1.5 P2 — the availability cache had no invalidation path (fixed)

`ModelAvailabilityService.clear_available_models_cache()` had **zero production
callers**, while its own docstring named the model-install and provider-toggle
paths that would call it. Result: the 30 s availability cache served a deleted
model and hid an installed one, and a provider enable/disable — which changes the
candidate set outright — was not seen either. `LoadBalancer`
`invalidate_model_availability_cache` is now the single entry point that clears
both, and the provider update route calls it when `enabled` or `capabilities`
change.

### 1.6 P2 — routes and queries that accepted impossible input (fixed)

- `api/routes/jobs.py:243` (`/jobs/search`) and `:562` (`/jobs/breakdown`)
  clamped only the upper bound, so a negative `limit` reached the repository as
  `LIMIT -1` — Postgres answers a 500, SQLite reads it as unlimited, which is an
  unauthenticated whole-table dump on that dialect. Both now clamp at both ends.
- `api/routes/world_vault/world_hub.py:246` accepted an unbounded `q` — a free
  full scan over five text columns — while importing `MAX_SEARCH_LENGTH` and
  never using it. Now bounded like every sibling search route.
- `services/tag_service.list_tag_vocabulary` fetched `limit + 1` rows and
  returned all of them, so `?limit=50` answered with 51 tags. It now returns a
  `TagVocabulary` (a `list` subclass) carrying a `truncated` flag, so the route
  can report truncation without a second fetch and every existing reader is
  untouched.

### 1.7 P2 — request bodies with fields the handlers never persisted (fixed)

- `api/routes/world_vault/scenarios.py` `PUT /scenarios/{id}`: `ScenarioUpdate`
  declares `default_checkpoint` and `default_voice_profile` and the handler
  applied only name/description/prompt_template. A client that sent the other two
  got a 200, a success toast, and no change.
- `api/routes/world_vault/characters.py` `CharacterUpdateRequest` accepted
  `group_greetings`, `creator` and `character_version` in the create request and
  not in the update one, so a card's version and creator notes were write-once
  and the v3 `group_greetings` list uneditable after import. Pydantic's default
  `extra='ignore'` dropped them and the route answered 200.
- `api/routes/world_vault/stories.py` `POST /stories/parse` took an unbounded
  `text`, truncated it silently at 10,000 chars, and never checked the story
  exists — an invalid `story_id` imported chapters into a nonexistent story.

### 1.8 P2 — dead config, dead branches and statuses nobody decodes (fixed)

- `config.json:34` still shipped `modal.vllm`, a block `config.py` documents as
  removed, and which has higher precedence than DEFAULT_CONFIG. Deleted.
- `services/model_downloader.py` wrote status `not_installed` for
  external-host providers — outside the documented `pending / downloading /
  ready / failed` vocabulary. `provider_status_service` keeps unknown values and
  simply never buckets them, so those rows counted toward `total_models` while
  every bucket read zero: the providers page showed "9 assigned" next to "0
  installed, 0 pending, 0 failed, 0 downloading". Now writes `pending`.
- The same loop carried an unreachable `worker_type == "llm"` skip (guarded by a
  `runtime.mode != "in_process"` the preceding guard had already excluded), a
  tautological `if runtime.mode == "in_process":`, and a third
  `type in {direct_url, remote_comfy}` arm that can never be reached from an
  in-process runtime. All removed.
- `infrastructure/migrations/steps.py:088` scanned every provider row instead of
  only those with `container_config`.
- `services/reference_cleanup._scrub_json_array` built its LIKE pattern by raw
  f-string interpolation, drifting from the `core.sql_search` helpers the rest of
  the tree uses (and which `asset_metadata_index` and `tag_service` both use).
- `api/routes/models/maintenance.py:518` derived its sweep list from
  `model_reconciliation._DIRECTORY_TO_MODEL_TYPE` — a directory → model *type*
  map with 14 entries — instead of importing `MODEL_DIRECTORIES` (16), silently
  dropping `models/clip_vision` and both `models/ultralyses/*` trees from the
  sweep. Now imports the canonical list.
- `direct_comfy_engine.NODE_TO_DIRECTORY` mapped `"DiffusersLoader" → "diffusers"`,
  a directory that is not in `MODEL_DIRECTORIES`, so `list_models` can never
  fetch it. Removed.

### 1.9 P2 — a test guard that could not fail (fixed)

`tests/test_like_pattern_escaping.py`'s `test_no_application_like_call_builds_its_
pattern_by_interpolation` had been **passing vacuously since it was written**. It
computed its attribute set as `{c.lstrip(".") for c in {".like(", ".ilike(", …}}`,
and `".like(".lstrip(".")` is `"like("` — which no `ast.Attribute.attr` ever
equals. `_like_pattern_arguments()` therefore returned `[]` for every file and
the test iterated nothing.

Fixed, and strengthened while fixing: the set is now the attribute names, the
helper resolves one level of variable indirection (the reason
`reference_cleanup`'s `pattern = f"%{id}%"` was invisible to it), and the rule
distinguishes a literal from an interpolated pattern by AST node type rather
than by whether the unparsed text starts with `"`. Re-verified against the
original `reference_cleanup` source.

### 1.10 P2/P3 — drift in the provider runtime (fixed)

- Six `int()`/`float()` env reads executed at import (`beam_engine:36-37`,
  `:48`; `modal_engine:41`; `llm_engine:507`; `orchestrator_service:31`), so a
  typo in a deployment env file was a boot crash. Added `env_positive_int` /
  `env_positive_float` to `config.py` and routed the engines through them.
- `modal_engine.get_file_stream` treated an empty chunk as a clean end of file,
  so a short read produced a silently truncated stream — which the caller then
  hashes and stores, and which fails its own sha256 check later. Now raises.
- `modal_engine.close()` dropped the client reference without closing it, leaking
  the connection pool across every credential rotation — exactly when it is
  called.
- `modal_tts_engine` bounded its reads with a hardcoded 64 MiB while
  `PROVIDER_GET_FILE_MAX_BYTES` remained the documented, exported knob. Fetch now
  uses the shared read cap; upload keeps its 64 MiB, which is the container's 413
  parity contract, and is now named as such.
- `direct_comfy_engine.get_file_stream`'s agent branch applied no size cap at
  all — the only stream in the tree without one — and answered an agent 413 with
  a bare `RuntimeError` rather than `FileTooLargeError`. Both fixed.
- `job_queue` re-spelled the active-status set as raw SQL string literals in two
  statements (`:385`, `:903`), decoupled from `core.entities.ACTIVE_JOB_STATUSES`.
  Now interpolated from the enum. **This found a bug in the refactor itself**: the
  literals are the enum *names* (`'GENERATING'`), and reading `.value` produced
  parameters that matched nothing — a reset that reported success and did
  nothing. `tests/test_job_queue.py::TestRawSqlStatusVocabulary` now executes the
  statement against SQLite, which it never did (it is Postgres-guarded and was
  previously covered only by a live EXPLAIN).

### 1.11 P2 — query-key and invalidation bugs in the frontend (fixed)

- `useSetLLMDefault` invalidated the default and models keys but not the providers
  key, whose rows carry `is_default` — so the old winner kept its badge and the
  new winner got none.
- `awaitJobText` skipped only *iteration 0* when the WebSocket was connected and
  then polled once per interval until `maxPolls` ran out, doubling the load for
  the whole job. Now a slow heartbeat (`WS_FALLBACK_EVERY`) plus a guaranteed
  final fetch, so an event emitted before the subscription is still caught.
- `useJobsRealtime`'s gallery refresh ignored `gallery.autoRefreshOnJobComplete`
  while the Dashboard's own handler for the same refresh honoured it — with the
  setting off the gallery still reloaded. Now gated. (The double request when the
  setting was on was already coalesced by `refetchNewestGalleryPage`'s in-flight
  map.)
- `useJobRecovery` invalidated the bare `['gallery']` prefix, which walks every
  loaded page of an infinite query sequentially for one job state change. Now the
  scoped newest-page refresh.
- `useChatStreaming` never invalidated the memories list on a completed chat job,
  even though memory extraction writes character memories at exactly that point.

## 2. Open — not fixed in this pass

Ordered by value. Everything here is substantiated; nothing here is speculative.

### P2

1. **`remote_agent/provider_core/downloads.py:899` puts the CivitAI token in
   the URL query string.** `_resolve_download_auth` correctly uses
   `Authorization: Bearer` for HuggingFace but appends `token=` to the URL for
   CivitAI, and that URL is what the downloader logs and persists. A token in a
   query string leaks through access logs, redirects, `Referer` and `Range`
   polls. Note the fix is *not* "drop the query param" — CivitAI's
   anonymous-model download path is the consumer here, so it needs either the
   header (if that registry accepts it for this endpoint) or an un-logged,
   un-persisted URL. The bearer header at `:896` is the shape to copy.
2. **`vllm_engine.py:58` `check_updates` sorts the downloaded sources but upserts
   the unsorted `deduped`.** Ordering is the only guard against a duplicate
   crate/arch/version/entity, so which one wins is decided by dict iteration.
   Either upsert `result["sources"]` or drop the sort and document the tie-break.
3. **The five inference loops are five divergent re-implementations of one
   contract** (`modal_engine:92-108`, `vllm_engine:143-157`,
   `direct_comfy_engine:574-582`, `beam_engine:255-270`, `llm_engine:390-420`).
   `file_uploads`, `delete_after_use` and `outputs` are mandated by
   `client_v2`/the reducer but are absent from three of them, so the send path
   only works for the engines that happen to have copied it.
4. **`download_token_for_url` is copied four times** with drift: `llm_engine:496`
   adds Beam, `direct_comfy:719` silently defaults to the HF token.
   `beam_engine`'s private copy and `remote_agent`'s are byte-identical.
5. **Duplicate-worker creation commits an id-shaped placeholder.**
   `create_provider` (`crud.py:430`) inserts the provider row with no worker, and
   the explanatory comment attributes the leftover `worker_id: None` row to a live
   `worker_configs` API — but no such route exists in the backend. The PK identity
   should never be assigned in a commit that can fail.
6. **`_validate_model_url` (`crud.py:359`) constructs a URL from a controlled
   `model_id`,** so a caller-chosen `model_id` can chain the one unrestricted
   outbound fetch into an internal port scan. The files-type check should be
   `== 'model'` with the branch replaced by a registry lookup.
7. **`modal_engine`'s `_send_bytes_with_retries` retries a stream that already
   streamed bytes** (`:151-156` re-reads the request after a mid-stream failure;
   the fix's `_request_retries` is never passed in, so it is a no-op).

## 3. Reported and then disproved (kept so they are not re-reported)

1. **`files.py` `MoveAssetRequest` optional `character_id`/`story_id`** — claimed
   that the fallback `if body.character_id is not None else asset.character_id`
   was dead code and both associations were always cleared. It is not: omitting
   the key yields `None`, so the `else` branch runs and the existing value is
   kept. Both Dashboard callers send exactly `{workspace, copy_file}`
   (`FeedCard.jsx:311-322`). The real limitation is that there is no way to
   *unlink* an association by moving, which is a design gap, not a bug.
2. **`model_reconciliation.py:177-182` per-file `session.rollback()` discarding
   earlier imports** — claimed the `imported` counter counted discarded rows.
   `update_provider_status` calls `session.commit()` per file
   (`model_repo_v2.py:978`), so each successful file is already durable before
   the next one starts, and `imported` is only incremented after that commit
   returns. The rollback is correctly scoped to the file that failed.
3. **`session_detector._load_rows` sorting before filtering `None`** — already
   fixed at `:300-307`, which filters first and carries that comment. The audit
   read a stale snapshot.
4. **`files.py` `serve_asset_file` swallowing exceptions and returning a
   200-with-empty-body** — the route does no error handling, so an exception
   propagates to the error handler as a proper error. There is no swallow.
5. **`reference_cleanup` silently stripping the *wrong* id from a Story's
   `character_ids`** — the LIKE match was unscoped (§1.8), but the removal
   itself is exact in Python (`_without` matches by equality), so the blast
   radius was rows loaded and rewritten unnecessarily, not data corruption.
6. **`load_balancer.py` caching `_check_provider_health` failures with no TTL and
   no invalidation** — the cache is `TTLCache(ttl=15.0)` (`:58`), it is popped by
   `engine_factory.invalidate_engine` (`engine_factory.py:692-694`), and it is
   cleared by `LoadBalancer.reset_state` (`:221`). A 15-second failure window with
   explicit invalidation is the design, not a defect.
7. **The `remote_agent` `'ANY'` path-traversal escape
   (`shared/database.py:504-506`)** — the file does not exist in this tree, and
   neither does `_COMMON_DB_NAMES`; the agent read the `provider_containers/`
   tree that 10-08 deleted. The "durable fix" would have been a change to a file
   that is not here, which is the most expensive shape a false positive takes.
8. **`server.py:475-478` swallowing a delete error, and `maintenance.py:669`
   reading that as "confirmed gone"** — the validate-invalid path *does* swallow
   the `os.remove` `OSError` (a logging gap worth closing), but the backend's
   delete path records `status: "error"` per provider and does not treat a falsey
   result as success, and `cleanup_orphan_models` is about DB models with no
   versions rather than about delete results. The data-loss consequence does not
   follow.
