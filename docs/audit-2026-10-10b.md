# 2026-10-10b — the in-process worker (engines tier)

Scoped audit of the compute tier `9a91e6f2` made the only execution path:
`backend_v2/services/engines/` (6,293 LOC), plus the lifecycle that runs it
(`engine_factory`, `load_balancer`, `in_process_reconciliation`, `provider_client`,
`job_runner`, `job_queue`, `api/lifecycle`). Read `docs/audit-2026-10-10.md` first
— this is a second pass on the same working tree, not a supersession.

Method: two read-only sub-agents (contract completeness; lifecycle/concurrency/
integration), then hand-verification of every candidate before it was accepted or
fixed.

Baselines at the start of the pass: backend 3211 passed / 9 skipped.

## 1. Fixed in this pass

### 1.1 P0 — startup re-generated paid jobs on every restart

`api/lifecycle.py` ran the recovery phases in the order its own comment forbade.
The comment at the call site said post-processing recovery must run *before* the
claim sweep, and gave the reason in full; the two `await` lines were the other way
round.

The mechanism, verified end to end: `recover_pending_jobs` → `QueueManager.recover`
→ `_reset_claims_and_requeue_sync`, whose UPDATE carries
`ACTIVE_JOB_STATUSES` — which *includes* `POST_PROCESSING` — and sets those rows
to `PENDING` with `claimed_at` cleared. PENDING-with-no-claim is the claim
predicate, so a live worker re-ran the entire generation. Then
`recover_post_processing_jobs` queried `status == POST_PROCESSING` and found
nothing, because the sweep had just moved them all. `requeue_inflight_jobs_for_
shutdown` deliberately protects these rows on the way out; starting in the wrong
order undid that protection on every boot.

The two calls moved into a named, testable `_run_job_recovery_phase()` — the same
"name the phase so the guard guards the rule, not the symbol shape" reasoning as
`services/job_queue.py:353`'s `_name_placeholders` note. **A pre-existing guard
pinned the wrong order against its own correct docstring**
(`test_world_vault_audit_2026_09_29b.py`'s `test_pending_sweep_runs_after_
post_processing` asserted `["recover_pending_jobs",
"recover_post_processing_jobs"]` while the docstring above it stated the opposite
requirement). It now reads both symbols and asserts the order the docstring
always meant.

### 1.2 P1 — a cancelled Direct-ComfyUI job was finalised as a success

`cancel_job` sets the flag and `_on_cancel` POSTs `/interrupt`. ComfyUI answers an
interrupt with `executing {node: null}` — byte-for-byte the frame a *finished*
prompt emits. The loop's `if node is None ... break` treated it as `# Completed`,
fell through to the history fetch, and yielded `completed` with the artifacts
persisted. The loop-top cancel check never ran again after a `break`.

Fixed by re-checking the cancel state immediately after the loop exits, before the
history fetch. Attribute the interrupt to the job's own prompt
(`_on_prompt_ids` / `_interrupted_prompts`) rather than trusting the flag alone,
because `/interrupt` is global to the ComfyUI instance: a sibling job's cancel
must not be reported as this job's, and a real completion must not be
misreported as a cancellation. Both per-job maps are dropped in a `finally`, so
they do not grow one entry per job for process life.

### 1.3 P1 — the no-agent Direct rig's whole model tree looked orphaned

`_normalize_directory("models/checkpoints")` strips to `checkpoints`, and
`_iter_object_info_model_paths` then emitted `f"{target_dir}/{name}"` =
`checkpoints/foo.safetensors`. Every consumer of that list keys on
`models/<dir>/<filename>`: `model_repo_v2.py` builds it from
`f"models/{model.directory}/{file.storage_filename}"`, the maintenance scan uses
the same shape, and the *agent* branch of the same method returns
`os.path.relpath(..., DATA_DIR)`, which already carries the prefix.

So on a rig with no agent — exactly what `supports_discovery_reconcile` exists
for — discovery matched nothing. Files were never marked `ready`, and
`existing_files - all_expected_paths` computed to *every* file, which was then fed
to the orphan path; with `RECONCILIATION_DELETE_ORPHANS=true` that is a delete
against a path that does not exist, on every tick, forever. `name` now uses
`os.path.basename` so the filename no longer carries the directory prefix. The
existing `test_list_models_parsing` pinned the old shape and is updated to the
corrected contract.

### 1.4 P1 — Anthropic rejected any history with parallel tool calls

`translate_messages_anthropic` emitted one user message per `role == "tool"` row
and left consecutive user turns consecutive. Anthropic requires alternating roles
and rejects the first same-role pair with HTTP 400 — and `retryable_for_status(400)`
is False, so the job failed *permanently*. That is the agentic roleplay path:
`translate_tools_anthropic` exists precisely so the model can call several tools
per turn.

Fixed with `_normalize_anthropic_messages`, called from the translator rather than
at each call site, so no future engine copy re-introduces it. It merges
consecutive same-role turns (concatenating content blocks, which is how all the
`tool_result` blocks of one assistant `tool_use` turn end up in the *single* user
message the API requires), drops empty turns, and prefixes a placeholder user turn
rather than reordering a history that opens with `tool` — reordering would break
the pairing instead of fixing it.

### 1.5 P2 — engine clients were closed never correctly

Three defects in one small area:

- `clear_engine_cache()` had **no production caller at all** — its docstring named
  the shutdown path and the path did not exist. Shutdown closed only the shared
  `infrastructure/http_client` pool, so every engine's own client leaked until the
  process exited — and with a 30-minute engine TTL, across every credential
  rotation on top of that. `_shutdown_engine_cache()` is now a named shutdown
  phase, ordered before `close_http_client`, and it cannot raise.
- `invalidate_engine` closed an engine's client while a job was streaming through
  it. `execute_job` holds the engine for the whole attempt, so rotating
  credentials or disabling a provider mid-generation aborted the in-flight stream
  and retried a generation the provider had already billed. Closes are now
  idle-aware: the cache entry drops immediately (no new work uses it), the close
  is deferred by `run_inference`'s `finally` in `base.py`, and that drain is
  exactly the hook that was missing.
- `loop.create_task(close())` dropped its only strong reference, so the close
  coroutine could be collected before the loop ran it — the same hazard the queue
  documents for its own workers. The tasks are now held.

## 2. Open — verified, not fixed in this pass

### P1

1. **Only DirectComfy can actually stop upstream work.** `_on_cancel` is
   implemented in exactly one engine. For Modal/TTS the cancel path returns from
   the local loop and relies on the SDK tearing down the remote generator; there
   is no cancel call to the app, so a long generation keeps running (and billing)
   to completion. Beam stops its fetcher — the only other real upstream signal.
   The hosted LLM engines observe the flag only at the next SSE frame, so with an
   idle stream a cancel waits for the caller's `asyncio.timeout` instead of the
   2 s poll Modal/vLLM allow. Needs a per-engine `_on_cancel`.
2. **`job_runner`'s hot path does synchronous SQLModel on the event loop.**
   `update_job`/`get_job`/`record_attempt`/`mark_failed` are `async def` shells
   over `session.exec(...)` + `session.commit()`, and `_ImageReducer` calls
   `update_job` on every progress frame (throttled to 1/s). Each in-flight job
   issues a blocking DB commit per second, plus 2-4 blocking reads per attempt,
   all inline. `tests/test_event_loop_blocking.py` polices this class for other
   modules and the job path is not in its registry. Same for `load_balancer`:
   `get_next_provider` runs 2-3 DB reads per dispatch inline.
3. **The default thread pool, not the DB pool, will bound any `to_thread` fix.**
   No `set_default_executor` exists, so every `asyncio.to_thread` hop shares
   asyncio's `min(32, cpu+4)` pool — 6 threads on the documented 2-CPU
   deployment — while the DB pool is 30+30. Fixing #2 without sizing a dedicated
   executor just moves the queue.

### P2

4. **`direct_comfy_engine`'s websocket has no `max_size`** — the library default
   is 1 MiB, and Beam passes an explicit 20 MiB for the same traffic. A ComfyUI
   frame above 1 MiB raises `ConnectionClosedError`, which the loop turns into a
   retryable failure of the whole job.
5. **A failed `/view` fetch silently drops the image and the job still reports
   success** (`direct_comfy_engine._fetch_view` returns `None` on any non-200 and
   the outputs list filters it out). A transient ComfyUI 500 on one of four images
   finalises a "successful" 3-image job with no error and no retry.
6. **The provider model-delete route ignores `delete_file`'s boolean** and reports
   success unconditionally, and bypasses the sidecar-aware `delete_model` every
   other caller prefers — so `.json`/`.preview.png`/`.sha256` sidecars survive.
7. **`ModalVLLMEngine.get_file_stream` truncates on a short read** (`if not chunk:
   break`), where `modal_engine` treats the identical condition as fatal — and that
   file is what reconciliation hashes.
8. **Direct's `get_file_stream` maps 401/403 to a generic `RuntimeError`** where
   Beam/Modal raise `EngineAuthError`, so an expired token reads as a transient
   per-file failure.
9. **Contract-completeness matrix, the cells worth acting on** (from the agents'
   matrix, hand-checked): `get_file_stream` raises `NotImplementedError` on the
   hosted LLM engines (unreachable — every caller gates on `manages_model_files`
   first); `download_file` is absent on plain Direct; `setup_models` returns `True`
   on plain Direct with nothing to set up, which `registry.supports_setup` then
   reports as a live capability; `get_object_info` returns a dummy `{}` on
   ModalVLLM where the others raise; `validate_models` is a base default on five
   engines but is unreachable for all of them.

### P3

10. **Beam and ModalVLLM report `healthy` with zero network contact** — a dead
    `gpu_url` reads healthy for the health cache's 15 s and gets dispatched.
11. **Beam is the only engine whose stream can end with no terminal event**
    (`if item is None: break`), so the caller only learns from
    `reducer.finalize()`'s generic message.
12. **`BeamEngine.close()` abandons in-flight background downloads**, and can close
    the shared httpx client underneath a running POST.
13. **`ModalTTSEngine` has no `close`** at all, so `_close_engine` finds nothing.
14. **Cache-invalidation holes:** provider DELETE does not clear
    `_model_availability_cache`/`_available_models_cache` (the deleted provider
    stays eligible for the TTL); `/state/cleanup`,
    `/cleanup-orphaned-statuses` and the hourly `run_data_cleanup` mutate
    `ProviderVersionStatus` rows but only drop the provider-stats cache;
    **enable/disable never resets `provider_failures`/`provider_job_counts`**, so a
    provider disabled at streak 2 re-enables still 2-from-trip.
15. **`in_process_reconciliation`'s `current_download` is mutated lock-free** by
    concurrent downloads (last writer wins), and the periodic tick queries on the
    event loop.
16. **`infrastructure/scheduler.py`'s `_AdvisoryRunLock` leaks its session on every
    tick where the lock is not granted** — `__exit__` returns early before the
    close.
17. **Cold-provider health probes stampede**: `_check_provider_health` has no
    single-flight, so N concurrent dispatches all probe the same provider.
18. **`infrastructure/cache.py`** already solves the single-flight and TTL problems
    in #16/#17 correctly; these are sites that did not use it.
19. **Dead code that reads like a live contract:** `base.get_storage_stats` (and if
    ever wired, 16 `list_models` round-trips per call), `base.deploy`,
    `BeamEngine.queue_download`/`trigger_download`, and the unreachable
    post-loop `if offset < total_size` in `modal_engine.get_file_stream`.

## 3. Verification

```
cd backend_v2 && .venv/bin/python -m pytest -q      # 3225 passed, 9 skipped
cd backend_v2 && .venv/bin/ruff check .             # clean
```

Baseline was 3211. The increases are the tests added in this pass; each fix in §1
carries a test that fails without it, confirmed by reverting the fix and rerunning
(the startup order, the Direct cancel path, the `models/` prefix, the Anthropic
normaliser, and the three engine-lifetime behaviours).

The stack was restarted and re-checked against the new code:
`localhost:5174` → 200, `/api/live` and `/api/ready` → 200, job and world-vault
endpoints → 200, and the backend logs show a clean `startup_complete` with the
new `engines` shutdown phase in place. `backend_v2` is bind-mounted into the
backend container at `/app`, so a restart picks the changes up without a rebuild.

Frontend was not touched by this pass.
