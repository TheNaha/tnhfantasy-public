# Backend Documentation

The backend of TNHComfy (`tnhcomfy-backend`) is built with **FastAPI** (Python 3.13), serving as the core engine for job queuing, orchestration, and communication between the frontend and inference providers.

## Key technologies

- **FastAPI:** high-performance web framework for APIs.
- **SQLModel / PostgreSQL 16 + pgvector:** relational store for jobs, providers, World Vault entities (characters, chats, stories, lorebooks, …), settings, and a filesystem-synced Asset index. pgvector powers semantic Lorebook and memory retrieval.
- **Socket.IO:** real-time bi-directional communication with the frontend for job status updates, mounted on `/socket.io`.
- **HTTPX:** asynchronous HTTP client for non-blocking requests to external providers.
- **Structlog:** structured logging.
- **Prometheus:** metrics exposed at `/metrics` via `prometheus_client`.
- **Tenacity:** retry with exponential backoff for provider calls.

## Architecture

The backend consists of several key modules, in a strict **routes → services → repositories** flow:

1. **API Routes (`backend_v2/api/routes/`):** REST endpoints for jobs, models, providers, collections, generation, settings, statistics, health, files, websockets, and the World Vault (`/api/v2/*`). The World Vault routers are registered once in `api/routes/world_vault/__init__.py`.
2. **API infrastructure (`backend_v2/api/`):** app setup (`app_setup.py`), dependency injection (`deps.py`), error handlers, job orchestration and processing (`lifecycle.py`, `job_processing.py`), and the Socket.IO manager (`websocket.py`).
3. **Services (`backend_v2/services/`):** business logic — job queue, job service, job runner, job submission, load balancer, provider service, provider status/lifecycle/reconciliation, chat pipeline, pipeline runner/stages, illustrator, updater, asset reconciler, LLM router, embedding service, RAG pipeline, world ownership/integration/onboarding, and more.
4. **Core (`backend_v2/core/`):** domain entities (`entities.py`), domain events (`events.py`), domain exceptions (`exceptions.py`), DTOs, pipeline limits, workflow builder/parser/postprocess, scene graph, provider capabilities.
5. **Infrastructure (`backend_v2/infrastructure/`):** database setup, migrations (`migrations/steps.py`, no Alembic), HTTP client, image processor, logging, metrics, request dedup, scheduler, background tasks, repositories.
6. **In-process engines (`backend_v2/services/engines/`):** Modal, Beam, Direct ComfyUI, LLM (llama.cpp), and TTS engines implementing the `InProcessEngine` contract in `base.py`. The backend never runs ComfyUI itself — inference always goes to a worker.

## Data storage strategy

- **Relational data:** jobs, providers, World Vault entities, and application settings live in PostgreSQL. The dev/local default in `config.py` is SQLite (`sqlite:///./data/db/comfy.db`) for host-only runs, but the Compose stack always uses Postgres — they are different databases, so data created in one is invisible in the other.
- **Files:** output images generated by ComfyUI are stored locally on the filesystem, partitioned as `output/{user_id}/{workspace}/YYYY/MM/DD/`. An `assets` DB table is maintained by `services/asset_reconciler.py` (thumbnails, blurhash, metadata extraction) and is the single source of truth for gallery listing, thumbnail serving, and statistics — no filesystem scans at startup.
- **No permanent checkpoints:** the backend does not permanently store large model checkpoints, keeping it lightweight.

## Config

Precedence (highest to lowest): `COMFY_*` environment variables > `config.json` (runtime-editable via the Settings UI, written atomically) > `DEFAULT_CONFIG` in `config.py`.

`config.json` defaults to `backend_v2/config.json`; in Compose `COMFY_CONFIG_PATH=/data/config.json` points it at the durable bind mount so Settings UI changes survive recreates. The `.env` file with `COMFY_*` secrets lives at the **repository root**, not in `backend_v2/`.

## Migrations

Migrations run **automatically at backend startup** via the ordered steps runner in `infrastructure/migrations/steps.py`. Each step is a `MigrationStep(version=..., apply_fn=...)` entry, recorded in `schema_migrations`, and applied once. Add new migrations as new entries in that list — there is no Alembic. Do not introduce Alembic unless explicitly requested.

## Background tasks and lifecycle

The lifespan (`api/main.py` → `api/lifecycle.py` `startup_application`) runs:

1. Database init + schema migrations; provider-state artifact cleanup.
2. Job-queue configuration (worker pool) and interrupted-reconciliation reset.
3. Known-provider-host priming + 60s refresh timer.
4. Job queue start; provider monitor + telemetry polling.
5. PENDING/RUNNING job recovery (post-processing jobs are finalised before the sweep re-enqueues active ones — ordering is load-bearing).
6. Scheduler: provider-host refresh, vacuum, preview prefetch, data cleanup, job reaper, idle simulation (opt-in), CivitAI resync, in-process reconciliation.
7. Socket.IO broadcast + cross-process dispatch listener (Postgres LISTEN).
8. World integration start and the asset-migration background task.

Image jobs complete in the background: thumbnail generation, blurhash, and `assets` row upsert via `asset_reconciler.reconcile_asset` happen before the job transitions to `COMPLETED`, so the gallery is always consistent.

## Event loop and async operations

The backend relies heavily on `asyncio`. Synchronous DB work is offloaded where it would block the loop; a few remaining sync handlers are documented technical debt. Provider calls go through `httpx.AsyncClient`. Retries use tenacity with exponential backoff; 4xx is permanent, 5xx/429/408 transient.

## Security posture

- **Bind the backend to loopback, never `0.0.0.0`.** The API has no authentication, so a wildcard bind exposes every route — including `DELETE /api/jobs` — to the LAN. Use `COMFY_BACKEND_BIND=<address>` to publish on one named address.
- Compose publishes `127.0.0.1:8002` and `${COMFY_BACKEND_BIND:-100.150.0.4}:8002` (the operator's VPN/LAN address), never a wildcard.

## Development setup

The venv is **`.venv`** (not `venv`). `setup_jules.sh` creates `backend_v2/.venv`; every documented command uses `.venv`.

1. Ensure Python 3.13+ is installed (CI runs 3.13).
2. Navigate to `backend_v2` and set up the environment:
   ```bash
   cd backend_v2
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   ```
3. Copy `.env.example` to `.env` **at the repository root** and fill in the necessary tokens (`HF_TOKEN`, `CIVITAI_TOKEN`, provider credentials). `config.py` resolves `<repo-root>/.env`. A `backend_v2/.env` is gitignored and read by nothing.
4. Note that this path uses **SQLite**, not the Compose stack's PostgreSQL. `setup_jules.sh` and `cd backend_v2 && uvicorn` both resolve to `sqlite:///./data/db/comfy.db` (the `config.py` default), while Compose runs `postgresql://…@db/comfy`. They are different databases, so a character you create in one is invisible in the other. (One maintenance script, `scripts/backfill_download_urls.py`, still defaults to the older `sqlite:///./data/comfy.db` path — a latent inconsistency, not fixed here.)
5. Run the server (loopback only):
   ```bash
   .venv/bin/uvicorn api.main:app --host 127.0.0.1 --port 8002 --reload
   ```

Or run the full stack with Docker Compose:
```bash
bash scripts/preflight.sh
docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build -V -d
```

## Testing

- `pytest.ini` sets `addopts = -n auto` (xdist). The full suite (~4,200 tests) has OOM'd this host — run targeted files, and never run vitest at the same time as backend pytest.
- Postgres/pgvector tests run only when `PGVECTOR_TEST_URL` is set (as it is in CI).
- Tests that create DB sessions must override both `api.deps.get_session` and `infrastructure.database.get_session` — use the `session` fixture and never open your own session.
- `docs/api.md` is generated; after changing any router, run `scripts/generate_api_docs.py` or `test_api_docs_contract.py` fails.
- `ruff.toml` selects F only and F401 is on. Every `# noqa: F401` needs a stated reason. Run `ruff check .` from `backend_v2/` (the repo root reports ~450 unrelated errors).

## Hidden surface area (scripts, CLIs, background jobs)

### Host scripts (`scripts/`)

- `scripts/preflight.sh` — create external `metrics`/`proxy` networks; report config that silently disables features.
- `scripts/deploy.sh {list,check,image,tts,llm,beam,all} [--dry-run]` — the only supported way to deploy cloud workers (run on the host, never from the API).
- `scripts/generate_api_docs.py` — regenerate `docs/api.md` from `app.openapi()`.
- `scripts/launch_modal_worker.py`, `scripts/migrate_sqlite_to_pg.py`, `scripts/update_colab_notebooks.py` — maintenance helpers.

### Backend maintenance scripts (`backend_v2/scripts/`)

- `migrate_sqlite_to_postgres.py`, `migrate_output.py`, `migrate_unet_models.py` — data migrations.
- `reindex_asset_loras.py`, `backfill_download_urls.py`, `clean_preview_cache.py`, `benchmark_statistics.py` — one-off maintenance.
- `external_worker_client.py` — client helper for remote agents.

### Remote agent (`remote_agent/`)

Separate stack with its own compose file, `agentctl.sh`/`agentctl.bat`, and binary build. See `remote_agent/README.md`.

### Background scheduler jobs (started in `api/lifecycle.py`)

Registered at startup (see `startup_application`): provider-host refresh (60s), DB vacuum (24h), model-preview prefetch, data cleanup (1h), job reaper (5min), idle simulation (opt-in, default 10min), CivitAI resync (24h), in-process reconciliation, provider telemetry polling, provider monitor, WebSocket broadcast, asset migration (one-shot background thread), cross-process dispatch listener, world integration. `GET /api/settings/scheduler` exposes status and run history.
