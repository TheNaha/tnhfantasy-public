### Critical Bugs & High-Risk Defects

#### BUG-01: Thread-Safety Hazard in `JobService` Database Offload
- **Severity**: Blocker / High
- **Location**: `backend_v2/services/job_service.py:348-353, 489-532, 850-978`
- **Evidence**:
  In `backend_v2/services/job_service.py:978`, `update_job` offloads `_db_work` via `run_db(_db_work)`. In production with PostgreSQL and `QueuePool`, `run_db` schedules `_db_work` onto `db_executor.executor` (`ThreadPoolExecutor`). Inside `_db_work`, the callable directly invokes `self.repo.get(job_id)` and `self.repo.update_where_status(...)`, which use `self.session` bound to the caller's request-scoped `Session`.
  SQLAlchemy sessions and DBAPI connection handles are explicitly not thread-safe. When multiple progress updates or concurrent status changes occur, the same `Session` instance is accessed simultaneously or sequentially across different worker threads without thread affinity.
- **Proposed Fix**:
  Inside offloaded closures (`_db_work`, `_read`), bind to the underlying database engine (`bind = getattr(self.session, "bind", None) or ...`) and create a dedicated, thread-isolated `Session(bind, expire_on_commit=False)`. Expire caller session objects so any subsequent reads from `self.session` reload clean state.

#### BUG-02: Leaked Client Connection in `ModalTTSEngine` (Missing `close()`)
- **Severity**: High
- **Location**: `backend_v2/services/engines/modal_tts_engine.py:136-170`
- **Evidence**:
  `ModalEngine` (`backend_v2/services/engines/modal_engine.py:347-366`) explicitly defines `async def close(self)` to close its cached Modal client connection pool (`await aclose()`). `ModalTTSEngine` initializes `self._client = await modal.Client.from_credentials.aio(...)` at line 165, but defines no `close()` method. When `engine_factory.py:957-960` evicts cached engines on credential updates or shutdown (`close = getattr(engine, "close", None)`), `ModalTTSEngine` skips cleanup, leaking open network connections and gRPC client handles.
- **Proposed Fix**:
  Implement `async def close(self)` in `ModalTTSEngine` to cleanly close `self._client` when present.

#### BUG-03: Database Session Held Open Across External Cancel RPC
- **Severity**: High
- **Location**: `backend_v2/api/routes/websocket.py:364-420`
- **Evidence**:
  In `handle_cancel_job`:
  ```python
  async with get_session_context() as session:
      job_service = get_job_service(session)
      job = await job_service.get_job(job_id)
      ...
      if runtime.mode == "in_process":
          await engine.cancel_job(job_id)
      ...
      await job_service.update_job(job_id, status=JobStatus.CANCELLED)
  ```
  The database session is held checked out across external network RPCs (`engine.cancel_job` or `request_worker_job_cancel`). If the remote worker hangs or takes seconds to respond, a DB connection remains blocked in the pool, creating pool exhaustion under concurrent cancellations.
- **Proposed Fix**:
  Read job information within an initial session block, exit the block before awaiting network RPC cancellation, and re-acquire a session to write the cancelled state.

#### BUG-04: TDZ ReferenceError Race Condition in `awaitJobText`
- **Severity**: Medium
- **Location**: `frontend_v2/src/hooks/useLLMJobResult.js:46-52`
- **Evidence**:
  `const finish = (result) => { ... unsub(); resolve(result); }` references `unsub()` before `const unsub = on(EventTypes.JOB_COMPLETED, ...)` is initialized. If an event fires synchronously or before variable binding, calling `finish` raises a Temporal Dead Zone `ReferenceError: Cannot access 'unsub' before initialization`.
- **Proposed Fix**:
  Declare `let unsub;` above `finish()`, then assign `unsub = on(...)`.

## Design Note: JobService Thread-Isolated Database Offloading (BUG-01)

### Problem
`JobService.update_job`, `get_job`, and `record_attempt` run their database operations via `await run_db(callable)`. In production with PostgreSQL and `QueuePool`, `run_db` executes the callable on a worker thread in `ThreadPoolExecutor`. The callable accesses `self.session`, which is a request-scoped SQLModel `Session` created on the calling thread. SQLAlchemy Sessions are not thread-safe: concurrent access or passing sessions across threads causes transaction corruption, `InvalidRequestError`, and connection checkout conflicts.

### Approach
1. In `JobService`, retain `self.session` for callers operating on the main thread.
2. Inside `_db_work` (and `_read` / `_work`), acquire a dedicated, thread-local `Session(bind, expire_on_commit=False)` using `bind = getattr(self.session, "bind", None) or default_engine`.
3. Perform the read/write using the thread-local session, commit/refresh, and exit cleanly.
4. On `self.session`, call `self.session.expire_all()` so any subsequent reads through `self.session` fetch freshly committed data.
5. In tests with SQLite `StaticPool`, `run_db` already runs inline on `MainThread`, so both SQLite tests and PostgreSQL production behave consistently and safely.

### Affected Files
- `backend_v2/services/job_service.py`
- `backend_v2/tests/test_db_offload.py`

### Risk & Rollback
- **Risk**: Test cases relying on uncommitted writes across sessions could observe isolation boundaries.
- **Mitigation**: `bind = getattr(self.session, "bind", None)` ensures the exact same database engine/connection pool is used. If issues arise, changes can be rolled back cleanly commit-by-commit.
