## Critical bugs (fix now)

### M1 — Health-cache staleness after credential rotation
**Location:** `backend_v2/services/engines/engine_factory.py:invalidate_engine` vs `backend_v2/services/load_balancer.py:_check_provider_health`
**Evidence:** `invalidate_engine` (engine_factory.py:~1036) pops only the bare key `f"in_process:{provider_id}"` from `_provider_health_cache`. But `_check_provider_health` (load_balancer.py:~460, ~489) writes and reads per-task-type keys `f"in_process:{id}:{task_type}"` (image/llm/tts). Those survive `invalidate_engine` for up to the 15s TTL, so a just-rotated provider (credentials PATCHed) can still be judged healthy for a specific modality by the old verdict until the TTL expires.
**Risk:** After `PATCH /api/v2/providers/{id}` rotates credentials, the load balancer may route a job to the provider using stale-cached healthy verdict for up to 15s, then fail at call time.
**Fix:** Pop all per-task-type health-cache keys for the provider_id in `invalidate_engine`, or key health checks by provider_id only (task-type is orthogonal to credential validity).

### M2 — remote_hybrid can_create/get_engine asymmetry
**Location:** `backend_v2/services/engines/engine_factory.py:can_create_engine` vs `get_engine`
**Evidence:** `can_create_engine` (remote_hybrid branch, ~187-211) requires an explicit `container_url` (returns False without one). `get_engine` (remote_hybrid branch, ~570-634) defaults `base_url` to `"http://localhost"` when none configured. So `can_create_engine` can return False for a provider `get_engine` would build — a false-negative exclusion that keeps a reachable provider off the balancer.
**Risk:** A remote_hybrid provider with no `container_url` in config but a working default URL is never selected, even though `get_engine` would construct it.
**Fix:** Align `can_create_engine` with `get_engine` — treat missing `container_url` as constructible (default localhost) for remote_hybrid, matching the direct_url/remote_comfy pattern.

### M3 — SECTION_LEAF_ALLOW_LISTS omits most config sections
**Location:** `backend_v2/config.py:SECTION_LEAF_ALLOW_LISTS`
**Evidence:** The allow-list covers only `ai`, `generator`, `system_prompts`, `jobs.llm`. `_validate_config` calls `_reject_unknown_leaves` only for sections in the list. Typos in `worker`, top-level `jobs`, `model_sync`, `downloads`, `modal`, `api` (beyond `cors_origins` entries), `jobs_cleanup`, `image_processing`, `roleplay` pass validation, are deep-merged into config.json, and persist forever; only `reset_config` removes them. `tests/test_settings_exposure.py:409-422` asserts each listed section's DEFAULT_CONFIG leaves are present, but unlisted sections have no coverage.
**Risk:** A typo'd setting (e.g. `worker.poll_intarval`) is silently accepted and stored, with no effect and no way to remove except `reset_config`.
**Fix:** Extend `SECTION_LEAF_ALLOW_LISTS` to every DEFAULT_CONFIG section leaf (or reject unknown leaves for all sections), and add coverage for unlisted sections.

### M4 — Read-modify-write outside lock for system-prompts / library / llm_config
**Location:** `backend_v2/api/routes/settings.py` (system-prompts + library routes) and `backend_v2/services/llm_config.py` (`set_default_provider`, `set_active_models`)
**Evidence:** `update_config` and `reset_config` serialize on `_config_lock` (config.py:640), but the callers in settings.py and llm_config.py read the current value, merge locally, then call `update_config` — the read and write are not inside one lock. Two concurrent PUTs read the same list/dict, merge different entries, and the second write overwrites the first (lost update). `set_default_provider`/`set_active_models` in llm_config.py do the same read-modify-write on `llm_config.json` (atomic file write, but non-atomic read-modify-write boundary).
**Risk:** Concurrent settings updates lose earlier writes.
**Fix:** Hold `_config_lock` across the read-modify-write for system-prompts/library settings routes; add an equivalent lock around llm_config read-modify-write (or document the single-writer assumption).

### M5 — _capability_cache never invalidated on node install/uninstall
**Location:** `backend_v2/services/engines/engine_factory.py:invalidate_engine`
**Evidence:** `invalidate_engine` pops `_provider_health_cache[f"in_process:{provider_id}"]` and calls `invalidate_object_info_cache(provider_id)`, but never touches `_capability_cache` (load_balancer.py:~73, TTL 60s). The capability cache is populated from `engine.get_object_info()` and used for sampler/scheduler hard-block checks. After a node is installed/uninstalled on a provider, stale capabilities can select that provider for a job using a node it lacks → "node type not found" at dispatch.
**Risk:** Provider selected for a job it cannot run; job fails after dispatch delay.
**Fix:** In `invalidate_engine`, also clear `_capability_cache` entries for the provider_id (or bump a cache version).

### M6 — reset_config memory/disk divergence
**Location:** `backend_v2/config.py:reset_config`
**Evidence:** `reset_config` updates the in-memory `_config` under the lock, then attempts the atomic file write; if the write fails it logs a warning but still returns the in-memory reset. Memory and disk now diverge: the next `get_config()` returns the reset values, but disk still holds the old config; a restart restores the old config.
**Risk:** Operator believes settings were reset; after restart they're back. Inconsistent with `update_config`, which re-raises save failures.
**Fix:** On save failure in `reset_config`, restore the in-memory `_config` to its pre-reset value and re-raise (matching update_config's contract), or at minimum document the divergence.

### M7 — _config is None load_config outside lock (startup edge)
**Location:** `backend_v2/config.py:update_config`
**Evidence:** `update_config` calls `load_config()` when `_config is None` OUTSIDE the `_config_lock` (config.py:~623-624). Under concurrent early requests during startup, two calls could both see `_config is None` and both call `load_config`, racing on the module global. (Startup edge only; `get_config` also does this.)
**Risk:** Rare startup race; two early concurrent config writes could interleave badly.
**Fix:** Guard the `_config is None → load_config()` check inside the lock, or make `load_config` idempotent-safe under the lock.

## Medium / low bugs (fix now)

### m1 — Constructible ≠ reachable providers pass selection
**Location:** `backend_v2/services/engines/engine_factory.py:can_create_engine`
**Evidence:** `direct_url`/`remote_comfy`/`direct_tts` return True unconditionally (default localhost:8188); `openai_compat`/`ollama` need only `base_url` (no key). Such providers pass `can_create_engine` and the load balancer may select them, then fail at inference call time unless the 15s health cache has already marked them down.
**Risk:** Job dispatched to an unreachable provider, fails after dispatch delay; failover incurs a paid retry.
**Fix:** This is partially mitigated by the health cache, but `can_create_engine` returning True for unconfigured providers means they're never filtered out pre-dispatch. Accept as known tradeoff OR add a lightweight reachability probe in `can_create_engine` (flagged — see S3).

### m2 — Failure streaks persisted only every 20 jobs
**Location:** `backend_v2/services/load_balancer.py:_track_job`
**Evidence:** `_persist_snapshot` runs every 20 jobs; `report_success`/`report_failure` mutate in-memory `provider_failures`/`provider_job_counts` only. A restart mid-window loses up to 19 jobs of failure/job-count delta. Job counts are recalculated from DB on startup; failures come from the possibly-stale persisted row.
**Risk:** Circuit-breaker state slightly inaccurate after restart until the next 20-job window.
**Fix:** Accept (documented tradeoff) or persist on every report (write amplification). Flag as low-priority.

### m3 — Manifest `act` stage never executed by pipeline_runner
**Location:** `backend_v2/services/pipeline_runner.py:run_from` vs `backend_v2/services/api/routes/world_vault/chats.py:_send_message` and `backend_v2/services/job_processing.py:_run_pipeline_stages_isolated`
**Evidence:** The pipeline manifest's `act` stage has `runs_as="job"`, `executor=""` — `run_from` resolves no executor for it and walks to `act` as a no-op. The LLM generation job is hand-rolled in `_send_message` via `submit_llm_job`, outside any manifest executor. The post-turn audit/update/illustrate/chain walk runs in `_run_pipeline_stages_isolated("audit")` in job_processing.py, a SECOND walk duplicated from pipeline_runner. If one walk is edited without the other, the manifest and execution diverge.
**Risk:** Architectural divergence — the manifest stops being the single source of truth for the chat pipeline.
**Fix:** Document the duplication as intentional (act is a job boundary; audit walk is post-completion) and add a test asserting the two walks' stage sets are consistent. Not a behavior change.

### m4 — settingsStore mirrors server config in Zustand (stale mirror risk)
**Location:** `frontend_v2/src/store/settingsStore.js`
**Evidence:** `settingsStore` persists UI preferences to localStorage AND caches server-owned config mirrors (`defaultCheckpoint`, `prompt_shortcuts`, `ai.*` block wired to `/api/settings`). A stale mirror can outlive the server value. Generator pages read from Zustand.
**Risk:** Generator uses a stale default checkpoint or prompt shortcut after a server-side settings change, until page reload.
**Fix:** Document the mirror contract (stale until reload) OR have generator pages read server config via React Query instead of Zustand. Low-risk doc fix; flag the architectural question (S10-ish).

### m5 — React Query key prefix collisions (over-broad invalidation)
**Location:** `frontend_v2/src/hooks/useChats.js:CHAT_LIST_KEY` and `src/constants/queryKeys.js:modelListKey`
**Evidence:** `CHAT_LIST_KEY = ['world_vault','chats','list']` is a strict prefix of every `chatListKey()` result, so `invalidateQueries(CHAT_LIST_KEY)` refetches ALL chat-list variants (documented as intentional). Edge collision: a chat whose `id === 'list'` makes `CHAT_DETAIL_KEY('list')` identical to `CHAT_LIST_KEY`. Also `['models']` is a prefix of `modelListKey(...)` → broad model-list invalidation on any model change.
**Risk:** Over-fetching (performance) and, in the `id === 'list'` edge, writing a chat detail update onto the list key (stale list).
**Fix:** Accept the documented intentional behavior for `CHAT_LIST_KEY`; add a guard that a chat `id` of `'list'` is rejected/re-named at the API or frontend. Low risk.

### m6 — 16 of 33 overlay declarations hand-rolled, outside useEscapeKey registry
**Location:** `frontend_v2/src/components/` (candidates: CharacterCardImportPreview, CharacterCardImportReport, ModelSelector, ConfirmationModal, CharacterDetailsModal, NewChatModal, SceneGallery, GreetingPickerModal, DeployModal, ActionOutputModal, Modal, ModelDetailsModal, AutopopulateSelector, CivitaiSearchModal, KeyboardShortcutsModal, ModelMetadataModal, ImageLightbox, JobDetailsModal)
**Evidence:** `STATUS.md:1230` states 16 of 33 overlay declarations still hand-roll their backdrop and sit outside the `useEscapeKey` registry. Stacked dialogs can close together (the exact defect `common/Modal.jsx:24-27` records). `useEscapeKeyCoverage.test.jsx` covers 10.
**Risk:** UX regression — stacked modals close together; escape behavior inconsistent.
**Fix:** Mechanical conversion of the remaining 16 to `ModalOverlay` + `useEscapeKey`. `ModalOverlay` has no focus trap (a previous attempt broke 8 tests and was reverted) — do not change its `role`. This is a per-route screenshot/QA pass; flag as medium effort.

### m7 — Characters.test.jsx doesn't mock confirmationStore
**Location:** `frontend_v2/src/pages/Characters.test.jsx`
**Evidence:** `Characters.jsx:32` uses `useConfirmation`, but `Characters.test.jsx` does not mock `confirmationStore` (unlike Providers, ChatWorkspace, StorySandbox, etc.). The real Zustand singleton mounts, risking cross-test resolver leakage.
**Risk:** Flaky tests when confirmation dialog state leaks between tests.
**Fix:** Add `vi.mock('../store/confirmationStore')` to `Characters.test.jsx` factory. Low risk, clear win.

### m8 — load_config default-file creation not atomic
**Location:** `backend_v2/config.py:load_config` (~508-511)
**Evidence:** Default `config.json` creation uses plain `open(_config_path,'w')` — not atomic, no fsync. A crash mid-write leaves an empty/corrupt file; `load_config` handles it afterwards via quarantine (`_quarantine_unreadable_config`), so the operator's file is not destroyed.
**Risk:** Brief window of corrupt config; handled by quarantine. Low risk.
**Fix:** Use the same atomic writer (mkstemp + fsync + os.replace) as `update_config`/`reset_config`. Low risk, clear win.

### m9 — Branding/favorites use plain open(...,'w')
**Location:** `backend_v2/api/routes/settings.py` (`save_branding_config`, `save_favorites_list`)
**Evidence:** Plain `open(...,'w')`, not atomic, no fsync (settings.py:~834-838 documented). A corrupt favorites load wipes the file on next save.
**Risk:** Data loss for branding/favorites on crash during write.
**Fix:** Use atomic writer. Low risk, clear win.

### m10 — Frontend lint warnings (5)
**Location:** `frontend_v2/src/components/SceneGallery.jsx:70`, `ContextField.jsx:28`, `ParseStoryModal.jsx:15` (unused eslint-disable directives); `useDashboardModals.js:25,44` (unnecessary `filters` dep)
**Evidence:** `bun run lint` reports 0 errors / 5 warnings.
**Fix:** Remove unused eslint-disable directives; remove unnecessary `filters` dependency from `useCallback` in `useDashboardModals.js`. Low risk, clear win.

## Items flagged for user decision (deletion or public-contract/policy change)

### D1 — Orphaned scripts (backend_v2/scripts/{backfill_download_urls,benchmark_statistics,clean_preview_cache}.py)
Unreferenced from source code (grep confirmed no imports/callers). However `.kilo/plans/1786217595814-refine-unify-polish-plan.md:38` explicitly lists them under "Keep the real tools." So they're referenced by a plan artifact but not by source. **Decision needed:** delete (dead code) or keep (plan wants them). I will NOT delete without your say-so.

### D2 — Duplicate prestartup_script.py
`backend_v2/memory_snapshot_helper/prestartup_script.py` and `deployables/modal/image/memory_snapshot_helper/prestartup_script.py` are byte-identical. BUT both are referenced: the backend_v2 copy by `backend_v2/Dockerfile` (reload-exclude), the deployables copy by `deployables/modal/image/modal_app.py:462` (MEMORY_SNAPSHOT_HELPER_LOCAL_PATH packaged into the Modal image). This is intentional duplication across separate build contexts, not accidental. **No change; note only.**

### S1 — No authentication
Every destructive endpoint (`DELETE /api/jobs`, `PATCH /api/v2/providers/{id}`, etc.) is reachable by anyone who can reach the API. `DELETE /api/jobs` deleted 154 job-history rows on 2026-10-01. The compose file binds loopback + named addresses only (not 0.0.0.0), and Traefik/NetBird govern reachability. **Decision needed:** accept the demo/studio boundary, or add auth. This is a product/security decision, not a code defect.

### S2 — jobs_cleanup has zero consumers
`jobs_cleanup` settings exist (`max_age_hours`, `auto_cleanup`, `cleanup_interval`) but nothing reads them. The `jobs` table grows without bound. **Decision needed:** implement the consumer, or document it's intentional.

### S3 — Dispatch-time provider prune not implemented
The builder skips what the target provider cannot do (build-time), but there's no dispatch-time filter, so a graph reaching a provider with a missing node fails with "node type not found" rather than being pruned. **Decision needed:** implement the prune step (changes output — needs its own home).

### S4 — No provider-picker UI
`preferred_provider_id` is honored end-to-end by the backend, but the Enhancements panel asks about the first ENABLED image provider and the Advanced Generator silently uses `providers.filter(p => p.enabled)[0]` for object_info. With two enabled providers, the panel describes one and the balancer might run the other. **Decision needed:** add UI provider picker.

### S5 — file.path missing from /api/files projection
The `/api/files` projection lacks `file.path`, so the Provider Status list filters LLM providers out (`ModelDetailsModal.jsx`). **Decision needed:** add `file.path` to the projection (API change).

### S6 — Badge vs submit-time gate disagreement
The model-availability badge uses the model-level aggregate; the submit-time gate uses the exact `(directory, filename)` pair. They disagree about the same row. **Decision needed:** unify into one "can this provider run this exact file, right now" function.

### S7 — No integrity verification
The `.sha256` sidecar is read but never compared to an upstream hash; `ProviderVersionStatus.verified_at` has zero writers; `ModelFile.hash_sha256` conflates upstream expected hash with provider's local hash. Download gate is size + magic bytes only. **Decision needed:** implement integrity verification (feature).

### S8 — get_pending_downloads has no per-provider assignment filter
Every provider converges on the whole download catalogue. Coherent as policy, undocumented. **Decision needed:** add per-provider assignment, or document.

### S9 — /api/v2/models/catalog returns the LLM registry, not models
API-surface decision rather than a cleanup. **Decision needed:** change or document.

### S10 — charGen* prompts never seeded from server
Eight server-owned generation prompts are mirrored into the generator settings store and exposed on Characters, but nothing reads them from config.json. Editing them in Settings reports success while the value goes nowhere (inert control). **Decision needed:** seed from server, or remove the inert control.

### S11 — _use_db_claims env mismatch
`JobQueue._use_db_claims` is derived from the global `COMFY_DATABASE_URL`, but tests swap in a SQLite engine, so container runs report claims=True on a SQLite engine. Test-environment only; production consistent. **Decision needed:** resolve from live engine dialect, or accept test-env difference.

### S12 — Naive-datetime test fixtures
Many test seeds use naive datetimes against tz-aware SQLModel fields. Production uses `datetime.now(timezone.utc)`. Not a code defect; test-only. **Decision needed:** annotate fields with NaiveDatetime or migrate tests to tz-aware seeds.
