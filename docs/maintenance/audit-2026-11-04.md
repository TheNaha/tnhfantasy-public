## 2. Detailed Findings

### Critical Bugs

#### [CRIT-01] Concurrent Multi-Threaded Access to Shared SQLAlchemy Session in Targeted Model Downloads
- **Severity**: High / Critical
- **Location**: `backend_v2/services/in_process_reconciliation.py:1060-1175`
- **Evidence**: `_run_targeted_downloads` creates a single session via `session = api_deps.get_session_sync()` and passes it to `model_service`. Then `asyncio.gather(*[_download_one(...)])` runs concurrent download workers (bounded by semaphore up to 5). Inside each concurrent task, `asyncio.to_thread(_mark_downloading)` and `asyncio.to_thread(_mark_ready)` call `_write_provider_status`, invoking `model_service.repo.update_provider_status` on that shared SQLAlchemy session across worker threads concurrently.
- **Risk**: SQLAlchemy and SQLite sessions are not thread-safe. Concurrent multi-threaded commits/flushes lead to `sqlite3.ProgrammingError` or SQLite database lock / corrupt session state.
- **Proposed Fix**: Inside each worker or inside `_write_provider_status`, acquire an isolated session via `with api_deps.get_session_sync() as worker_session:` and instantiate a dedicated `model_service = api_deps.get_model_service_v2(worker_session)`.

#### [CRIT-02] Request-Scoped Session & JobService Used in Detached Background Story Comic Export
- **Severity**: High / Critical
- **Location**: `backend_v2/api/routes/world_vault/stories.py:2932-3003`
- **Evidence**: In `export_chapter_comic`, `job_service = JobService(session)` is created with the request-scoped `session`. Inside the background task `_run_export()`, a new `task_session = get_session_sync()` is created for `export_comic_chapter`, but the final status updates call `job_service.update_job(...)` (which references the request's `session`) and `await asyncio.to_thread(session.commit)`. When the HTTP response returns, FastAPI closes `session`, causing `_run_export` to raise `DetachedInstanceError` or `ResourceClosedError` and leave the export job permanently in progress.
- **Proposed Fix**: Inside `_run_export()`, instantiate `task_job_service = JobService(task_session)` and use `task_job_service.update_job(...)` and `task_session.commit()`.

#### [CRIT-03] Provider Cost Dashboard Uncaught TypeError Crashing Component on Mount
- **Severity**: High
- **Location**: `frontend_v2/src/pages/ProviderCostDashboard.jsx:27-36`
- **Evidence**: `useQuery` destructures `const { data: jobs = [] } = useQuery(...)` for `GET /api/jobs`. The endpoint returns `{ jobs: [...], total: ... }`, so `jobs` is assigned the object `{ jobs: [...] }`. In the component body, `for (const job of jobs)` throws `TypeError: jobs is not iterable` during React render, crashing the dashboard and unmounting the component.
- **Proposed Fix**: Unpack query data properly: `const { data: jobsData, isLoading, isError, error, refetch } = useQuery(...)` and `const jobs = Array.isArray(jobsData) ? jobsData : (jobsData?.jobs || []);`.

#### [CRIT-04] Relationship Timeline Messages Undefined Property Access Swallowing All Chat History
- **Severity**: High
- **Location**: `frontend_v2/src/pages/RelationshipTimeline.jsx:57`
- **Evidence**: `fetchTimeline` calls `const resp = await api.get('/api/v2/chats/.../messages')`. `api.get` directly returns the parsed JSON array. Line 57 reads `const msgs = Array.isArray(resp.data) ? resp.data : (resp.data.messages || [])`. Because `resp` is an Array, `resp.data` is `undefined`, so `resp.data.messages` throws a `TypeError: Cannot read properties of undefined (reading 'messages')`. The surrounding `catch { return []; }` silently catches the error, causing the timeline to always be completely empty.
- **Proposed Fix**: Unpack safely: `const msgs = Array.isArray(resp) ? resp : (resp?.messages || resp?.data || []);`.

### Integration Gaps

#### [GAP-01] Magic Prompt Hand-Rolls Job Creation and Bypasses Canonical Submission Pipeline
- **Severity**: Medium
- **Location**: `backend_v2/api/routes/prompts.py:285-330`
- **Evidence**: `magic_prompt` hand-rolls `job_service.create_job` + `queue_manager.enqueue(job.id, task_type='llm')`, bypassing `submit_llm_job` used by all other LLM routes. It bypasses default LLM provider resolution, leaves orphaned DB rows without rollback if enqueue fails, and fails to cancel the job upstream if `wait_for_job_completion` times out.
- **Proposed Fix**: Migrate to `await submit_llm_job(session, workflow, metadata={"source": "magic_prompt"})` and ensure timeouts cancel the job via `cancel_job_processing`.

#### [GAP-02] Double-Untransform Coordinate Calculation on World Map Pan/Zoom
- **Severity**: Medium
- **Location**: `frontend_v2/src/pages/WorldMap.jsx:38, 50-52, 63`
- **Evidence**: `mx = (e.clientX - rect.left - mapOffset.x) / mapScale` subtracts `mapOffset.x` and divides by `mapScale`. Then `fromSvgX(mx)` subtracts `mapOffset.x` AGAIN and divides by `(MAP_WIDTH * mapScale)`. As a result, clicking to place a pin or dragging a pin when the map is panned or zoomed computes severely distorted coordinates.
- **Proposed Fix**: Pass raw container pixel deltas into `fromSvgX`/`fromSvgY`: `fromSvgX(e.clientX - rect.left)` and `fromSvgY(e.clientY - rect.top)`.

#### [GAP-03] HybridRemoteEngine Cancellation Lacks Abort Registry and Cancelled Jobs Set
- **Severity**: Medium
- **Location**: `backend_v2/services/engines/hybrid_engine.py:397-401`
- **Evidence**: `HybridRemoteEngine.cancel_job` delegates to its child engines but fails to add `job_id` to its own `self._cancelled_jobs` set. When callers check `engine.is_cancelled(job_id)` on the hybrid engine instance, it returns `False`.
- **Proposed Fix**: Record `self._cancelled_jobs.add(job_id)` on `self` during `cancel_job` and clear it on completion.

### Tech Debt & Duplication

#### [DEBT-01] BeamEngine Background Download Task Leak on Close
- **Severity**: Medium
- **Location**: `backend_v2/services/engines/beam_engine.py:96-113`
- **Evidence**: `BeamEngine.close()` closes `self._http` but does not cancel or await `self._background_tasks`. Running downloads continue or crash with unhandled client closed errors.
- **Proposed Fix**: In `close()`, cancel all tasks in `self._background_tasks`, await them with `return_exceptions=True`, and clear the set before closing `_http`.

### Architecture & Performance

#### [ARCH-01] Blocking Synchronous File I/O and DB Transactions on Event Loop in Character Card Import
- **Severity**: Medium
- **Location**: `backend_v2/api/routes/world_vault/characters.py:757-759`
- **Evidence**: `commit_character_card_import` is an `async def` route that calls `_import_card_payload` directly on the asyncio event loop. `_import_card_payload` executes synchronous disk I/O (`open(..., "wb")`), PNG text chunk stripping, CHARX decoding, and synchronous SQLAlchemy commits, blocking the entire event loop during file uploads.
- **Proposed Fix**: Wrap with `await asyncio.to_thread(_import_card_payload, session, payload, filename, force_new=...)`.

#### [ARCH-02] N+1 Query Loop in Batch Character Collections Retrieval
- **Severity**: Medium
- **Location**: `backend_v2/api/routes/collections.py:217-231` & `backend_v2/infrastructure/repositories/collection_repo.py`
- **Evidence**: `get_character_collections_batch` loops through character IDs executing `repo.get_collection_by_character_id` and then `repo.get_collection_images` per ID, resulting in 2N queries.
- **Proposed Fix**: Add `get_collections_by_character_ids(character_ids)` to `CollectionRepository` to load collections in 1 query, and batch-fetch images using `get_images_for_collections` in 1 query (2 queries total instead of 2N).
