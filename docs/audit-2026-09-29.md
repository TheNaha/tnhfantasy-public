Supersedes `docs/audit-2026-09-28.md`, `-27`, `-26` and `-26-followup` for
everything it marks fixed.

## P0 — fixed

### 1. The Lorebooks page crashed with `RangeError` on open
`frontend_v2/src/hooks/useLorebooks.js:8`

```js
const LOREBOOK_ENTRIES_KEY = (lorebookId) => LOREBOOK_ENTRIES_KEY(lorebookId);
```

The factory called itself. Every consumer raised *Maximum call stack size
exceeded* during render — `pages/Lorebooks.jsx:280` and
`components/workspace/EntityContextInspector.jsx:54`. The same key was called in
the `onSuccess` of **all six** entry mutations, so creating, updating, deleting,
reindexing, importing or bulk-deleting a lorebook entry wrote to the server and
*then* threw in its invalidation: the list never refreshed.

`Lorebooks.test.jsx` and `EntityContextInspector.test.jsx` both `vi.mock` the
hook module, so neither could see it. Introduced in `22cc272c`.

**Fixed**, with `src/hooks/useLorebooks.test.js` importing the real module. The
tests were verified to fail against the original code and pass against the fix.

### 2. Every mutation retried on failure, on every page load
`frontend_v2/src/App.jsx:271`

The effect applying the user's cache-time settings called
`queryClient.setDefaultOptions({ queries: {…}, mutations: { retry: 1 } })`.
`setDefaultOptions` *replaces* both sub-objects wholesale, so this reinstated
the `retry: 1` the QueryClient constructor had just set to `retry: 0` with a
ten-line comment explaining why react-query v5 retries mutations regardless of
method. The guard above it compared against a hardcoded `gcTime` of 30 minutes
while `settingsStore` defaults to 10, so it never matched and the overwrite was
unconditional, not an edge case.

Consequence: a lost response re-sent non-idempotent POSTs and DELETEs —
duplicate jobs, duplicated chat messages **and duplicate paid LLM calls**,
duplicate characters, and a DELETE that succeeded server-side then reporting
*Failed to remove job* on its 404.

**Fixed** by merging into the existing defaults, so the constructor's policy
survives a settings change.

### 3. Batch "Add to favorites" favourited only the last image
`frontend_v2/src/hooks/useFavorites.js` + `useDashboardSelection.js`

`toggleFavorite` is a read-modify-write of the *whole* favorites list, and
`settingsApi.updateFavorites` is a full-list `POST`. The batch handler looped it
synchronously, but `mutate()` runs `onMutate` asynchronously — so every
iteration read the same pre-batch list and computed "base + one image". N
overwrites went to the server, the last one won, and the UI reported
*Added N images to favorites*. The `onSettled` invalidation then quietly
corrected the display to 1, so it failed invisibly.

**Fixed** with a single `addFavorites` that merges and writes once.

### 4. Branching a story chapter silently deleted the prose
`backend_v2/api/routes/world_vault/stories.py:1394`

`branch_chapter` rebuilt the forked chapter's `content` **exclusively from the
beat prefix**. `chapter.content` was never read. Hand-typed editor text never
creates a beat, and `restore_chapter_revision` sets `content` from a snapshot
while leaving `beats` untouched — so the two diverge after any restore. The user
clicked Branch, was navigated to the new chapter, and found their chapter
truncated, while the dialog said *The original chapter is untouched*.

**Fixed**: the fork is now taken from the prose, truncated at the anchor beat
using the same `_beat_snippet` convention `_replace_beat_text` already owns,
falling back to the beat-derived text when the two have drifted. Also fixed the
404, which reported the *chapter* id for a bad *beat* id.

### 5. Every agentic `narrate_scene` turn cost two paid LLM calls and wrote the narration twice
`backend_v2/services/orchestrator_service.py:513` + `services/job_queue.py:256`

`_tool_narrate_scene` creates an LLM job row with `status=PENDING,
claimed_at=NULL` and deliberately does **not** enqueue it — it runs inline,
because the agentic chain holds the parent job's queue slot. But the Postgres
claim query selected *any* `task_type='llm' AND status='PENDING' AND
claimed_at IS NULL` row; enqueueing was never part of the predicate. So the LLM
worker claimed the "not enqueued" job within a second. Two independent
completions, two `JOB_COMPLETED` events for one job id, and
`_handle_narrator` inserted the same paragraph into the chat **twice**.
`llm_workers = max(1, len(llm_providers))`, so the LLM pool always polls.

**Fixed** by making "enqueued" a queryable fact: new `jobs.enqueued_at` column,
stamped only by `QueueManager.enqueue` (the single funnel all 20 dispatch paths
go through), and required by the claim query. Migration `074` backfills existing
PENDING rows so a deploy does not strand its queue.

### 6. ~40 CSS classes were deleted while 94 live references remained
Commit `10024929` ("a real token layer") removed `.tab-bar`, `.metric-chip`,
`.provider-dot`, `.pb-safe`, `.text-gradient-primary`, `.custom-scrollbar`,
`.glow-focus`, `.card-elevated`, `.glass` and others from `src/index.css`, and
restored only `.glass-panel`. Every remaining class became a silent no-op:

- `.provider-dot` lost its width/height, so the sidebar's **System Status panel
  rendered a 0×0, invisible status dot** on every provider.
- `.tab-bar` (the provider detail strip) carries no Tailwind classes at all, so
  its buttons fell back to browser-default grey chrome with no active underline.
- `.metric-chip` — all 13 provider metric pills collapse to bare text.
- `.custom-scrollbar` — never defined in the repo's history; 34 dead
  `className`s.

Lint was clean, the build was clean, and the existing token test only counts
literals, so nothing caught it.

**Fixed** by restoring the rules in `@layer components`, written against the
token variables so they follow the theme. `designTokens.test.js` gained three
assertions, including that `.provider-dot` still has a size and that all nine
status tones have a colour.

### 7. Every Settings-UI change was lost on production container recreate
`backend_v2/config.py` + `docker-compose.yml`

`_config_path` resolved to `<repo>/config.json`, i.e. `/app/config.json` in the
container. The production compose mounts only `./data:/data`, so that path is the
container's **writable layer**. `update_config` answered 200 and every system
prompt, `generator.default_checkpoint`, `jobs.*` and `image_processing.*` change
was discarded by the next `up --build`. Only the dev override's
`./backend_v2:/app` bind mount made it durable, which is exactly why this was
invisible: dev worked, production did not.

**Fixed** with `COMFY_CONFIG_PATH`, set in compose to `/data/config.json` (the
same bind mount as Postgres and the generated images), plus a first-boot seed
from the shipped defaults.

### 8. `remote_agent/.env.agent` was baked into a published image
`.dockerignore:1`

The root `.dockerignore` pattern was `.env*`, which is **root-anchored**.
`remote_agent/docker-compose.yml` builds with `context: ..` and its Dockerfile
does `COPY remote_agent/ /app/remote_agent/`, so the nested `.env.agent` — the
file the deployment doc tells you to create, holding a live
`REMOTE_AGENT_TOKEN` — went into the build context and into a layer. `.gitignore`
covers it for git and gitleaks, which is precisely why the *image* was the only
leak route and therefore the one nobody was looking at.

**Verified empirically**: built a `FROM scratch` probe with both patterns. The
old one produced `ctx/remote_agent/.env.agent` in the image; the new one does
not, while still including `.env.example*`.

### 9. The Beam GPU inference endpoint had no authentication
`provider_containers/image_worker/engines/beam/beam_app.py:700`

`verify_beam_token` gates `storage_app`, `download_app` and `extractor_app`. The
`@realtime` `comfy_gpu` route — the one that bills GPU time, executes an
arbitrary ComfyUI graph, and reads and writes `/mnt/data` — took no token at
all, and the worker's `Authorization: Bearer` header went unread. Anyone who
learned the deployment URL got free SDXL inference.

**Fixed** with a fail-closed check. The token travels in the payload as well as
the header: a `@realtime` handler's signature is what the SDK decorator
inspects, and the request-context object that would carry the header is not
present in every deployed version, so a second positional parameter would fail
to bind rather than fail safe. Both ends changed in one commit.

### 10. A malformed auth header became a paid retry storm
`provider_core/router.py:69`, `beam_app.py:278`

`hmac.compare_digest` raises `TypeError` on a `str` holding a byte ≥ 0x80, and
Starlette decodes header bytes as latin-1. A single non-ASCII character in
`X-Provider-Token` raised *inside* the comparison; the catch-all turned that
into **500 with `retryable: true`**, which the backend reads as "this provider is
unhealthy, try it elsewhere" — so one bad header re-ran the request across the
whole pool, for money. Reproduced with a raw ASGI request.

**Fixed** by encoding to bytes first, and unified: the five hand-written copies
of "compare a token" now share `provider_core/auth.py`, which also fixes the
inconsistency in whether each one failed open or closed.

### 11. The gallery's ordering key was not indexed
`infrastructure/migrations/steps.py`

`ASSET_GALLERY_TIMESTAMP` (`coalesce(generated_at, created_at)`) is what the
gallery listing, its date seek and its day histogram all order on, and the
codebase goes out of its way to bind the same expression object in all three so
they cannot disagree. Nothing indexed it, and the two composite indexes that
look relevant lead with `user_id`, which is never in the predicate.

The rows are wide — the average non-deleted asset measured **3,469 bytes**,
because `metadata_` carried the whole job metadata — so every gallery page read
the entire table and detoasted the jsonb for each row before the top-N sort
could discard it. Migration `075` adds a partial index on that expression
`WHERE deleted_at IS NULL`.

### 12. A full model record was denormalized into every job
`backend_v2/services/job_metadata.py` (new)

The frontend's model picker works on `GET /api/v2/models/`, whose rows are full
catalogue records: description HTML, tags, file list, provider statuses, and for
a checkpoint seven base64 preview thumbnails. The client sent that whole object
as the job's `checkpoint`, and every selected LoRA as `loras`. With one
checkpoint and six LoRAs that is **59 KB per job row**.

Nothing reads any of it: `getCheckpointDisplayName` reads
`display_name || name`, and `loras` only for `.length`, `name` and `strength`.
`build_job_outputs` then copies both verbatim into the PNG sidecar and
`assets.metadata_`, so it was paid for three times — which is why `jobs` was
6.9 MB for 58 rows and `assets` 207 MB for 16.5 k.

**Fixed** with an allowlist (not a denylist, so a new catalogue field cannot
re-inflate every future row) applied at the single write path, covering all
callers. A representative payload goes from 131,850 B to 1,098 B.

> The `/api/jobs` and gallery byte figures are the *pre-fix* measurement. The
> already-written rows are not rewritten; existing bloat shrinks as jobs are
> cleared or the tables are vacuumed. A backfill migration was considered and
> rejected as riskier than the win — rewriting 207 MB of jsonb unattended
> during a deploy is not a trade worth making for disk space.

### 13. The context builder could send a paid prompt with no conversation
`services/context_builder.py`

Three compounding gaps, all fixed:

- `if remaining_budget <= 0: return system_msgs` — when the system block alone
  exceeded the budget the call returned the character sheet and **no
  conversation at all**. The system prompt was also never shortened, so any
  large card or lorebook could trigger it.
- The prune loop required `len(unpinned_msgs) > 2`, so a one- or two-message
  history was never pruned no matter how large. A story continuation is exactly
  that shape — one message carrying a whole chapter.
- With the floor reached, the survivors went out whole, so two 40,000-token
  messages were sent at ~80,000 against a 4096 budget.

`MIN_UNPINNED_MESSAGES` stays authoritative for message *count* — the existing
tests pin that a tight budget prunes to the floor and stops, and truncation must
not overturn it for messages a provider would accept. Truncation is therefore
scoped to messages that are individually unsendable
(`TRUNCATION_MIN_TOKENS = 8192`, below every real context window), and applies
proportionally across them because per-message trimming does not compose.

### 14. Two chat loads had no limit at all
`infrastructure/repositories/message_repo.py`

`list_by_chat(chat_id)` defaulted to *every message in the chat*. Two callers
relied on it and then used a slice: the context build (keeps the most recent
`MAX_CONTEXT_MESSAGES` = 200) and the scene-job prep (uses the last 10). The
database was materialising and ORM-instantiating the whole transcript per send.
`list_by_chat` now has a default ceiling and a `newest_first` mode that lets the
database do the limiting.

### 15. `/api/jobs/active` shipped the full metadata of every queued job
`api/routes/jobs.py:231`

It called `_job_to_dict(job)` with the default `include_full_metadata=True`,
unlike its sibling `list_jobs`. PENDING has no limit, so the response carried
each job's entire `metadata_` — including `original_messages`, the whole agentic
conversation — and `useActiveJobs` polls it every 5 seconds from the dashboard.

### 16. The previously-claimed "1× concurrency" was a measurement artifact
The prior audit reported the backend as effectively single-threaded, based on 20
concurrent `GET /api/settings` taking 400 ms. Re-measured with a proper client
instead of 20 `curl` processes, the real figure is a **plateau at ~300 req/s**,
and `get_settings` does no database work at all — it returns a cached module
global. The ceiling is single-process GIL plus the middleware chain, not
serialization. `log_requests` costs about 15% of it.

Correcting this matters because the obvious fix is wrong. Production runs
**one** uvicorn worker, and `startup_application` starts the job queue, the
PG-notify listener, the APScheduler jobs, `queue_manager.recover()` and the
websocket broadcast **in-process**. `--workers N` would duplicate all of it and
double-dispatch jobs. Multi-worker needs the queue and scheduler externalised
first; it is not a config change, and it was not attempted here.

## P2 — open, with the fix decided

These are real and worth doing; they are listed so they are not lost, not
because they were started.

- **`jobs.outputs` and `asset.metadata_` bloat in existing rows.** Fixed at the
  write path; the 207 MB already on disk is not rewritten. See note 12.
- **The `prose` typography gap.** 64 elements name `prose prose-invert
  prose-sm`; `@tailwindcss/typography` is not a dependency. The Story preview
  toggle, the public `StoryReader` and three model-description panels render
  markdown with no heading sizes, list indentation or `pre`/`code` styling. The
  two compensating rules are restored; the structural fix is to add the plugin.
- **`/api/v2/models/` is 1.58 MB** for 484 LoRAs and 4 checkpoints, of which
  804 KB is CivitAI description HTML that no component renders (`description` is
  read only for client-side search on the *preloaded* path, where the backend is
  not doing the filtering). Needs a summary/list DTO.
- **`@dnd-kit/utilities` is imported by three components but is not in
  `package.json`.** It resolves only as a transitive dependency of
  `@dnd-kit/core` and `@dnd-kit/sortable`. Any hoisting change or a v11 bump is a
  build failure.
- **`MemoryRepository` serialises the 384-float `embedding`** in
  `list_memories`, `get_memory`, `create_memory` and `update_memory`. A 200-row
  page is ~1.5 MB of JSON the UI never uses.
- **`Story`'s AI-illustrate prompt loads every lorebook entry** when RAG is off
  — the unbounded path `context_builder` deliberately bounded and
  `rag_pipeline` documents as fixed. A user who turns RAG off to save memory gets
  an unbounded prompt the moment they illustrate a chapter.
- **The story lorebook relevance query is always empty.** `_lorebook_query` is
  built with `getattr(m, 'role', None) in (USER, CHAR)`, but every story path
  passes a list of **dicts**, so `recent` is empty and the query is `""`.
  `search_lorebook_entries` then skips semantic search and returns
  `entries[:limit]` — the 5 newest entries per lorebook. Story continuation gets
  recency-ordered lore, never relevance-ordered, while `story_illustrate_system_prompt`
  does it correctly, so the two paths disagree.
- **RAG has no similarity threshold** in either semantic search, so
  `[Relevant Memories]` and `[World Information]` are injected unconditionally
  even when the nearest neighbour is unrelated.
- **The lorebook keyword fallback scans 50 rows** (`created_at DESC`) and the
  keyless-constant fallback takes 10 (`created_at ASC`). For a SillyTavern world
  book imported before Reindex, only the newest 50 and the oldest 10 are ever
  visible.
- **`memory_extraction` has no `ai.memoryExtractionEnabled` gate and no
  dedup.** `create_memories_from_extraction` inserts unconditionally, and the
  hook fires for swipes and regenerations too, so regenerating a reply inserts a
  second copy of the same 1–5 memories — which are then always in the top-10
  retrieval set. It is throttled to every 4th user turn, but still an
  unconditional paid call with no off switch.
- **The idle simulator has no per-tick cap** and builds its workflow without
  `sampler_overrides(chat)`, so a chat configured for `temperature: 0.2` /
  `max_output_tokens: 300` gets unbounded, high-temperature, long-form replies
  that the user did not ask for.
- **`rollback_chat` and `regenerate_reply` do not cancel in-flight LLM jobs.** The
  user hits undo, messages are deleted, and 20 s later the already-paid job
  completes and appends the reply they just undid.
- **ST round-trip is lossy**: export writes `swipes`/`swipe_id` but
  `_import_chat_sync` reads only `mes`, so every alternate and the active index
  are dropped on re-import, as are `pinned` and `message_metadata`. Export
  hardcodes `constant: false, disable: false, order: 100, depth: 4,
  probability: 100`, so a disabled ST entry switches **on** here and a keyless
  one stops firing there.
- **`edit_message` does not adjust `active_index`**, so after editing a swiped
  message the ST export writes a `swipe_id` pointing at text the user is not
  seeing, and the next swipe selects a shifted element.
- **`get_session_context()` is an `@asynccontextmanager` yielding a
  synchronous Session**, so `async with` gives no concurrency benefit and reads
  as async. Every world-integration handler runs its sync SQLModel work inline
  on the event loop as a result.
- **`_PgNotifyListener` has no restart supervision.** It degrades to the 1 s
  poll when the connection dies, so claims still happen, but nothing logs or
  recovers the listener itself.
- **~30 `COMFY_*` env vars are read but appear in no `.env.example*`**, and ~15
  more are `Settings` fields pydantic reads and nothing then honours — setting
  them does nothing. Six `PROVIDER_HTTP_*` vars are documented in
  `.env.example.provider.engines` and read by no code at all.
- **Production publishes backend port 8002 on `0.0.0.0` with no
  authentication.** `docs/api.md` claims a Traefik mitigation but only 5174 has a
  router. This is a product decision, not a bug to fix unilaterally; the
  deployment doc now says so explicitly.
- **`docker compose config` prints every credential in cleartext** — the
  natural debugging step, and the one output people paste into issues.
- **`backend_v2/config.json` is still tracked**, so Settings-UI changes dirty
  the working tree in dev. `COMFY_CONFIG_PATH` makes this fixable by untracking
  it; doing so needs a first-boot seed, which now exists.
- **The dev frontend bind-mount omits `package.json`, `package-lock.json` and
  `postcss.config.js`**, and initialises the anonymous `node_modules` volume from
  the image — a lockfile change leaves the container serving the previous
  dependency set silently unless `-V` is passed.
- **`retryable_for_exception` and the 503 handler need one more pass**: several
  validation and filesystem paths still answer 500 with the raw exception string
  in the body, which leaks driver detail and is misread as retryable.

## How this was verified

Every P0 was checked against the running stack before and after, not just
against the code. The `.dockerignore` leak was proved by building probe images
with both patterns and diffing their contents. The Beam auth gate and the
`indeterminate` contract are covered by 22 new provider tests; the auth
comparison lives in `provider_core/auth.py` precisely so it is testable, since
`beam_app` cannot be imported in the test venv at all — which is why the gate went
unaudited in the first place. The three frontend P0s have a regression test file
that imports the real modules and was confirmed to fail against the original
code.

The 6/8 CSS restoration and the non-root frontend were verified by building the
production image and running it: uid 1000, index/API/SPA routes all 200, no
nginx errors. The live site was reachable at `:5174` throughout.

## Still worth deciding

1. **Externalise the job queue and scheduler**, then run more than one uvicorn
   worker. Today the ceiling is ~300 req/s on a single core, and the reason
   `--workers 2` is unsafe is that the queue, the PG-notify listener, the
   scheduler and the websocket broadcast are all in-process. This is the one
   change with real architectural upside, and the one with the largest blast
   radius.
2. **Whether 8002 should be reachable at all** outside the host.
3. **Whether a `pg_dump` schedule should live in this repo** or stay an operator
   responsibility. `data/pgdata` is the entire World Vault and nothing backs it
   up.
4. **Whether the tracked `config.json` should be untracked** now that
   `COMFY_CONFIG_PATH` plus a seed exists.
