## Phase 1 — High-impact, reuse-heavy (P1)

These three features build on backend services that already exist and mainly need frontend wiring.

### 1. Voice Cloning + Per-Character Voices

**Roleplay Chat — P1 — Medium**

**Rationale:** `tts_workflow_builder.py` already defines three Qwen3-TTS graphs (voice design from description, speak in an adopted voice, clone from reference audio). `Voices.jsx` + `useVoices.js` manage voices. The gap: no way to assign a voice to a Character and play it in chat. This is the most natural next step for the roleplay pillar.

**Existing infra to build on:**
- `backend_v2/services/tts_workflow_builder.py` — three TTS graphs
- `backend_v2/api/routes/world_vault/voices.py` (implied) — voice CRUD
- `frontend_v2/src/hooks/useVoices.js` — voice list/mutations
- `frontend_v2/src/pages/ChatWorkspace.jsx` — chat message rendering

**What needs to be built:**
1. **Backend:** Route to trigger a TTS job for a specific text + voice (or voice-design clone) and return an audio URL. Wire into the job queue / WebSocket completion events.
2. **Frontend:** "Assign voice" control on the Character modal. "Speak this message" button on chat messages in `ChatWorkspace.jsx` that fetches/plays audio. Audio player component.

**Dependencies:** None beyond existing TTS graphs.

**Definition of done:** User can clone/design a voice, assign it to a character, click a message in chat to hear that character speak it, and the audio plays in-browser.

---

### 2. Comic Strip Assembly UI

**Story Sandbox — P1 — Medium**

**Rationale:** `comic_exporter.py` backend service already splits a story chapter into panels, generates consistent images per panel (same seed + visual_tags per character), and assembles a CBZ archive + self-contained HTML reader. It is triggered manually with no frontend.

**Existing infra to build on:**
- `backend_v2/services/comic_exporter.py` — full comic export pipeline
- `frontend_v2/src/components/QueueVisualization.jsx` — job progress display
- `frontend_v2/src/pages/StoryReader.jsx` — chapter view

**What needs to be built:**
1. **Frontend:** Comic assembly page — select story chapter, choose panel count/layout, map characters to visual tags, set seed per panel, trigger export.
2. **Frontend:** Job polling via WS, then download link for CBZ + HTML reader.

**Dependencies:** Comic exporter backend route must accept the same parameters the frontend will send.

**Definition of done:** User can configure a chapter → comic export and download a CBZ + HTML reader.

---

### 3. Story Branching UI / Alternate Timelines

**Story Sandbox — P1 — Medium**

**Rationale:** `branches.py` API route + `useBranches.js` hook handle branching chats at the data layer. No UI exists to fork a story at any decision point, visualize the branch tree, or switch timelines.

**Existing infra to build on:**
- `backend_v2/api/routes/world_vault/branches.py` — branch CRUD
- `frontend_v2/src/hooks/useBranches.js` — branch mutations
- `frontend_v2/src/hooks/useStoryStreaming.js` — story chapter streaming

**What needs to be built:**
1. **Frontend:** Branch-tree view on story chapters — visualize forks, create a branch from any message/chapter, switch between timelines.
2. **Frontend:** Side-by-side comparison view for two branches.

**Dependencies:** Branch API must support creating a branch from a specific chapter/message index.

**Definition of done:** User can fork a story at any chapter, see the branch tree, and switch between alternate timelines.

## Phase 2 — World-building expansion (P2)

These features deepen the World Vault and World Architect pillars.

### 4. World Templates / Starter Packs

**World Building — P2 — Low–Medium**

**Rationale:** `world_onboarding_service.py` + `useWorldOnboarding.js` guide users through world creation. Pre-built templates reduce the blank-page problem.

**Existing infra to build on:**
- `backend_v2/services/world_onboarding_service.py`
- `frontend_v2/src/hooks/useWorldOnboarding.js`
- `frontend_v2/src/pages/WorldHub.jsx` (implied)

**What needs to be built:**
1. **Backend:** Template definitions (JSON) — high fantasy, cyberpunk, gothic horror, space opera — with pre-populated characters, locations, lorebooks, scenarios.
2. **Frontend:** Template picker in onboarding flow; apply template to a new world.

**Definition of done:** New user can pick a world template during onboarding and get a pre-populated world.

---

### 5. Cross-Story Character Portability UI

**World Building — P2 — Low–Medium**

**Rationale:** `character_portability.py` backend service handles character bundle export/import. Needs the upload/import frontend.

**Existing infra to build on:**
- `backend_v2/services/character_portability.py` — bundle export/import
- `frontend_v2/src/pages/Characters.jsx` / `CharacterModal.jsx`

**What needs to be built:**
1. **Frontend:** Export character as bundle (card + images + lorebook links) → download file.
2. **Frontend:** Import bundle → create character in current world.

**Definition of done:** User can export a character bundle and import it into another world/story.

---

### 6. Interactive World Map

**World Building — P2 — Medium–High**

**Rationale:** `Locations.jsx` + `useLocations.js` manage locations; `world_architect/` components exist. No spatial view to place locations, characters, and story events.

**Existing infra to build on:**
- `frontend_v2/src/pages/Locations.jsx`
- `frontend_v2/src/hooks/useLocations.js`
- `frontend_v2/src/components/world_architect/`

**What needs to be built:**
1. **Frontend:** Canvas/SVG map — place location pins, link characters to places, show story chapters per location.
2. **Frontend:** Click pin → jump to location lore; click character → show where they appear.

**Dependencies:** Location entity needs optional coordinates (lat/lng or x/y) — may require a small entity migration.

**Definition of done:** User sees a map of their world with location pins and can navigate to location lore from the map.

## Phase 3 — Longer-term / experimental (P3)

### 7. Character Relationship Timeline

**Roleplay Chat — P3 — Medium**

**Rationale:** `RelationshipGraph.jsx` shows character relationships; `memory_extraction.py` pulls memories from chats. Expand into a timeline of how relationships evolved across stories/chats.

**Existing infra to build on:**
- `frontend_v2/src/components/RelationshipGraph.jsx` (implied)
- `backend_v2/services/memory_extraction.py`
- `frontend_v2/src/hooks/useMemories.js` (implied)

**What needs to be built:**
1. **Frontend:** Timeline view — relationship milestones between two characters across chats/stories, with message snapshots.
2. **Backend:** Query messages/memories tagged with character pairs and timestamps.

**Definition of done:** User can view a relationship timeline between any two characters with key moments.

---

### 8. Image-to-Story Reverse Pipeline

**Image Generation — P3 — Medium**

**Rationale:** Existing image generation (ComfyUI workers) + LLM chat pipeline + story sandbox. Reverse direction: image → text → image.

**Existing infra to build on:**
- `backend_v2/services/llm_workflow.py`
- `backend_v2/services/chat_pipeline.py`
- `frontend_v2/src/pages/SimpleGenerator.jsx`

**What needs to be built:**
1. **Frontend:** Upload image → describe it via LLM → generate story prompt or opening chapter → continue with images.
2. **Backend:** Image-to-text endpoint (VLM or captioning) feeding into chat_pipeline.

**Definition of done:** User uploads an image and gets a story chapter generated from it.

---

### 9. Batch Story Chapter Generation

**Image Generation / Story Sandbox — P3 — Low**

**Rationale:** `BatchGenerate.jsx` exists for batch image generation. Extend the concept to story chapters — generate multiple chapter variants from one prompt, pick the best to continue.

**Existing infra to build on:**
- `frontend_v2/src/pages/BatchGenerate.jsx`
- `frontend_v2/src/hooks/useBatchPresets.js`
- `frontend_v2/src/hooks/useStories.js` (implied)

**What needs to be built:**
1. **Frontend:** Batch chapter UI — one prompt, N variants, side-by-side preview, "continue with this one" action.

**Definition of done:** User can generate multiple story chapter variants and select one to continue.

---

### 10. Provider Cost & Usage Dashboard

**Provider System — P3 — Medium**

**Rationale:** Providers page UX was recently improved (attention banners, disabled-button hints, issue cards). `provider_telemetry_service.py` exists. Cost/usage analytics is the missing UI layer.

**Existing infra to build on:**
- `backend_v2/services/provider_telemetry_service.py`
- `frontend_v2/src/pages/Providers.jsx`

**What needs to be built:**
1. **Backend:** Cost aggregation per provider/model over time windows.
2. **Frontend:** Dashboard — cost by provider, usage charts, rate-limit warnings, budget alerts.

**Definition of done:** User can see how much each provider has cost and which models are most expensive.

## Suggested Implementation Order

| Order | Feature | Rationale |
|-------|---------|-----------|
| 1 | Voice cloning + per-character voices | Highest user-visible impact; TTS graphs already done |
| 2 | Comic strip assembly UI | Backend pipeline complete; frontend is a form + poller |
| 3 | Story branching UI / alternate timelines | Data layer complete; pure frontend visualization |
| 4 | World templates / starter packs | Low effort; improves new-user onboarding |
| 5 | Cross-story character portability UI | Backend service complete; frontend import/export |
| 6 | Interactive world map | Needs entity coordinate migration; higher effort |
| 7 | Character relationship timeline | Depends on memory/query indexing |
| 8 | Image-to-story reverse pipeline | Needs VLM/captioning integration |
| 9 | Batch story chapter generation | Simple extension of existing batch UI |
| 10 | Provider cost & usage dashboard | Needs telemetry aggregation + charts |

**Recommended first sprint:** Features 1–3 (all P1, all medium effort, all reuse existing backend). These ship the most user-visible value with the least new backend work.

## Notes

- All effort estimates assume one developer working part-time on the feature.
- "Medium–High" (world map) is the only feature that likely requires a schema change (location coordinates).
- No public contracts are changed by any of these features; all are additive frontend + optional backend routes.
- Before starting any feature, check `docs/audit-2026-10-21.md` and `docs/STATUS.md` for the authoritative status of the area being touched.
